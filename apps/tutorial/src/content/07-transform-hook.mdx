_This is the eighth installment in a series where we build a toy Next.js on top of Vite. [Part 6](/06-production-builds#loaders-are-still-in-the-client-bundle) ended with an uncomfortable discovery: the production client bundle still contains every loader, because pages are loaded with `React.lazy(() => import(...))` and tree-shaking can't remove exports from a dynamically imported module. The same holds in dev, where the browser fetches each page module whole. The fix is the `transform` hook: rewrite each page's source for the client environment so the loader, and the imports only it needs, never enter the client graph in the first place._

---

## The problem

Here's a page whose loader talks to a database:

```tsx title="src/pages/dashboard.tsx"
import { db } from "../lib/database"; // pulls in 'pg' (PostgreSQL driver)
import { defineLoader } from "eigen/helpers";
import type { PageProps } from "eigen/types";

export const loader = defineLoader("/dashboard", async () => {
  const users = await db.query("SELECT id, name FROM users");
  return { users: users.rows as { id: number; name: string }[] };
});

type LoaderData = Awaited<ReturnType<typeof loader>>;

export default function Dashboard({ data }: PageProps<"/dashboard", LoaderData>) {
  return (
    <ul>
      {data.users.map((u) => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}
```

The client virtual module from [Part 2](/02-route-discovery-plugin#plugin-hooks) only ever renders `Dashboard`. But it reaches the file through `React.lazy(() => import("/src/pages/dashboard.tsx"))`, and a dynamic import hands over the whole module. So the client chunk for this page contains:

1. **The loader itself**, including the SQL, any API keys or internal URLs it mentions, and its error messages.
2. **Everything the loader imports.** The first line pulls in `../lib/database`, which pulls in `pg`, which pulls in `net`, `tls`, and `fs`. Vite replaces Node built-ins with empty browser stubs and warns ("Module "net" has been externalized for browser compatibility"). The rest of the driver still gets bundled, and at best it's dead weight. At worst it throws the moment the page chunk evaluates in the browser.

This is the "server-only code leaking into client bundles" problem. Every framework that ships a loader/component split has to solve it:

- [Next.js](https://nextjs.org)'s Pages Router runs an SWC transform on every page for the client build. It removes `getServerSideProps`/`getStaticProps` and then eliminates the imports that only those functions used, so the server code never reaches the browser bundle.
- [Remix](https://remix.run) and React Router v7 do the same for route modules (`loader`, `action`, and friends are removed from the client build), and also offer [`.server` modules](https://remix.run/docs/en/main/file-conventions/-server) that the client build refuses to include at all.
- React Server Components draw the boundary at [`"use server"` / `"use client"` directives](https://react.dev/reference/rsc/use-client) and split the module graph at those markers.

Our solution follows the first model. A `transform` hook removes the server-only exports, _and the imports only they depend on_, from each page file, but only when the file is being processed for the client environment. The SSR environment sees the file unchanged.

## A first attempt: regular expressions

The tempting approach is a regex that deletes `export const loader = …` up to the end of the statement:

```typescript
// Don't ship this. It's here to show why it breaks.
code.replace(/export\s+const\s+loader\s*=[\s\S]*?;/, "");
```

"Up to the end of the statement" is where it falls apart. A lazy `[\s\S]*?;` stops at the _first_ semicolon, and every real loader has semicolons inside its body. Run it on the loader from [Part 5](/05-typed-loaders):

```tsx
export const loader = defineLoader("/posts/:id", async ({ params }) => {
  const res = await fetch(`https://jsonplaceholder.typicode.com/posts/${params.id}`); // ← the regex stops here
  return (await res.json()) as { id: number; title: string; body: string };
});
```

The regex removes everything through `);` and leaves the rest of the function body dangling: a syntax error. You can patch this ("match up to `});` at the start of a line"), and the next loader breaks a different way:

- **Formatting**: a loader written as `export const loader = async () => ({ … })` or ending in `})` without a semicolon.
- **Nested braces and template literals**: `${…}` and object literals inside the body confuse any brace-counting pattern.
- **`satisfies` and generics**: `export const loader = (async () => { … }) satisfies LoaderFn<"/posts/:id">;`.
- **Other export forms**: `export async function loader() { … }`, `export { loader }`, `export { load as loader }`, `export { loader } from "./loaders"`.
- **Strings and comments**: `export const message = "export const loader = 'oops'";` contains the pattern without being a loader.
- **Imports**: deciding that `db` is _only_ used by the loader means finding every reference to `db` in the file, which regex can't do reliably.

All of these are questions about the _structure_ of the code, and regex sees only characters. The answer is to parse.

## The real transform: parse, then edit

Vite 8 exports `parseAst`, a binding to Rolldown's Oxc parser (written in Rust). It turns TypeScript/JSX source into an [ESTree](https://github.com/estree/estree)-shaped AST, the same tree format ESLint and most JavaScript tooling understand, in well under a millisecond for a typical page. Each node carries `start`/`end` offsets into the original string, which is what lets us _edit_ the source instead of regenerating it. For the edits we use [`magic-string`](https://github.com/Rich-Harris/magic-string), the string-splicing library Vite and Rollup plugins use to make surgical changes and get an accurate source map back for free.

```bash
pnpm add -D magic-string
```

The plugin removes four server-only page exports: `loader` (this part), `middleware` ([Part 14](/14-framework-middleware)), `generateStaticParams` ([Part 16](/16-static-site-generation)), and `generateMetadata` ([Part 30](/30-route-metadata-seo)). The `default` export (the component) stays, and so does every other export, including `parse` from [Part 18](/18-runtime-validation), which must run in the browser.

```typescript title="plugins/eigen-strip-loaders.ts"
import MagicString from "magic-string";
import { parseAst, type Plugin } from "vite";

/** Page exports that only make sense on the server. `default` and `parse` stay. */
const SERVER_EXPORTS = new Set(["loader", "middleware", "generateStaticParams", "generateMetadata"]);

// A loose view of the ESTree / TS-ESTree nodes Oxc returns. Every node
// carries `start`/`end` offsets into the original source string.
interface AstNode {
  type: string;
  start: number;
  end: number;
  [key: string]: any;
}

/** Visit every node under `node`, depth-first. */
function walk(node: AstNode, visit: (n: AstNode) => void): void {
  visit(node);
  for (const key in node) {
    if (key === "parent") continue;
    const value = node[key];
    const children = Array.isArray(value) ? value : [value];
    for (const child of children) {
      if (child && typeof child === "object" && typeof child.type === "string") {
        walk(child, visit);
      }
    }
  }
}

/** Name an `export { a as b }` specifier is exported under (`b`). */
function exportedName(spec: AstNode): string {
  return spec.exported.type === "Identifier" ? spec.exported.name : spec.exported.value;
}

/** Names a top-level statement declares (`function f`, `const a = …, b = …`). */
function declaredNames(stmt: AstNode): string[] {
  if (stmt.type === "FunctionDeclaration" && stmt.id) return [stmt.id.name];
  if (stmt.type === "VariableDeclaration") {
    return stmt.declarations.filter((d: AstNode) => d.id.type === "Identifier").map((d: AstNode) => d.id.name);
  }
  return [];
}

/**
 * Remove server-only exports from a page module, then remove any imports
 * that only those exports used. Returns null when there's nothing to strip.
 */
export function stripServerExports(code: string, id: string): MagicString | null {
  const program = parseAst(code, { lang: "tsx" }, id) as unknown as AstNode;
  const s = new MagicString(code);
  const removed: Array<[number, number]> = [];
  const remove = (node: AstNode, note: string) => {
    s.overwrite(node.start, node.end, `/* [eigen] ${note} stripped for client bundle */`);
    removed.push([node.start, node.end]);
  };

  // Local bindings exported under a server-only name via `export { … }`.
  const serverLocals = new Set<string>();

  // Pass 1: export statements.
  for (const stmt of program.body as AstNode[]) {
    if (stmt.type !== "ExportNamedDeclaration") continue;

    if (stmt.declaration) {
      // export function loader() {} / export const loader = …
      const names = declaredNames(stmt.declaration);
      const server = names.filter((n) => SERVER_EXPORTS.has(n));
      if (server.length === 0) continue;
      if (server.length !== names.length) {
        throw new Error(`[eigen] ${id}: declare ${server.join(", ")} in its own export statement`);
      }
      remove(stmt, server.join(", "));
      continue;
    }

    // export { loader } / export { load as loader } / export { loader } from "./x"
    const specs = stmt.specifiers as AstNode[];
    const kept = specs.filter((sp) => !SERVER_EXPORTS.has(exportedName(sp)));
    if (kept.length === specs.length) continue;
    if (!stmt.source) {
      for (const sp of specs) {
        if (!kept.includes(sp)) serverLocals.add(sp.local.name);
      }
    }
    if (kept.length === 0) {
      remove(stmt, "server export");
    } else {
      const from = stmt.source ? ` from ${code.slice(stmt.source.start, stmt.source.end)}` : "";
      const list = kept.map((sp) => code.slice(sp.start, sp.end)).join(", ");
      s.overwrite(stmt.start, stmt.end, `export { ${list} }${from};`);
      // Only the dropped specifiers count as removed: the kept ones still
      // reference their local bindings, so those imports must survive.
      for (const sp of specs) {
        if (!kept.includes(sp)) removed.push([sp.start, sp.end]);
      }
    }
  }

  // Pass 1b: the local declarations behind `export { loader }`.
  for (const stmt of program.body as AstNode[]) {
    const names = declaredNames(stmt);
    if (names.length > 0 && names.every((n) => serverLocals.has(n))) {
      remove(stmt, names.join(", "));
    }
  }

  if (removed.length === 0) return null;

  // Pass 2: count identifier references outside import statements,
  // before and after stripping. Name-based, no scope analysis — a
  // shadowing local keeps an import alive, which is the safe direction.
  const isRemoved = (n: AstNode) => removed.some(([a, b]) => n.start >= a && n.end <= b);
  const before = new Map<string, number>();
  const after = new Map<string, number>();
  for (const stmt of program.body as AstNode[]) {
    if (stmt.type === "ImportDeclaration") continue;
    walk(stmt, (n) => {
      if (n.type !== "Identifier" && n.type !== "JSXIdentifier") return;
      before.set(n.name, (before.get(n.name) ?? 0) + 1);
      if (!isRemoved(n)) after.set(n.name, (after.get(n.name) ?? 0) + 1);
    });
  }
  // Used before, unused now → only the stripped code needed it.
  const dead = (name: string) => (before.get(name) ?? 0) > 0 && !after.has(name);

  // Pass 3: prune imports. Side-effect imports (`import "./x.css"`) have
  // no specifiers and are always kept.
  for (const stmt of program.body as AstNode[]) {
    if (stmt.type !== "ImportDeclaration" || stmt.specifiers.length === 0) continue;
    const specs = stmt.specifiers as AstNode[];
    const kept = specs.filter((sp) => !dead(sp.local.name));
    if (kept.length === specs.length) continue;
    if (kept.length === 0) {
      s.remove(stmt.start, stmt.end);
      continue;
    }
    const parts: string[] = [];
    const named: string[] = [];
    for (const sp of kept) {
      if (sp.type === "ImportSpecifier") named.push(code.slice(sp.start, sp.end));
      else parts.push(code.slice(sp.start, sp.end)); // default or `* as ns`
    }
    if (named.length > 0) parts.push(`{ ${named.join(", ")} }`);
    const typeOnly = stmt.importKind === "type" ? "type " : "";
    const source = code.slice(stmt.source.start, stmt.source.end);
    s.overwrite(stmt.start, stmt.end, `import ${typeOnly}${parts.join(", ")} from ${source};`);
  }

  return s;
}

/** String-in, string-out wrapper — handy for tests. */
export function stripLoaderForClient(code: string, id = "page.tsx"): string {
  return stripServerExports(code, id)?.toString() ?? code;
}

export default function eigenStripLoaders(): Plugin {
  return {
    name: "eigen-strip-loaders",
    // See the source before Vite's built-in Oxc plugin strips types and compiles JSX
    enforce: "pre",

    // Only the client environment; SSR keeps every export
    applyToEnvironment(environment) {
      return environment.name === "client";
    },

    transform: {
      // Hook filter: Vite skips the handler entirely for files that can't match
      filter: {
        id: /\/src\/pages\/.+\.tsx$/,
        code: /\b(?:loader|middleware|generateStaticParams|generateMetadata)\b/,
      },
      handler(code, id) {
        const s = stripServerExports(code, id);
        if (!s) return; // nothing server-only exported
        return {
          code: s.toString(),
          map: s.generateMap({ hires: true, source: id, includeContent: true }),
        };
      },
    },
  };
}
```

Run on the dashboard page above, the client environment receives:

```tsx
import type { PageProps } from "eigen/types";

/* [eigen] loader stripped for client bundle */

type LoaderData = Awaited<ReturnType<typeof loader>>;

export default function Dashboard({ data }: PageProps<"/dashboard", LoaderData>) {
  // ...unchanged
}
```

The `db` and `defineLoader` imports are gone, because the only references to them were inside the removed loader. `PageProps` survives because the component still uses it. The leftover `type LoaderData = … typeof loader` line is harmless: it's a type, and Vite's Oxc transform erases it right after our plugin runs.

Three passes do the work:

1. **Remove server exports.** Every form is a different node shape: `export const loader = …` and `export function loader` are an `ExportNamedDeclaration` with a `declaration`. `export { loader }` and `export { load as loader }` are an `ExportNamedDeclaration` with `specifiers`; for those we also remove the local `load` declaration they point at. `export { loader } from "./loaders"` has a `source` and simply disappears. When a list mixes server and client names (`export { helper, load as loader }`), only the server specifiers are dropped and recorded as removed, so `helper` and its import stay. Because these are nodes rather than text, a semicolon inside the loader body, a `satisfies` clause, or a template literal can't confuse anything: `stmt.end` _is_ the end of the statement.
2. **Count references.** Walk the rest of the file and count each identifier name, once over the original program and once skipping the removed ranges. A name that appeared before and doesn't appear after was only used by the code we removed.
3. **Prune imports.** Remove those names from their import statements, and drop a statement entirely when nothing is left. Side-effect imports (`import "./post.css"`) have no bindings, so they always stay.

The reference count is deliberately conservative. It matches on names without doing scope analysis, so a local variable that happens to share an import's name keeps that import alive. Keeping an import we could have dropped costs some bytes; dropping one the component still needs would break the page. A production implementation would use a scope-aware analyzer (Oxc's semantic analysis, Babel's scope tracker) to be exact.

<TypeDeepDive title="Concept: Abstract Syntax Trees (ASTs)">

An AST is a tree representation of source code. Instead of working with raw text (where a regex can't tell `export` in code from `export` in a string), you work with structured nodes: `ExportNamedDeclaration`, `VariableDeclarator`, `Identifier`, and so on. Each node knows its type, its children, and its position in the source. Oxc's JavaScript AST follows [ESTree](https://github.com/estree/estree), the community standard also used by Acorn, ESLint and Rollup; for TypeScript it follows the [TS-ESTree](https://typescript-eslint.io/packages/typescript-estree/) extension. We never print the tree back to code. We use node positions to tell `magic-string` which character ranges to replace, so everything we don't touch, including formatting and comments, comes through byte-for-byte.

</TypeDeepDive>

<TypeDeepDive title="Concept: The visitor pattern for tree traversal">

The visitor pattern walks every node in a tree and calls your code on each one. Our `walk` is the minimal version: visit the node, then recurse into every property that holds a node or an array of nodes. It needs no list of node types because ESTree nodes are plain objects with a `type` string. Real tools add enter/exit callbacks per node type (`oxc-parser`'s `Visitor`, Babel's `traverse`, ESLint rules), but the shape is the same: handle the node types you care about and pass through everything else.

</TypeDeepDive>

### Why `enforce: 'pre'`

Vite runs plugins in a fixed order: aliases, then user plugins with `enforce: 'pre'`, then Vite's core plugins, then user plugins without `enforce`, then Vite's build plugins, then `enforce: 'post'` plugins, then Vite's post-build plugins (minify, manifest, reporting). One of the core plugins is Vite's built-in Oxc transform, which strips TypeScript and compiles JSX. Without `enforce: 'pre'`, our plugin would receive JavaScript that has already been through it, no matter where we put it in the `plugins` array. That's workable (the AST would just look different), but `pre` gives us two guarantees. First, we see the source the developer wrote, which is what the error messages and tests are written against. Second, anything that runs after us, including the Oxc transform, React Fast Refresh, and Rolldown's tree-shaking, never sees the loader or its imports at all.

### `applyToEnvironment` — environment-scoped plugins

The [`applyToEnvironment`](https://vite.dev/guide/api-environment-plugins#per-environment-plugins-using-the-applytoenvironment-hook) hook (added with the [Environment API](https://vite.dev/guide/api-environment) in [Vite 6](https://vite.dev/blog/announcing-vite6); the API is still marked "release candidate" in Vite 8's docs) is how a plugin declares which environments it should be active in. By returning `environment.name === 'client'`, we ensure this transform _only_ runs when building or serving client-side code. The SSR environment keeps the loaders intact — it needs them to call from `render` and `loadData` ([Part 6](/06-production-builds#exposing-the-loader-for-production)).

Before the Environment API, you'd check the `ssr` flag that some hooks received (`transform(code, id, { ssr })`) _inside_ the hook and bail early. The `applyToEnvironment` approach is cleaner: the plugin is simply not present in the SSR pipeline, so there's no conditional logic in `transform` and no chance of accidentally applying the strip to a server build. It also filters the _whole plugin_, not individual hooks. `transform` is the only hook this plugin defines, but if we later add `resolveId` or `load`, they'd also be skipped on the server side.

### Hook filters

The `transform: { filter, handler }` object form is a [hook filter](https://vite.dev/guide/api-plugin#hook-filters) (Vite 6.3+, native in Rolldown). Instead of calling our handler for every module and letting it return early, Vite checks the filter first: the module id must match `/src/pages/….tsx`, and the code must mention one of the four export names. In Vite 8 the filter check runs inside Rolldown in Rust. A file that fails it is never handed to JavaScript, which saves a JS round trip per module across a large app. Hook filters filter by module (`id`, `code`, `moduleType`), not by environment; `applyToEnvironment` covers that.

The filter is a cheap pre-check, not the decision. A page that mentions the word "loader" in a comment passes the filter, gets parsed, and `stripServerExports` returns `null` because nothing is exported under that name. The handler then returns `undefined`, which tells Vite "no change". Only the parser decides what gets stripped.

<Callout type="info" title="Performance">
Parsing a page with Oxc takes a fraction of a millisecond, and the hook filter means non-page modules never reach the parser at all. The cost is small enough to run on every dev request for a page module, not just in production builds.

Real frameworks do the same job with a range of parsers. Next.js uses [SWC](https://swc.rs) (Rust); React Router's and TanStack Router's Vite plugins use Babel. In a Vite 8 plugin, Oxc is the natural choice because `parseAst` ships with Vite itself, with no extra dependency or second parser to keep in sync with the syntax Vite accepts.

</Callout>

## Wiring the plugin

Add the strip plugin to `vite.config.ts`:

```typescript title="vite.config.ts"
import { resolve } from "node:path";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import inspect from "vite-plugin-inspect";
import eigenRoutes from "./plugins/eigen-routes";
import eigenStripLoaders from "./plugins/eigen-strip-loaders"; // [!code ++]

export default defineConfig({
  plugins: [react(), eigenRoutes(), eigenStripLoaders(), inspect()], // [!code ++]
  plugins: [react(), eigenRoutes(), inspect()], // [!code --]
  resolve: {/* ...aliases from previous parts */},
  build: {/* ...manifest and onwarn from Part 6 */},
});
```

Position in the array doesn't matter much here. `enforce: 'pre'` already moves the plugin ahead of Vite's core transforms and every un-enforced plugin, including `react()`'s Fast Refresh transform. And `eigenRoutes` handles a different set of modules (the `\0eigen/routes` virtual module) than `eigenStripLoaders` (files under `src/pages/`). [`vite-plugin-inspect`](https://github.com/antfu-collective/vite-plugin-inspect) shows the resulting order per module, which is the easiest way to confirm it.

## What code stripping teaches about boundaries

The `transform` hook is where frameworks enforce the server/client boundary at the code level. There are several boundary models in use:

**Export stripping** (our approach; also Next.js's Pages Router and [Remix](https://remix.run)/React Router route modules) — The framework strips specific named exports (`loader`) from the client bundle, then removes the imports that only those exports used. The boundary is at the export level: everything in the file is universal except the server exports. It's convenient, but it depends on the analysis being right. An import that the component _also_ touches (even just for a type guard or a constant) stays in the client bundle, along with everything it imports.

**File-level splitting** ([Remix](https://remix.run)/React Router's `.server.{ts,tsx}` modules; Next.js's `server-only` package plays a similar role) — Server-only code goes in files whose name ends with `.server.ts`. The build refuses to include these modules in the client graph, and errors if client code imports one. The boundary lives in the filesystem, which is easy to grep for and easy for the build tool to detect.

**Directive-based** ([React Server Components](https://react.dev/reference/rsc/server-components)' [`"use server"`](https://react.dev/reference/rsc/use-server) / [`"use client"`](https://react.dev/reference/rsc/use-client)) — The boundary is declared with a string directive at the top of the file. The compiler splits the module graph at these boundaries, generating RPC client stubs for server functions and component reference markers for client components. This is what we'll build in [Part 15 (server functions)](/15-server-functions) and [Part 21 (RSC)](/21-react-server-components).

All three approaches use the `transform` hook (or its build-time equivalent) under the hood. The difference is in _what they detect_ (export names, file extensions, directives) and _what they produce_ (stripped exports, build errors or empty modules, RPC stubs or reference markers).

<TypeDeepDive title="Concept: Why directives instead of file extensions?">

`"use client"` and `"use server"` look like a regression from `.server.ts` filenames — strings inside files are easier to overlook than file extensions. But they mark something different. A `.server.ts` file marks a whole module as server-only. A directive marks an _entry point_ across the boundary: `"use client"` says "the server graph stops here and references this module instead", and `"use server"` says "these functions can be called from the client". Modules without a directive belong to neither side, so a shared component or utility can be pulled into either graph depending on who imports it. And an inline `"use server"` inside a function body lets a single function cross the boundary without moving its file. A file-level `"use server"` has the same cost as a `.server.ts` file (every export becomes a server function), so the gain is in what you _don't_ have to mark. The cost is tooling: a string in a file is easy to miss, so the compiler and lint rules have to enforce what the eye might not.

</TypeDeepDive>

Put the plugin back and the warning disappears. The import was pruned because only the loader used it, and you didn't have to annotate anything.

The hook filter's `code` check matches (the word `loader` is in the string), so the handler runs. But the parser sees a `message` export whose value is a string, so `stripServerExports` returns `null` and the file passes through untouched. A regex-only implementation would have mangled it.

## Key insight

The `transform` hook is essentially a compiler pass — you receive source code and return modified source code. For framework development, it's the mechanism that enforces _what code runs where_. Tree-shaking can only drop exports that no code path could reach. A dynamically imported module's exports all _could_ be reached, so it keeps them. The `transform` hook can apply knowledge the bundler doesn't have: "on the client, nobody will ever read `loader`".

The choice between regex and AST is the same trade-off compiler authors have made for decades: text patterns are quick to write and break on the first input you didn't anticipate; a parser costs a dependency and understands the whole grammar. With Vite 8 exporting an Oxc-backed `parseAst`, the parser is already installed and fast enough for the dev server, so there's little left to argue for the regex. Pair the parser with `magic-string` for position-based edits and you keep formatting, comments and source maps intact.

This part finishes the server/client boundary story for the _loader pattern_. Later parts lean on the same plugin: [Part 14](/14-framework-middleware)'s `middleware`, [Part 16](/16-static-site-generation)'s `generateStaticParams` and [Part 30](/30-route-metadata-seo)'s `generateMetadata` are all stripped by the export list above. The same hook, with different detection logic, will reappear in [Part 15](/15-server-functions) (turning `"use server"` exports into RPC stubs) and [Part 21](/21-react-server-components) (turning `"use client"` exports into reference markers that the RSC environment can serialize). The pattern doesn't change; the input and output do.

<TestSection title="Testing: transform output">

Transform hooks are code-in, code-out — making them straightforward to test. `stripLoaderForClient` is the string-in, string-out wrapper around `stripServerExports`, so tests call it directly with realistic page source. That includes a loader with semicolons, template literals and a `satisfies` clause, exactly the inputs that broke the regex.

```typescript title="plugins/__tests__/eigen-strip-loaders.test.ts"
import { describe, expect, it } from "vitest";
import { stripLoaderForClient } from "../eigen-strip-loaders";

describe("stripLoaderForClient", () => {
  it("strips a realistic loader and the imports only it used", () => {
    const input = `import { db } from "../../lib/database";
import { defineLoader } from "eigen/helpers";
import type { PageProps } from "eigen/types";
import { formatDate } from "../../lib/format";
import "./post.css";

export const loader = defineLoader("/posts/:id", async ({ params }) => {
	const res = await db.query("SELECT * FROM posts WHERE id = $1", [params.id]);
	const post = res.rows[0];
	if (!post) throw new Error(\`Post \${params.id} not found\`);
	return { title: post.title as string, createdAt: post.created_at as string };
});

type LoaderData = Awaited<ReturnType<typeof loader>>;

export default function PostPage({ data }: PageProps<"/posts/:id", LoaderData>) {
	return (
		<article>
			<h1>{data.title}</h1>
			<time>{formatDate(data.createdAt)}</time>
		</article>
	);
}
`;
    const output = stripLoaderForClient(input, "/app/src/pages/posts/[id].tsx");

    // The whole loader is gone — not cut off at its first semicolon
    expect(output).not.toContain("db.query");
    expect(output).not.toContain("not found");
    expect(output).toContain("[eigen] loader stripped for client bundle");

    // Imports only the loader used are pruned...
    expect(output).not.toContain("../../lib/database");
    expect(output).not.toContain("eigen/helpers");

    // ...while the component's imports and side-effect imports survive
    expect(output).toContain('import { formatDate } from "../../lib/format";');
    expect(output).toContain('import type { PageProps } from "eigen/types";');
    expect(output).toContain('import "./post.css";');
    expect(output).toContain("export default function PostPage");
  });

  it("handles satisfies, function declarations, and export lists", () => {
    const input = `import { readFileSync } from "node:fs";
import type { LoaderFn } from "eigen/types";
import { z } from "zod";

async function load() {
	return { text: readFileSync("x.txt", "utf8") };
}
export const middleware = (async () => ({ ok: true })) satisfies (() => unknown);
export async function generateStaticParams() { return [{ id: "1" }]; }
export const parse = (input: unknown) => z.object({ id: z.string() }).parse(input);
export { load as loader, parse as parseParams };
export default function Page() { return null; }
`;
    const output = stripLoaderForClient(input);

    expect(output).not.toContain("readFileSync");
    expect(output).not.toContain("node:fs");
    expect(output).not.toContain("export const middleware");
    expect(output).not.toContain("generateStaticParams()");

    // `parse` is not server-only — it runs in the browser (Part 18)
    expect(output).toContain("export const parse");
    expect(output).toContain('import { z } from "zod";');
    expect(output).toContain("export { parse as parseParams };");
  });

  it("keeps imports that a surviving export specifier re-exports", () => {
    const input = `import { helper } from "./h";
import { load } from "./l";
export { helper, load as loader };
`;
    const output = stripLoaderForClient(input);

    expect(output).toContain('import { helper } from "./h";');
    expect(output).toContain("export { helper };");
    expect(output).not.toContain("./l");
  });

  it("leaves files without server exports untouched", () => {
    const input = `export const message = "export const loader = 'oops'";
export default function About() { return <h1>{message}</h1>; }
`;
    expect(stripLoaderForClient(input)).toBe(input);
  });

  it("matches the snapshot for the canonical page", () => {
    const input = `import { defineLoader } from "eigen/helpers";

export const loader = defineLoader("/posts/:id", async ({ params }) => {
	const res = await fetch(\`https://jsonplaceholder.typicode.com/posts/\${params.id}\`);
	return (await res.json()) as { title: string };
});

export default function PostPage() { return null; }
`;
    expect(stripLoaderForClient(input)).toMatchSnapshot();
  });
});
```

The last test is a **snapshot test**: the first run writes the output to `__snapshots__/eigen-strip-loaders.test.ts.snap`, and later runs fail if it changes. Snapshot tests suit transforms well. A change to the stripping logic that alters output shows up as a readable diff of exactly what moved. Run `npx vitest run --update` to accept intentional changes.
