_This module builds the data fetching strategy layer — the framework infrastructure that sits between "a loader calls fetch" and "the user sees data." It covers request-scoped deduplication, safe credential forwarding, client-side cache management, and TanStack Query integration for seamless SSR-to-client handoff._

## The problems with naive data fetching

Our loaders from Part 5 call `fetch` or query a database directly. This works, but it has several issues at scale:

**Problem 1: Duplicate requests.** A layout loader and a page loader might both need the current user. Without deduplication, the API gets hit twice for the same data in the same request.

**Not a problem any more: waterfall loading.** [Part 13](/13-nested-layouts#parallel-vs-sequential-loader-execution)'s `loadRouteData` already starts every loader in the layout stack at once and awaits them with `Promise.all`, and [Part 14](/14-framework-middleware) hands each of them the same `ctx`. What's missing is that those parallel loaders don't share anything else: two of them asking for the same URL still cost two requests, which is Problem 1.

**Problem 3: No client-side cache.** After hydration, every client-side navigation fetches fresh data from the server. There's no caching, no stale-while-revalidate, no optimistic updates.

**Problem 4: No cache-aware prefetching.** [Part 23](/23-advanced-router) preloads a route's loader data on hover, but that preload lives in its own short-lived map; nothing else on the page can share or invalidate it.

## A request-scoped fetch

Two jobs belong to the server-side `fetch` that loaders use: deduplicating identical GETs within one request, and forwarding the user's credentials to _our own_ APIs. Both depend on the incoming request, so the framework creates a fresh fetch per request rather than keeping a module-level cache (a module-level `Map` would be shared by every concurrent request in the process — one user's response could be served to another):

<FetchDedupeDiagram />

```typescript title="packages/eigen/fetch.ts"
export type Fetch = (input: RequestInfo | URL, init?: RequestInit) => Promise<Response>;

export interface ServerFetchOptions {
  /**
   * Origins (besides the app's own) allowed to receive the user's cookie and
   * Authorization header. Everything else gets the request without them.
   */
  forwardCredentialsTo?: string[];
}

/**
 * A fetch bound to one incoming request:
 *  - identical GETs made while handling this request share one network call
 *  - cookies/authorization are forwarded only to trusted origins
 */
export function createServerFetch(request: Request, options: ServerFetchOptions = {}): Fetch {
  // Lives exactly as long as this request — nothing leaks between users
  const cache = new Map<string, Promise<Response>>();
  const trusted = new Set([new URL(request.url).origin, ...(options.forwardCredentialsTo ?? [])]);

  return async (input, init) => {
    const source = input instanceof Request ? input : undefined;
    // Relative URLs resolve against the incoming request, like in a browser
    const url = new URL(source ? source.url : String(input), request.url);
    const method = (init?.method ?? source?.method ?? "GET").toUpperCase();
    const headers = new Headers(init?.headers ?? source?.headers);

    // Forwarding the session cookie to a third-party API would hand that
    // API the user's credentials — only trusted origins get them
    if (trusted.has(url.origin)) {
      const cookie = request.headers.get("cookie");
      if (cookie && !headers.has("cookie")) headers.set("cookie", cookie);
      const auth = request.headers.get("authorization");
      if (auth && !headers.has("authorization")) headers.set("authorization", auth);
    }

    // Rebuilding from `source` keeps a Request's body, signal, redirect mode, ...
    const doFetch = () => fetch(new Request(source ?? url, { ...init, method, headers }));

    // Only GETs are deduplicated; 'no-store' opts out
    if (method !== "GET" || init?.cache === "no-store") return doFetch();

    // Same URL with a different Accept or explicit Authorization header is a
    // different request, so those headers are part of the key
    const key = [url.href, headers.get("accept"), headers.get("authorization")].join("\n");
    let pending = cache.get(key);
    if (!pending) {
      pending = doFetch();
      cache.set(key, pending);
      // A failed request must not be cached for the rest of the request
      pending.catch(() => cache.delete(key));
    }

    // The cached Response is never handed out or read — every caller gets
    // its own clone, so one consumer reading the body can't break another
    return (await pending).clone();
  };
}
```

The fetch reaches loaders through the middleware context. A global middleware ([Part 14](/14-framework-middleware)) creates it — along with the per-request `QueryClient` used later in this module:

```typescript title="src/middleware/data.ts"
import { defineMiddleware } from "eigen/middleware";
import { createServerFetch } from "eigen/fetch";
import { createQueryClient } from "eigen/query";

export const dataMiddleware = defineMiddleware((ctx) => ({
  fetch: createServerFetch(ctx.request, {
    forwardCredentialsTo: ["https://api.example.com"],
  }),
  // One QueryClient per request — a shared one would leak cached data between users
  queryClient: createQueryClient(),
}));
```

```typescript title="src/eigen-context.d.ts"
import type { QueryClient } from "@tanstack/react-query";
import type { Fetch } from "eigen/fetch";

declare module "eigen/types" {
  interface EigenContext {
    fetch: Fetch;
    queryClient: QueryClient;
  }
}
```

Add `dataMiddleware` to the global list in `src/middleware.ts`. Now two loaders that both call `ctx.fetch('https://api.example.com/user')` produce one network request. This is the same idea as Next.js's request memoization of `fetch` — but explicit, rather than patching the global `fetch`.

## Parallel loaders, one shared fetch

<LoaderWaterfallDiagram />

Nested layouts create a loader hierarchy. Running the loaders one after another mirrors the component nesting, but layout loaders are usually independent — the root layout's user data doesn't depend on the dashboard layout's metrics data. That's why the loader step inside `runRoute` has run them all at once since Part 13. For reference, here is the function `runRoute` calls, unchanged from [Part 14](/14-framework-middleware#the-middleware-execution-engine):

```typescript title="packages/eigen/route-data.ts"
export async function loadRouteData({ route, params }: RouteMatch, ctx: EigenContext): Promise<RouteData> {
  // Every loader in the stack runs concurrently
  const [layoutEntries, page] = await Promise.all([
    Promise.all(
      route.layouts.map(
        async (layout) => [layout.path, layout.loader ? await layout.loader({ params, ctx }) : null] as const,
      ),
    ),
    route.loader ? route.loader({ params, ctx }) : null,
  ]);
  return { layouts: Object.fromEntries(layoutEntries), page };
}
```

A three-level layout stack with 200ms loaders takes ~200ms total instead of ~600ms. This is the Remix approach — all loaders for matched routes run concurrently. The `ctx` every loader receives is the one middleware built, so after this module they all hold the same `ctx.fetch`: when two loaders that start together ask for the same URL, the second finds the first one's pending request in the cache, and the stack still costs one request.

## Client-side data management with TanStack Query

[TanStack Query](https://tanstack.com/query) (formerly React Query) is a data fetching and caching library for React. It manages server state on the client — caching responses, background refetching when data becomes stale, retry logic, and cache invalidation on mutations. Its `dehydrate` function serializes a server-side cache, and its `HydrationBoundary` component restores it on the client.

After hydration, the client needs its own data management strategy. Raw `fetch` calls on every navigation waste bandwidth and show loading states unnecessarily. TanStack Query provides the client-side cache layer:

```typescript title="packages/eigen/query.ts"
import { QueryClient } from "@tanstack/react-query";

/**
 * Create a QueryClient configured for SSR.
 * On the server: one per request (created by dataMiddleware).
 * On the client: one for the lifetime of the page.
 */
export function createQueryClient(): QueryClient {
  return new QueryClient({
    defaultOptions: {
      queries: {
        // On the server: don't retry (fail fast)
        retry: typeof window === "undefined" ? false : 3,
        // Data fetched during SSR is fresh for 60 seconds, so the client
        // doesn't immediately refetch what the server just loaded
        staleTime: 60 * 1000,
      },
    },
  });
}
```

### Seeding the query cache in loaders

A query is described once with TanStack's `queryOptions` helper and used in three places: the loader (server), the component (client), and hover prefetching. The `fetch` is a parameter, so the server can pass the request-scoped `ctx.fetch` while the browser uses its own.

The same `queryFn` runs in both places, so the URL it fetches has to work in both. This example assumes the app's backend serves `/api/posts/:id` on the app's own origin (behind the same reverse proxy, say). On the server, `ctx.fetch` resolves the relative URL against the incoming request and forwards the user's cookie, because the app's origin is always trusted. In the browser, a same-origin `fetch` sends the cookie by itself and needs no CORS. Calling a cross-origin API directly from the browser would do neither: the default `credentials: 'same-origin'` leaves the cookie out, and the API would have to allow the app's origin with CORS. For an authenticated third-party API, keep the browser-side `queryFn` on a same-origin endpoint (a proxy route or a [Part 15](/15-server-functions) server function) so the credentials stay first-party.

```tsx title="src/pages/posts/[id].tsx"
import { queryOptions, useQuery, type QueryClient } from "@tanstack/react-query";
import { defineLoader } from "eigen/helpers";
import type { Fetch } from "eigen/fetch";
import type { PageProps } from "eigen/types";

interface Post {
  title: string;
  body: string;
}

const postQuery = (id: string, fetcher: Fetch = fetch) =>
  queryOptions({
    queryKey: ["posts", id],
    queryFn: async (): Promise<Post> => {
      // Same-origin: relative on both sides (see above)
      const res = await fetcher(`/api/posts/${encodeURIComponent(id)}`);
      if (!res.ok) throw new Error(`Failed to load post ${id}: ${res.status}`);
      return res.json();
    },
    staleTime: 5 * 60 * 1000, // 5 minutes
  });

export const loader = defineLoader("/posts/:id", ({ params, ctx }) =>
  // query() resolves with the data and REJECTS if the query fails, so a
  // failing fetch reaches the route's error boundary (Part 35) instead of
  // rendering the page with `undefined` data.
  ctx.queryClient.query(postQuery(params.id, ctx.fetch)),
);

// Used by the router to warm the cache on hover (see below).
// The caller swallows errors: a failed prefetch just means the click fetches.
export function prefetch(params: { id: string }, queryClient: QueryClient) {
  return queryClient.query(postQuery(params.id));
}

export default function PostPage({ params, data: initialPost }: PageProps<"/posts/:id", Post>) {
  // On initial SSR and hydration: the cache already holds the post.
  // initialData covers client navigations, where the loader's result arrives
  // via /_eigen/data; it's ignored whenever the cache already has the query.
  // Because initialData is always defined, `data` is typed Post (never undefined).
  const { data } = useQuery({ ...postQuery(params.id), initialData: initialPost });

  return (
    <article>
      <h1>{data.title}</h1>
      <p>{data.body}</p>
    </article>
  );
}
```

Part 7's transform strips `loader` from the client bundle; `postQuery`, `prefetch` and the component remain.

`queryClient.query()` is the current TanStack Query v5 method for "give me this query's data": it returns cached data while it's fresh, fetches otherwise, and rejects on failure. The older `ensureQueryData`, `fetchQuery` and `prefetchQuery` still work but are deprecated in its favor, and their notices say they will be removed in the next major version: `fetchQuery` becomes `query(options)`, `prefetchQuery` becomes `query(options).catch(noop)`, and `ensureQueryData` becomes `query({ ...options, staleTime: 'static' })`.

Two trade-offs in this pattern are worth knowing. The post is serialized twice into the first page: once as page data in `window.__EIGEN_DATA__`, once in the dehydrated query cache below. And `initialData` only applies when the cache has no entry for the key: after a client navigation to a post that is cached but stale, the component shows the cached copy while a background refetch runs, even though fresh loader data just arrived from `/_eigen/data`. If that matters, write the navigation's loader data into the cache with `queryClient.setQueryData(postQuery(id).queryKey, data)` before rendering the page.

### The SSR → client handoff

On the server, the app renders inside a `QueryClientProvider` for the request's client — `useQuery` needs one, even when the data is already cached. The cache is then dehydrated and embedded next to the session from Part 33:

<QueryHandoffDiagram />

```tsx title="entry-server.tsx"
import { QueryClientProvider, dehydrate } from "@tanstack/react-query";
import { serializeForScript } from "eigen/serialize";

// Inside render(), after runRoute(), resolveRouteData() and the Part 30/33 steps
// (`data` is the resolved RouteData, `clientSession` comes from Part 33):
const { queryClient } = result.context;

const html = renderToString(
  <SessionProvider initialSession={clientSession}>
    <QueryClientProvider client={queryClient}>
      <App pathname={pathname} data={data} />
    </QueryClientProvider>
  </SessionProvider>,
);

// Only successful queries are dehydrated by default
const queryState = dehydrate(queryClient);
const head =
  renderMetadataToHTML(meta) +
  `\n    <script>window.__EIGEN_SESSION__=${serializeForScript(clientSession)}</script>` +
  `\n    <script>window.__EIGEN_QUERY_STATE__=${serializeForScript(queryState)}</script>`;

return { html, status: 200, data, head };
```

```tsx title="entry-client.tsx"
import { hydrateRoot } from "react-dom/client";
import { HydrationBoundary, QueryClientProvider, type DehydratedState } from "@tanstack/react-query";
import { createQueryClient } from "eigen/query";
import { SessionProvider } from "eigen/auth/session";
import { App } from "./app";

declare global {
  interface Window {
    __EIGEN_QUERY_STATE__?: DehydratedState;
  }
}

// One client for the lifetime of the page. `initialSession` is built from
// window.__EIGEN_SESSION__ exactly as in Part 33.
const queryClient = createQueryClient();

hydrateRoot(
  document.getElementById("root")!,
  <SessionProvider initialSession={initialSession}>
    <QueryClientProvider client={queryClient}>
      <HydrationBoundary state={window.__EIGEN_QUERY_STATE__}>
        <App pathname={window.location.pathname} data={window.__EIGEN_DATA__} />
      </HydrationBoundary>
    </QueryClientProvider>
  </SessionProvider>,
);
```

After hydration, TanStack Query manages all subsequent data fetching: background refetching when data becomes stale, cache invalidation on mutations, optimistic updates, and retry logic. The framework's loader seeds the cache; TanStack Query manages it from there.

## Prefetching on navigation intent

The advanced router ([Part 23](/23-advanced-router)) preloads loader data on hover. Pages that export `prefetch` can also put their data into the shared query cache at the same moment.

The router can't read `prefetch` from the page module directly: on the client, `eigen/routes` only holds a `React.lazy` wrapper per page ([Part 13](/13-nested-layouts#generating-the-nested-virtual-module)), and the page module isn't loaded until it renders. Importing every page eagerly to find its `prefetch` export would undo code splitting. Instead, the client branch of `generateRouteCode` gives every route a lazy `prefetch` that loads the page chunk first:

```typescript title="packages/eigen/plugins/route-tree.ts"
      } else {
        routes.push(
          `  { path: '${page.path}', component: React.lazy(() => import('${page.url}')), layouts: ${layouts} }`, // [!code --]
          `  { path: '${page.path}', component: React.lazy(() => import('${page.url}')), layouts: ${layouts}, ` + // [!code ++]
            `prefetch: (params, qc) => import('${page.url}').then((m) => m.prefetch?.(params, qc)) }`, // [!code ++]
        );
      }
```

Add the matching optional field to `RouteDefinition`: `prefetch?: (params: Record<string, string>, queryClient: QueryClient) => Promise<unknown>`. The `import()` is the same one `React.lazy` makes, so hovering also warms the page's chunk, and the click doesn't wait for it. A page without a `prefetch` export just resolves to `undefined`.

The `Link` component from Part 23 calls it next to the existing `preloadRoute(href)`, which warms `/_eigen/data`:

```tsx title="packages/eigen/router.tsx"
import { useQueryClient } from "@tanstack/react-query"; // [!code ++]
import { matchRoute } from "eigen/match-route"; // [!code ++]
import { routes } from "eigen/routes"; // [!code ++]

export function Link<T extends RoutePaths>(props: LinkProps<T>) {
  // ...href and the preload effect, unchanged from Part 23
  const queryClient = useQueryClient(); // [!code ++]

  const onIntent = preload === "intent" ? () => preloadRoute(href) : undefined; // [!code --]
  const onIntent = // [!code ++]
    preload === "intent" // [!code ++]
      ? () => { // [!code ++]
          preloadRoute(href); // [!code ++]
          const match = matchRoute(new URL(href, location.href).pathname, routes); // [!code ++]
          // A failed prefetch only means the click fetches the data itself // [!code ++]
          match?.route.prefetch?.(match.params, queryClient).catch(() => {}); // [!code ++]
        } // [!code ++]
      : undefined; // [!code ++]
```

`useQueryClient()` needs the `QueryClientProvider` that both entries render around `<App>`, so `Link` only works inside it.

If the data is already cached and fresh, `query()` returns it without a request. If it's stale or missing, TanStack Query fetches it. Unlike Part 23's private preload map, the result lives in the same cache every component reads, so it can be invalidated by mutations and refetched on focus.

The cost is a second request on hover: `preloadRoute` asks `/_eigen/data` for every loader in the route (the page loader included, on the server), and `prefetch` asks the API for the post directly. Both are cheap and run in parallel, but if a route's data is only the post, you can skip one of them for routes that export `prefetch`.

## Isomorphic fetch normalization

`fetch` behaves differently across environments:

| Environment    | `fetch` source                 | Differences                                              |
| -------------- | ------------------------------ | -------------------------------------------------------- |
| Browser        | Native `window.fetch`          | Sends cookies automatically (same-origin), respects CORS |
| Node SSR       | `undici` (built into Node 18+) | No cookie jar, no CORS, relative URLs throw              |
| Edge (Workers) | Web standard `fetch`           | Similar to browser but no cookie jar                     |

`createServerFetch` normalizes the server side: relative URLs resolve against the incoming request, and the user's cookie and `Authorization` header are forwarded — but only to the app's own origin and the origins listed in `forwardCredentialsTo`. Forwarding them to every URL would leak the user's session to any third-party API a loader happens to call.

## What to observe

1. **Make two loaders fetch the same URL through `ctx.fetch`.** Check your API server's logs — only one request arrives per page load, and a second page load makes its own request (the cache is per request).

2. **Add `console.log` with a timestamp to each layout loader.** With parallel execution, all logs appear at nearly the same time instead of 200ms apart.

3. **Point a loader at a third-party URL not in `forwardCredentialsTo`.** Inspect the outgoing request: no `cookie` header. Add the origin to the list and it appears.

4. **Leave a post page open past its `staleTime`, then refocus the window.** TanStack Query refetches in the background (`refetchOnWindowFocus`) and the page updates without a navigation.

5. **Hover over a post link.** The Network tab shows the page's chunk and the `/api/posts/…` request fired on hover, next to Part 23's `/_eigen/data` preload — the query is in the cache before you click.

6. **Make the post API return 500.** The loader throws (`queryClient.query()` rejects on failure), and the route's error boundary renders instead of a page with `undefined` data.

## Key insight

Data fetching strategy is the layer between "the loader returns data" and "the user sees content." Without it, every navigation is a cold fetch, every request might duplicate API calls, and there's no continuity between server-rendered data and client-side interactions.

The framework provides three things: a request-scoped fetch (deduplication plus safe credential forwarding) shared by loaders that already run in parallel since Part 13, a query function that works unchanged on both sides because it only talks to the app's own origin, and a query cache handoff pattern (server seeds it, client manages it). TanStack Query is the natural client-side cache manager because it's designed for exactly this SSR → client transition — `dehydrate` on the server, `HydrationBoundary` on the client, and automatic cache management from there.

TanStack Start's TanStack Query integration follows the same architecture natively: route loaders fill the query cache from shared query options, and components read it with `useSuspenseQuery`, which also gives it streaming support. We're implementing the same idea explicitly.
