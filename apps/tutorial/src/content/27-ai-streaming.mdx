Now we'll extend server functions to support streaming AI model responses — text, structured data, and tool calls flowing progressively from the server to the client._

---

## Why AI streaming is a framework concern

When an application calls an LLM, the response arrives as a stream of tokens over seconds. If the server function from [Part 15](/15-server-functions) waits for the full response before returning, the user stares at a loading spinner for 3-10 seconds. Streaming the response token-by-token — showing text as it generates — transforms the UX from "waiting" to "watching it think."

This isn't just a `fetch` with `ReadableStream`. AI responses are _structured_: they contain text chunks, tool call invocations (the model wants to run a function), tool results, and errors. The framework needs to serialize this structure across the server/client boundary and provide typed React hooks to consume it.

Two libraries cover this ground today. The [AI SDK](https://ai-sdk.dev) (the `ai` package, from Vercel) provides the primitives for calling models — `streamText`, tools, structured output — plus UI hooks and its own streaming protocol. [TanStack AI](https://tanstack.com/ai), released in alpha in late 2025 and [in release candidate](https://tanstack.com/blog/tanstack-ai-rc) since August 2026, is an independent, framework-agnostic alternative with its own provider adapters (OpenAI, Anthropic, Gemini, Ollama, …), per-model type inference, and streaming-first React and Solid bindings. It isn't built on the AI SDK; it competes with it. We'll use the AI SDK's model-calling primitives on the server and build the transport and hooks ourselves, because the transport is the framework's job.

## Extending server functions for streaming

In Part 15, a server function's handler returns a single JSON value, and the client stub returns `Promise<T>`. For AI, the handler is an **async generator** that yields chunks, and the client gets a `ReadableStream` of those chunks. We add one method to Part 15's builder, `streamHandler`, next to `handler`:

```typescript title="packages/eigen/server.ts (addition)"
/** What .streamHandler() produces: resolves to a stream of the yielded chunks */
export interface StreamingServerFn<TInput, TChunk> {
  (input: TInput): Promise<ReadableStream<TChunk>>
  url: string
}

export interface ServerFnBuilder<TContext extends EigenContext, TInput> {
  // ...middleware, validator, handler as in Part 15...

  /** Chunks must be JSON-serializable: each one becomes one SSE event */
  streamHandler<TChunk>(
    fn: (opts: { data: TInput; context: TContext }) => AsyncIterable<TChunk>,
  ): StreamingServerFn<TInput, TChunk>
}

// In createServerFn's builder object — the server side is identical to
// handler(): middleware, then validation, then the function. It just
// returns the async iterator instead of a value.
streamHandler(fn) {
  return builder.handler(fn as any) as any
},
```

On the server, nothing else changes: the same middleware and validator run first, so a streaming endpoint gets the same protection as any other server function.

### The streaming server function convention

```typescript title="src/server/chat.ts"
import { createServerFn } from "eigen/server";
import { streamText, tool, isStepCount, type StaticToolCall } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const tools = {
  getWeather: tool({
    description: "Get weather for a location",
    inputSchema: z.object({ location: z.string() }),
    execute: async ({ location }) => fetchWeather(location),
  }),
  searchProducts: tool({
    description: "Search the product catalog",
    inputSchema: z.object({ query: z.string(), maxResults: z.number().int().max(20) }),
    execute: async ({ query, maxResults }) => searchDB(query, maxResults),
  }),
};

// The wire protocol: a small, JSON-safe subset of the AI SDK's stream parts
export type ChatChunk =
  | { type: "text-delta"; text: string }
  | ToolCallChunk
  // failed: the tool threw. The model sees the error and can still answer.
  | { type: "tool-result"; toolCallId: string; toolName: keyof typeof tools; failed?: true };

const chatInput = z.object({
  messages: z.array(
    z.object({
      role: z.enum(["user", "assistant"]),
      content: z.string(),
    }),
  ),
});

export const chat = createServerFn()
  .validator(chatInput)
  .streamHandler(async function* ({ data, context }): AsyncGenerator<ChatChunk> {
    const result = streamText({
      model: openai("gpt-5-mini"),
      messages: data.messages,
      tools,
      // Let the model answer after a tool result, up to 5 steps
      // (`stepCountIs` in AI SDK 5 and 6, still exported as an alias)
      stopWhen: isStepCount(5),
      abortSignal: context.request.signal,
    });

    // Yield structured chunks as they arrive. We map instead of forwarding
    // the raw parts: they carry provider metadata and Error objects that
    // don't belong on the wire. (`stream` was `fullStream` before AI SDK 7,
    // which keeps the old name as a deprecated alias.)
    for await (const part of result.stream) {
      switch (part.type) {
        case "text-delta":
          yield { type: "text-delta", text: part.text };
          break;
        case "tool-call":
          // Dynamic calls (unknown or unparsable tool names) aren't in our
          // tool set and have untyped input; we don't forward them
          if (part.dynamic) break;
          // toolName and input come from the same part, so this pairing is
          // safe; TypeScript just can't correlate them through a destructure
          yield {
            type: "tool-call",
            toolCallId: part.toolCallId,
            toolName: part.toolName,
            input: part.input,
          } as ToolCallChunk;
          break;
        case "tool-result":
          if (part.dynamic) break;
          yield { type: "tool-result", toolCallId: part.toolCallId, toolName: part.toolName };
          break;
        case "tool-error":
          // A throwing execute() emits tool-error, not tool-result. Forward it
          // so the client clears its "Calling getWeather…" indicator.
          if (part.dynamic) break;
          yield { type: "tool-result", toolCallId: part.toolCallId, toolName: part.toolName, failed: true };
          break;
        case "error":
          // Errors arrive *inside* the stream; rethrow so the endpoint emits an error event
          throw part.error;
      }
    }
  });
```

`ToolCallChunk` is defined below, in [Typed tool calls](#typed-tool-calls). The model ID is just an example — any AI SDK provider works.

### The transform: streaming RPC

The `transform` hook from Part 15 already finds `createServerFn()` chains. It needs one more fact per chain: does it end in `.streamHandler(...)`? The outermost call in the chain answers that:

```typescript title="packages/eigen/plugins/eigen-server-fns.ts (change)"
// In findServerFns, alongside name/start/end:
const streaming = decl.init.callee.type === "MemberExpression" && decl.init.callee.property.name === "streamHandler";

// In transformForClient:
const stub = fn.streaming ? "createStreamingServerFnStub" : "createServerFnStub";
s.overwrite(fn.start, fn.end, `${stub}(${JSON.stringify(generateFnId(rel, fn.name))})`);
// ...and import both stubs from 'eigen/server-fn-client'
```

The streaming stub posts to the same `/_eigen/fn/<id>` endpoint with the same JSON body and returns a `ReadableStream` that decodes server-sent events (SSE) into chunks:

```typescript title="packages/eigen/server-fn-client.ts (addition)"
/** Parses an SSE text stream into the JSON payload of each event */
function sseDecoder<T>(): TransformStream<string, T> {
  let buffer = "";
  let finished = false;
  return new TransformStream<string, T>({
    transform(text, controller) {
      buffer += text;
      const events = buffer.split("\n\n");
      buffer = events.pop()!; // the last piece may be an incomplete event

      for (const raw of events) {
        let event = "message";
        let data = "";
        for (const line of raw.split("\n")) {
          if (line.startsWith("event:")) event = line.slice(6).trim();
          else if (line.startsWith("data:")) data += line.slice(5).trimStart();
        }
        if (event === "done") {
          finished = true;
          return controller.terminate();
        }
        if (event === "error") return controller.error(new Error(JSON.parse(data).error));
        controller.enqueue(JSON.parse(data) as T);
      }
    },
    // The body ended. Without a `done` event first, the connection dropped
    // mid-answer: fail the stream instead of passing off a truncated answer
    flush(controller) {
      if (!finished) controller.error(new Error("Stream ended unexpectedly"));
    },
  });
}

export function createStreamingServerFnStub(id: string) {
  const url = `/_eigen/fn/${id}`;

  const call = async (input?: unknown) => {
    const res = await fetch(url, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(input ?? null),
    });
    if (!res.ok || !res.body) {
      const body = await res.json().catch(() => null);
      throw new Error(body?.error ?? `Server function failed (${res.status})`);
    }

    // Return a ReadableStream that decodes SSE events into typed chunks
    return res.body.pipeThrough(new TextDecoderStream()).pipeThrough(sseDecoder());
  };

  return Object.assign(call, { url });
}
```

### The endpoint: async iterators become SSE

The whole path, from the generator on the server to the hook in the browser:

<SseStreamDiagram />

Part 15's `handleServerFnRequest` runs in dev (through the module runner) and in production (mounted on the H3 server). It gets one branch: if the function returned an async iterable, respond with an event stream instead of JSON. Each chunk becomes a `data:` event; the end of the stream is an explicit `done` event, so the client can tell "finished" from "connection dropped":

```typescript title="packages/eigen/server-fn-endpoint.ts (change)"
const encoder = new TextEncoder();
const sse = (event: string | null, data: unknown) =>
  encoder.encode(`${event ? `event: ${event}\n` : ""}data: ${JSON.stringify(data)}\n\n`);

function toEventStream(iterable: AsyncIterable<unknown>): ReadableStream<Uint8Array> {
  const iterator = iterable[Symbol.asyncIterator]();
  return new ReadableStream({
    async pull(controller) {
      try {
        const { done, value } = await iterator.next();
        if (done) {
          controller.enqueue(sse("done", {}));
          controller.close();
        } else {
          controller.enqueue(sse(null, value)); // JSON.stringify keeps it on one line
        }
      } catch (e) {
        console.error(e);
        // Same rule as JSON responses: don't leak internals to the caller
        controller.enqueue(sse("error", { error: "Stream failed" }));
        controller.close();
      }
    },
    async cancel() {
      // The client went away: stop the generator, which stops consuming the model's stream
      await iterator.return?.();
    },
  });
}

// In handleServerFnRequest, replacing `return Response.json(result ?? null)`:
const result = await registration.fn(input, context);
if (result != null && typeof (result as any)[Symbol.asyncIterator] === "function") {
  return new Response(toEventStream(result as AsyncIterable<unknown>), {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache",
    },
  });
}
return Response.json(result ?? null);
```

Nothing changes in dev. Part 14's `sendWebResponse` already streams: it flushes the headers right away (an SSE client shouldn't wait for the first event), copies chunks as they arrive with backpressure, and cancels the body when the browser disconnects, which triggers the `cancel()` above.

## Typed React hooks for AI streams

The framework provides a hook that consumes the typed stream and manages UI state:

```typescript title="packages/eigen/ai-hooks.ts"
import { useCallback, useRef, useState } from "react";

export interface ChatMessage {
  role: "user" | "assistant";
  content: string;
}

type BaseChunk =
  | { type: "text-delta"; text: string }
  | { type: "tool-call"; toolCallId: string }
  | { type: "tool-result"; toolCallId: string };

export function useChat<TChunk extends BaseChunk>(
  serverFn: (input: { messages: ChatMessage[] }) => Promise<ReadableStream<TChunk>>,
) {
  type ToolCall = Extract<TChunk, { type: "tool-call" }>;

  const [messages, setMessages] = useState<ChatMessage[]>([]);
  const [isStreaming, setIsStreaming] = useState(false);
  const [error, setError] = useState<Error | null>(null);
  const [activeToolCalls, setActiveToolCalls] = useState<ToolCall[]>([]);

  // The latest history, without making `send` change on every token
  const messagesRef = useRef(messages);
  messagesRef.current = messages;

  const send = useCallback(
    async (content: string) => {
      const history: ChatMessage[] = [...messagesRef.current, { role: "user", content }];
      setMessages(history);
      setIsStreaming(true);
      setError(null);

      let assistantContent = "";

      try {
        const stream = await serverFn({ messages: history });
        const reader = stream.getReader();

        while (true) {
          const { done, value: chunk } = await reader.read();
          if (done) break;

          switch (chunk.type) {
            case "text-delta":
              assistantContent += (chunk as Extract<BaseChunk, { type: "text-delta" }>).text;
              setMessages([...history, { role: "assistant", content: assistantContent }]);
              break;

            case "tool-call":
              setActiveToolCalls((prev) => [...prev, chunk as ToolCall]);
              break;

            case "tool-result":
              const { toolCallId } = chunk as Extract<BaseChunk, { type: "tool-result" }>;
              setActiveToolCalls((prev) => prev.filter((t) => t.toolCallId !== toolCallId));
              break;
          }
        }
      } catch (e) {
        setError(e as Error);
      } finally {
        setIsStreaming(false);
        setActiveToolCalls([]);
      }
    },
    [serverFn],
  );

  return { messages, isStreaming, error, send, activeToolCalls };
}
```

### Usage in a component

```tsx title="src/pages/chat.tsx"
"use client";

import { useChat } from "eigen/ai-hooks";
import { chat } from "../server/chat";

export default function ChatPage() {
  const { messages, isStreaming, error, send, activeToolCalls } = useChat(chat);

  return (
    <div>
      {messages.map((m, i) => (
        <div key={i} className={m.role}>
          {m.content}
        </div>
      ))}

      {activeToolCalls.map((tc) => (
        <div key={tc.toolCallId} className="tool-call">
          Calling {tc.toolName}({JSON.stringify(tc.input)})...
        </div>
      ))}

      {isStreaming && <div className="typing-indicator">●●●</div>}
      {error && <div role="alert">{error.message}</div>}

      <input
        onKeyDown={(e) => {
          if (e.key === "Enter" && !isStreaming) {
            send(e.currentTarget.value);
            e.currentTarget.value = "";
          }
        }}
        placeholder="Type a message..."
      />
    </div>
  );
}
```

`useChat(chat)` infers `TChunk` as `ChatChunk` from the server function's type, so `tc.toolName` is `'getWeather' | 'searchProducts'` and checking it narrows `tc.input` to that tool's input type.

## Typed tool calls

The most interesting type safety challenge: tool calls are defined on the server (in the streaming function), but the client needs to know about them for rendering. The AI SDK already infers a discriminated union from a tool set. `TypedToolCall<typeof tools>` is the type of the stream's `tool-call` parts, but it also includes `DynamicToolCall` (`toolName: string`, `input: unknown`), which would widen every member and defeat the narrowing. We project the static half, `StaticToolCall<typeof tools>`, onto our wire format, matching the `if (part.dynamic) break` above:

```typescript title="src/server/chat.ts (continued)"
// Distributes over the union: one member per tool, with its own input type
type ToToolCallChunk<C> = C extends { toolCallId: string; toolName: infer N; input: infer I }
  ? { type: "tool-call"; toolCallId: string; toolName: N; input: I }
  : never;

type ToolCallChunk = ToToolCallChunk<StaticToolCall<typeof tools>>;
// → | { type: 'tool-call'; toolCallId: string; toolName: 'getWeather'; input: { location: string } }
//   | { type: 'tool-call'; toolCallId: string; toolName: 'searchProducts'; input: { query: string; maxResults: number } }
```

This is the same pattern as server functions (Part 15): TypeScript checks the source file where tools are defined, the `transform` hook generates the client stub, and the types survive because the type checker operates on source, not transformed output. The client page imports `chat` for its _type_; the bundle gets only the stub.

## Structured object streaming

Beyond chat, AI models can generate structured data (JSON objects) progressively. In the current AI SDK that's `streamText` with an `output` schema; `partialOutputStream` yields the object as it fills in (older versions had a separate `streamObject` function):

```typescript title="src/server/report.ts"
import { createServerFn } from "eigen/server";
import { streamText, Output } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const reportSchema = z.object({
  title: z.string(),
  sections: z.array(
    z.object({
      heading: z.string(),
      content: z.string(),
    }),
  ),
  summary: z.string(),
});

export const generateReport = createServerFn()
  .validator(z.object({ topic: z.string().min(1).max(200) }))
  .streamHandler(async function* ({ data, context }) {
    const { partialOutputStream } = streamText({
      model: openai("gpt-5-mini"),
      output: Output.object({ schema: reportSchema }),
      prompt: `Write a short structured report about: ${data.topic}`,
      abortSignal: context.request.signal,
    });

    for await (const partial of partialOutputStream) {
      yield partial; // A deep-partial of z.infer<typeof reportSchema>
    }
  });
```

The client receives a progressively-completing object — first `{ title: "..." }`, then `{ title: "...", sections: [{ heading: "..." }] }`, and so on. Each chunk is the whole object so far, so the component renders the latest one and fills in as more arrives. (Sending only the changes would save bandwidth for long objects; the AI SDK's own UI protocol does that.)

## What to observe

1. **Watch the Network tab** during a chat interaction. The `/_eigen/fn/<id>` request is an `EventStream` response; open it to see one `data:` event per chunk, ending with `event: done`.

2. **Type a message and watch the response build** chunk by chunk. The text streams in via the `text-delta` chunks.

3. **Trigger a tool call** (ask about weather). The `tool-call` chunk appears in the stream, the UI shows a "calling tool" indicator, then the `tool-result` chunk arrives and the model's answer streams in after it. Make `fetchWeather` throw: the chunk arrives with `failed: true`, the indicator still clears, and the model answers around the error.

4. **Check the types** — hover over `tc.toolName` and `tc.input` in the page. TypeScript knows the possible tool names, and inside `if (tc.toolName === 'getWeather')` it knows `tc.input` is `{ location: string }`.

5. **Close the tab mid-response.** The server log shows the generator stopping — the stream's `cancel()` ran and the model call was abandoned instead of running to completion.

## Key insight

AI streaming extends the server function model from "request/response" to "request/stream." The same `transform` hook generates the client stub, but instead of returning `Promise<T>` it returns `ReadableStream<T>`. The SSE transport replaces the JSON response, on the same endpoint and behind the same middleware and validation. The type safety story is unchanged — TypeScript checks the source, the transform generates the stub, and the types survive.

This pattern isn't AI-specific. Any use case that produces structured data over time — real-time analytics, file processing progress, multi-step workflows — benefits from the same streaming server function primitive. AI is just the most compelling current application.
