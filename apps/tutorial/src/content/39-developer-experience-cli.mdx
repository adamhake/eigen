## `create-eigen` scaffolding CLI

Every popular framework ships a `create-*` CLI: `create-next-app`, `create-vite`, `create-remix`. Eigen's version is `create-eigen` — invoked via `npm create eigen`.

### How `npm create` works

When a user runs `npm create eigen`, npm:

1. Resolves the package `create-eigen`
2. Downloads and executes its `bin` entry
3. The CLI runs in the user's terminal

That's it — `npm create <name>` is shorthand for `npx create-<name>`.

### The CLI entry point

```typescript title="packages/create-eigen/src/index.ts"
#!/usr/bin/env node

import { parseArgs } from "node:util";
import { resolve } from "node:path";
import { fileURLToPath } from "node:url";
import { existsSync } from "node:fs";
import { cp, readdir, readFile, rename, writeFile } from "node:fs/promises";
import { loadFile, writeFile as writeModule } from "magicast";
import { addVitePlugin } from "magicast/helpers";
import prompts from "prompts";
import { mergePackageJson } from "./merge.js";

// Templates ship inside the package: dist/index.js → ../templates
const TEMPLATES = fileURLToPath(new URL("../templates/", import.meta.url));
const OVERLAYS = fileURLToPath(new URL("../overlays/", import.meta.url));

const { values, positionals } = parseArgs({
  allowPositionals: true,
  allowNegative: true, // --no-tailwind
  options: {
    tailwind: { type: "boolean" },
  },
});

async function main() {
  console.log("\n  create-eigen\n");

  // Project name from positional arg or prompt
  let projectName = positionals[0];
  if (!projectName) {
    const { name } = await prompts({
      type: "text",
      name: "name",
      message: "Project name:",
      initial: "my-eigen-app",
    });
    projectName = name;
  }
  if (!projectName) process.exit(1); // prompt cancelled

  // Interactive prompts for options not passed as flags
  const options = await prompts([
    {
      type: values.tailwind !== undefined ? null : "confirm",
      name: "tailwind",
      message: "Add Tailwind CSS?",
      initial: true,
    },
    {
      type: "select",
      name: "deploy",
      message: "Deployment target:",
      choices: [
        { title: "Node.js", value: "node" },
        { title: "Netlify", value: "netlify" },
        { title: "Cloudflare", value: "cloudflare" },
        { title: "None (decide later)", value: "none" },
      ],
    },
  ]);

  const config = {
    projectName,
    tailwind: values.tailwind ?? options.tailwind ?? true,
    deploy: options.deploy ?? "node",
  };

  // Refuse to scaffold into a non-empty directory. (fs.cp would merge into
  // it silently: errorOnExist only fires when an individual file collides.)
  const targetDir = resolve(process.cwd(), projectName);
  if (existsSync(targetDir) && (await readdir(targetDir)).length > 0) {
    throw new Error(`${targetDir} already exists and is not empty`);
  }

  // Copy the base template
  const base = config.deploy === "none" ? "node" : config.deploy;
  await cp(resolve(TEMPLATES, base), targetDir, { recursive: true });

  // npm never publishes a file named .gitignore, so templates ship it as _gitignore
  await rename(resolve(targetDir, "_gitignore"), resolve(targetDir, ".gitignore"));

  // Apply variant overlays
  if (config.tailwind) {
    await applyOverlay(targetDir, "tailwind");
    await addTailwindPlugin(targetDir);
  }

  // Post-setup
  await writeFile(resolve(targetDir, ".eigen.json"), JSON.stringify({ deploy: config.deploy }, null, 2));

  console.log(`\n  Done! Created ${projectName} at ${targetDir}`);
  console.log(`\n  cd ${projectName}`);
  console.log(`  npm install`);
  console.log(`  npm run dev\n`);
}

async function applyOverlay(targetDir: string, overlay: string) {
  const overlayDir = resolve(OVERLAYS, overlay);
  const pkgPath = resolve(targetDir, "package.json");
  const basePkg = JSON.parse(await readFile(pkgPath, "utf-8"));

  // Copy overlay files over the base, replacing files with the same name...
  await cp(overlayDir, targetDir, {
    recursive: true,
    force: true,
    filter: (src) => !src.endsWith("package.json"),
  });

  // ...except package.json, which is merged
  const overlayPkg = JSON.parse(await readFile(resolve(overlayDir, "package.json"), "utf-8"));
  await writeFile(pkgPath, JSON.stringify(mergePackageJson(basePkg, overlayPkg), null, 2) + "\n");
}

// vite.config.ts belongs to the base template (Netlify and Cloudflare put their
// adapter plugins there), so the overlay patches it instead of replacing it
async function addTailwindPlugin(targetDir: string) {
  const configPath = resolve(targetDir, "vite.config.ts");
  const mod = await loadFile(configPath);
  addVitePlugin(mod, { from: "@tailwindcss/vite", constructor: "tailwindcss", index: 0 });
  await writeModule(mod, configPath);
}

main().catch((error) => {
  console.error(error instanceof Error ? error.message : error);
  process.exit(1);
});
```

```json title="packages/create-eigen/package.json"
  "version": "0.1.0",
  "type": "module",
  "bin": {
    "create-eigen": "./dist/index.js"
  },
```

<Callout type="tip" title="Bundled vs. downloaded templates">
  Shipping templates inside the package (`"files"` includes `templates` and `overlays`) keeps them version-locked to the
  CLI release and works offline. The alternative is downloading them at run time with
  [`giget`](https://github.com/unjs/giget) — e.g.
  `downloadTemplate('gh:your-org/eigen/packages/create-eigen/templates/node', {dir})`. Note the `gh:owner/repo/subdir`
  source format: a bare `eigen/templates/node` would mean GitHub user `eigen`, repo `templates`.
</Callout>

## Project templates

Templates are complete, runnable projects that serve as starting points. The key challenge is keeping them in sync with the framework as it evolves.

### Template structure

```
packages/create-eigen/
  src/
    index.ts
    merge.ts
  templates/
    node/                    # Node.js deployment target
      src/
        pages/
          index.tsx
          about.tsx
        components/
          Layout.tsx
        app.css
      index.html
      server.ts                # dev server (Part 3); the adapter builds the production one
      vite.config.ts
      package.json
      tsconfig.json
      _gitignore               # renamed to .gitignore on copy
    netlify/                 # Netlify deployment target
      ...same structure...
      netlify.toml
    cloudflare/              # Cloudflare deployment target
      ...same structure...
      wrangler.toml
  overlays/                  # Sibling of templates/, also shipped in "files"
    tailwind/                # Adds Tailwind to any template
      src/
        app.css              # Replaces base app.css with Tailwind imports
      package.json           # Adds tailwindcss + @tailwindcss/vite (merged)
```

### Variant composition

Instead of maintaining N×M templates (every deployment target × every option), use overlays:

```
base template (node/netlify/cloudflare)
  + tailwind overlay
  = final project
```

Overlays add or replace files, so an overlay must never ship a file that varies between base templates. `vite.config.ts` is one: the Netlify and Cloudflare templates register their adapter plugins in it ([Part 17](/17-deployment-adapters)), and a replaced config would silently drop them. That's why the Tailwind overlay has no `vite.config.ts`. `addTailwindPlugin` patches the base template's config with `magicast` (introduced under [Codegen commands](#editing-an-existing-file-ast-based-with-magicast) below), which adds the import and the plugin call and leaves the rest of the file as it was. The `package.json` is special too — it's **merged** rather than replaced, so overlay dependencies are combined with base dependencies:

```typescript title="packages/create-eigen/src/merge.ts"
export function mergePackageJson(
  base: Record<string, unknown>,
  overlay: Record<string, unknown>,
): Record<string, unknown> {
  return {
    ...base,
    dependencies: {
      ...((base.dependencies as Record<string, string>) ?? {}),
      ...((overlay.dependencies as Record<string, string>) ?? {}),
    },
    devDependencies: {
      ...((base.devDependencies as Record<string, string>) ?? {}),
      ...((overlay.devDependencies as Record<string, string>) ?? {}),
    },
    scripts: {
      ...((base.scripts as Record<string, string>) ?? {}),
      ...((overlay.scripts as Record<string, string>) ?? {}),
    },
  };
}
```

## Codegen commands

Scaffolding gets you started. Codegen keeps you productive — generating routes, loaders, and components with the right conventions already wired up.

### `eigen generate route`

```bash
npx eigen generate route dashboard/settings
```

This creates:

```
src/pages/dashboard/settings.tsx    # Page component with loader
```

### Creating a new file: a template is fine

A brand-new file has nothing to preserve, so a template string is the simplest correct tool:

```typescript title="packages/eigen/cli/generate.ts"
import { writeFile, mkdir } from "node:fs/promises";
import { dirname, relative, resolve } from "node:path";
import { existsSync } from "node:fs";
import { fileToRoute } from "../plugins/eigen-routes";

export async function generateRoute(routePath: string) {
  // "posts/[id]" → '/posts/:id', "blog/index" → '/blog', "About" → '/about':
  // the same rule the route plugin applies, so the path matches RouteParamsMap
  const { path } = fileToRoute(`${routePath}.tsx`);
  // "user-settings/[id]" → UserSettingsIdPage: a valid identifier
  const words = routePath.split(/[^A-Za-z0-9]+/).filter(Boolean);
  const componentName = words.map((w) => w[0].toUpperCase() + w.slice(1)).join("") + "Page";
  const filePath = `src/pages/${routePath}.tsx`;
  const fullPath = resolve(process.cwd(), filePath);
  if (existsSync(fullPath)) throw new Error(`${filePath} already exists`);

  const code = `import { defineLoader } from 'eigen/helpers'
import type { PageProps } from 'eigen/types'

export const loader = defineLoader('${path}', async ({ params }) => {
  return {}
})

type LoaderData = Awaited<ReturnType<typeof loader>>

export default function ${componentName}({ data }: PageProps<'${path}', LoaderData>) {
  return (
    <div>
      <h1>${componentName}</h1>
    </div>
  )
}
`;

  await mkdir(dirname(fullPath), { recursive: true });
  await writeFile(fullPath, code);
  console.log(`  Created ${filePath}`);
}
```

The new path type-checks once the running dev server's watcher regenerates `eigen-routes.d.ts` for the new file ([Part 9](/09-hmr)); until then, `defineLoader` reports it as an unknown route.

### Editing an existing file: AST-based with `magicast`

`eigen generate loader src/pages/dashboard.tsx` adds a loader to a page the developer has already written. String concatenation would have to guess where imports end and exports begin; [`magicast`](https://github.com/unjs/magicast) parses the file, lets you edit it through a proxy, and prints it back with the original formatting preserved everywhere you didn't touch:

```typescript title="packages/eigen/cli/generate.ts (continued)"
import { builders, loadFile, writeFile as writeModule } from "magicast";
// relative, resolve, and fileToRoute are already imported at the top of the file

export async function generateLoader(file: string) {
  const mod = await loadFile(file);

  if (mod.exports.loader) {
    console.log(`  ${file} already exports a loader`);
    return;
  }

  // Add `import { defineLoader } from 'eigen/helpers'` unless it's there
  if (!mod.imports.defineLoader) {
    mod.imports.$append({ imported: "defineLoader", from: "eigen/helpers" });
  }

  // export const loader = defineLoader('/dashboard', async ({ params }) => ({}))
  const pagesDir = resolve(process.cwd(), "src/pages");
  const { path } = fileToRoute(relative(pagesDir, resolve(file)));
  mod.exports.loader = builders.functionCall("defineLoader", path, builders.raw("async ({ params }) => ({})"));

  await writeModule(mod, file);
  console.log(`  Added a loader to ${file}`);
}
```

### The CLI entry point

```typescript title="packages/eigen/cli/index.ts"
#!/usr/bin/env node

import { parseArgs } from "node:util";
import { generateRoute, generateLoader } from "./generate.js";

const { positionals } = parseArgs({
  allowPositionals: true,
  strict: false,
});

const [command, subcommand, ...args] = positionals;

if (command === "generate" || command === "g") {
  switch (subcommand) {
    case "route":
      await generateRoute(args[0]);
      break;
    case "loader":
      await generateLoader(args[0]);
      break;
    default:
      console.log("Unknown generator:", subcommand);
      console.log("Available: route, loader");
  }
} else {
  console.log("eigen CLI");
  console.log("  eigen generate route <path>");
  console.log("  eigen generate loader <file>");
}
```

For `npx eigen generate ...` to find this file, the `eigen` package needs a `"bin": { "eigen": "./dist/cli/index.js" }` entry pointing at the built CLI — [Part 40](/40-monorepo-publishing) adds it along with the build that produces `dist/cli/index.js`.

## Custom ESLint rules

Framework-specific linting catches mistakes that generic ESLint rules and the type checker can't — like a loader that's never exported, or a server function the compiler won't recognize.

### `eslint-plugin-eigen`

A page's loader only runs if it's exported: the route generator ([Part 2](/02-route-discovery-plugin)) reads `mod.loader`, and Part 7's transform only strips exported loaders. Drop the `export` and everything still type-checks and renders, but the loader never runs and `data` is `undefined`. That's a bug no type can express, which makes it a good lint rule:

```typescript title="packages/eslint-plugin-eigen/src/rules/no-unexported-loader.ts"
import type { Rule } from "eslint";

/**
 * Reports a top-level `loader` that isn't exported.
 * Eigen only reads exported loaders, so this one would silently never run.
 */
export const noUnexportedLoader: Rule.RuleModule = {
  meta: {
    type: "problem",
    docs: {
      description: "Require page loaders to be exported",
    },
    messages: {
      unexported: "`loader` is declared but not exported, so Eigen never runs it. Add `export`.",
    },
  },

  create(context) {
    let declaration: Rule.Node | null = null;
    let exported = false;

    return {
      // `const loader = ...` / `function loader() {}` directly in the module body.
      // Exported declarations sit under an ExportNamedDeclaration instead, so they don't match.
      "Program > VariableDeclaration > VariableDeclarator[id.name='loader']"(node: Rule.Node) {
        declaration = node;
      },
      "Program > FunctionDeclaration[id.name='loader']"(node: Rule.Node) {
        declaration = node;
      },
      // ...unless an `export { loader }` further down exports it after all
      "ExportNamedDeclaration > ExportSpecifier[local.name='loader'][exported.name='loader']"() {
        exported = true;
      },
      "Program:exit"() {
        if (declaration && !exported) {
          context.report({ node: declaration, messageId: "unexported" });
        }
      },
    };
  },
};
```

The keys are [ESLint selectors](https://eslint.org/docs/latest/extend/selectors), CSS-like patterns over the AST: `>` means "direct child", and `[id.name='loader']` matches on a property. The rule is meant for page files; scope it to `src/pages/**` in the config (below) so an unrelated module-level `loader` elsewhere isn't flagged.

### Server-only boundary detection

A second rule (`server-fn-boundary`) protects the server/client split from [Part 15](/15-server-functions). That transform only rewrites `createServerFn(...)` chains that initialize an **exported** `const`; a chain anywhere else — a non-exported `const`, inline in a component, inside a function — makes Part 15's client transform fail the build, because left as-is it would ship the handler (and its `db` import) to the browser. The lint rule reports the same mistake in the editor, before a build. The rule visits every `CallExpression` whose callee is `createServerFn`, walks up through the builder's member calls to the outermost chain, and reports unless that chain's parent is a `VariableDeclarator` inside an `ExportNamedDeclaration`. Same shape as `no-unexported-loader`: visitors, a structural check, a `context.report`.

### Plugin entry point

```typescript title="packages/eslint-plugin-eigen/src/index.ts"
import type { ESLint, Linter } from "eslint";
import { noUnexportedLoader } from "./rules/no-unexported-loader";
import { serverFnBoundary } from "./rules/server-fn-boundary";

const plugin = {
  meta: { name: "eslint-plugin-eigen", version: "0.1.0" },
  rules: {
    "no-unexported-loader": noUnexportedLoader,
    "server-fn-boundary": serverFnBoundary,
  },
  configs: {} as Record<string, Linter.Config[]>,
} satisfies ESLint.Plugin;

// Flat config: `plugins` is an object mapping a namespace to the plugin
// itself (not an array of names, as in the legacy .eslintrc format)
plugin.configs.recommended = [
  {
    name: "eigen/recommended",
    plugins: { eigen: plugin },
    rules: { "eigen/server-fn-boundary": "error" },
  },
  {
    name: "eigen/recommended/pages",
    files: ["src/pages/**/*.{ts,tsx}"],
    rules: { "eigen/no-unexported-loader": "error" },
  },
];

export default plugin;
```

The plugin is the module's **default** export, and its recommended config references the plugin object directly — that's the flat-config shape ESLint 9 and 10 expect. The recommended config is an array of two config objects, so the loader rule can be limited to page files with `files`. (Plugins registered in the first object are available to the second.) Users enable it with a single spread in their ESLint config:

```javascript title="eslint.config.js"
import eigen from "eslint-plugin-eigen";

export default [...eigen.configs.recommended];
```

## TypeScript plugin

A TypeScript language service plugin runs inside the editor's TypeScript server. It wraps the language service, so it can add completions, go-to-definition targets, and diagnostics for framework-specific patterns.

### What it's for

Most editor intelligence comes from the types alone. `<Link to="/` already completes every route path, because `to` is typed with the generated `RoutePaths` union ([Part 2](/02-route-discovery-plugin), [Part 11](/11-framework-plugin)), and a page's `data` prop is checked against its loader's return type ([Part 5](/05-typed-loaders)). A plugin that re-added those completions would only produce duplicates. A plugin earns its place for rules the type system can't express. One example: every file in `src/pages/` must default-export the page component. A page without one compiles cleanly, then renders nothing. The plugin turns that into an error in the editor.

### Plugin structure

```typescript title="packages/eigen/typescript-plugin.ts"
import type ts from "typescript";

function init(modules: { typescript: typeof ts }) {
  const ts = modules.typescript;

  function create(info: ts.server.PluginCreateInfo): ts.LanguageService {
    const ls = info.languageService;
    // Configurable from the tsconfig entry, like the eigen() plugin's pagesDir (Part 11)
    const pagesDir = `${info.project.getCurrentDirectory()}/${info.config.pagesDir ?? "src/pages"}/`;

    // Forward every method to the original language service...
    const proxy = Object.create(null) as ts.LanguageService;
    for (const k of Object.keys(ls) as Array<keyof ts.LanguageService>) {
      const x = ls[k];
      if (typeof x === "function") {
        (proxy as any)[k] = (...args: any[]) => (x as any).apply(ls, args);
      }
    }

    // ...then add one Eigen-specific check on top of TypeScript's own
    proxy.getSemanticDiagnostics = (fileName) => {
      const diagnostics = ls.getSemanticDiagnostics(fileName);
      const isPage = fileName.startsWith(pagesDir) && fileName.endsWith(".tsx") && !fileName.endsWith("/layout.tsx");
      if (!isPage) return diagnostics;

      const program = ls.getProgram();
      const sourceFile = program?.getSourceFile(fileName);
      if (!program || !sourceFile) return diagnostics;

      // A file with no exports at all has no module symbol
      const moduleSymbol = program.getTypeChecker().getSymbolAtLocation(sourceFile);
      if (moduleSymbol?.exports?.has(ts.InternalSymbolName.Default)) return diagnostics;

      return [
        ...diagnostics,
        {
          category: ts.DiagnosticCategory.Error,
          code: 100001, // any number TypeScript doesn't use itself
          source: "eigen",
          file: sourceFile,
          start: 0,
          length: 0,
          messageText: "Eigen pages need a default export (the page component). This route renders nothing.",
        },
      ];
    };

    return proxy;
  }

  return { create };
}

export default init;
```

In TypeScript 6, `typescript/lib/tsserverlibrary` is just a re-export of `typescript`, so the `server` namespace (`ts.server.PluginCreateInfo`) comes from the main package. The plugin only uses its types: at run time, everything goes through the `typescript` instance the server passes to `init`, which is the version the editor is actually running.

`tsserver` loads plugins with `require()`, so this file has to reach users as **CommonJS** even though the rest of `eigen` is ESM. [Part 40](/40-monorepo-publishing) builds it separately as `typescript-plugin.cjs` (tsdown turns the single `export default` into `module.exports = init`). How `tsserver` _finds_ it matters too. It resolves plugin names with the old `node10` algorithm, which ignores the `exports` map, so `eigen/typescript-plugin` must exist as a real path inside the package. Part 40 adds a `typescript-plugin/package.json` stub whose `main` points at the built file.

### Registering the plugin

Users add it to their `tsconfig.json`:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "plugins": [{ "name": "eigen/typescript-plugin" }]
  }
}
```

<Callout type="warning" title="Editor support: TypeScript 6 only, for now">
  Language service plugins run in the JavaScript-based TypeScript language service, the one in TypeScript 6.x and
  earlier, that VS Code (with "Use Workspace Version"), WebStorm, and other `tsserver`-based editors load. TypeScript 7,
  the native Go port, ships without a programmatic API, so its language server doesn't load `compilerOptions.plugins` at
  all. The TypeScript team expects a new, different API in 7.1. Until then, a project that wants the plugin can follow
  the split the TypeScript team suggests for Angular projects: TypeScript 7's `tsc` for fast command-line checks, and
  TypeScript 6 (installable side by side as `@typescript/typescript6`) for the editor. Plugins never affect `tsc` on the
  command line either way: they're purely for editor intelligence.
</Callout>

## Framework diagnostics

The dev overlay from [Part 10](/10-dev-overlay) shows runtime information. Framework diagnostics extend it with proactive checks — catching configuration mistakes, version mismatches, and common errors before they cause problems.

### Health checks

```typescript title="packages/eigen/diagnostics/health.ts"
import { existsSync } from "node:fs";
import { resolve } from "node:path";

export interface Diagnostic {
  level: "info" | "warning" | "error";
  title: string;
  message: string;
  fix?: string;
}

export async function runHealthChecks(root: string): Promise<Diagnostic[]> {
  const diagnostics: Diagnostic[] = [];

  // Check: TypeScript config
  diagnostics.push(...(await checkTsConfig(root)));

  // Check: Required dependencies
  diagnostics.push(...(await checkDependencies(root)));

  // Check: Route directory exists
  diagnostics.push(...(await checkRouteDirectory(root)));

  return diagnostics;
}

// Each check function reads a config file and returns diagnostics.
// checkTsConfig: verifies jsx and strict mode settings
// checkDependencies: ensures react, react-dom, and vite are installed
// checkRouteDirectory: confirms src/pages/ exists

async function checkTsConfig(root: string): Promise<Diagnostic[]> {
  const diagnostics: Diagnostic[] = [];
  // Read tsconfig.json, check compilerOptions.jsx and strict
  // Push an error if missing, a warning if strict mode is off
  return diagnostics;
}

async function checkDependencies(root: string): Promise<Diagnostic[]> {
  const diagnostics: Diagnostic[] = [];
  // Read package.json, check dependencies for react and vite
  // Push an error for each missing required package
  return diagnostics;
}

async function checkRouteDirectory(root: string): Promise<Diagnostic[]> {
  if (existsSync(resolve(root, "src/pages"))) return [];
  return [
    {
      level: "warning",

```

### Integrating with the dev overlay

Send diagnostics through the overlay's collector from [Part 10](/10-dev-overlay). Two details matter. Eigen's dev server runs in middleware mode ([Part 3](/03-server-side-rendering)), so `server.httpServer` is `null` and there's no `'listening'` event to wait for. And the checks finish long before any browser connects — a broadcast at startup would reach nobody. Part 10's collector solves the second problem already: it buffers events and replays them to each overlay that announces itself with `eigen:dev-hello` over Vite's HMR channel. Since Part 10 publishes the collector in `configResolved`, it exists by the time any `configureServer` runs.

```typescript title="packages/eigen/plugins/diagnostics.ts"
import type { Plugin } from "vite";
import { runHealthChecks } from "../diagnostics/health";

export function eigenDiagnosticsPlugin(): Plugin {
  return {
    name: "eigen:diagnostics",
    apply: "serve",

    async configureServer(server) {
      const diagnostics = await runHealthChecks(server.config.root);
      if (diagnostics.length === 0) return;

      // Buffered by Part 10's collector and replayed when the overlay connects.
      // (Plugin code runs in Node without Vite's transforms, so call the
      // collector directly rather than devEmit, which relies on import.meta.env.)
      const collector = (globalThis as any).__eigenDevCollector;
      collector?.emit({
        type: "diagnostics",
        timestamp: Date.now(),
        data: { diagnostics },
      });

      // Also log to the terminal, at the matching log level
      const { logger } = server.config;
      for (const d of diagnostics) {
        const prefix = d.level === "error" ? "✗" : d.level === "warning" ? "⚠" : "ℹ";
        const text = `  ${prefix} ${d.title}: ${d.message}` + (d.fix ? `\n    Fix: ${d.fix}` : "");
        if (d.level === "error") logger.error(text);
        else if (d.level === "warning") logger.warn(text);
        else logger.info(text);
      }
    },
  };
}
```

Part 10's buffer holds the most recent 200 events, so on a busy dev server a diagnostics event can scroll out before an overlay connects; a production-quality version would keep the latest diagnostics in a separate slot that's always replayed.

The dev overlay renders diagnostics in a panel:

```tsx title="packages/eigen/overlay/DiagnosticsPanel.tsx"
import type { Diagnostic } from "../diagnostics/health";

interface DiagnosticsPanelProps {
  diagnostics: Diagnostic[];
}

export function DiagnosticsPanel({ diagnostics }: DiagnosticsPanelProps) {
  if (diagnostics.length === 0) {
    return <div className="eigen-diagnostics-ok">All checks passed</div>;
  }

      {diagnostics.map((d, i) => (
        <div key={i} className={`eigen-diagnostic eigen-diagnostic-${d.level}`}>
          <strong>{d.title}</strong>
          <p>{d.message}</p>
          {d.fix && <code className="eigen-diagnostic-fix">{d.fix}</code>}
        </div>
      ))}
    </div>
  );
}
```

## The tooling layer in context

Here's how the DX tools relate to the runtime framework:

```
Developer writes code
  ├── create-eigen         → scaffolds the project
  ├── eigen generate       → generates routes, loaders
  ├── eslint-plugin-eigen  → catches framework-specific mistakes
  ├── TypeScript plugin    → editor errors for rules types can't express
  └── Dev overlay          → runtime diagnostics, health checks

Developer runs dev server
  ├── Vite dev server      → HMR, transforms, virtual modules
  ├── eigen() plugin       → route discovery, SSR, server functions
  └── Diagnostics plugin   → proactive error detection
```

None of these tools change the runtime behavior. They exist to make the developer faster, catch mistakes earlier, and reduce the gap between "I want to do X" and "X is working."

---

## Key insight

A framework's developer experience is a force multiplier — it doesn't change what's possible, but it dramatically changes what's practical. The scaffolding CLI removes the "blank page" problem. Code generation enforces conventions without documentation. ESLint rules catch mistakes before they become bugs. The TypeScript plugin puts framework rules the type system can't express into the editor. And diagnostics surface problems before the developer even knows to look.

The common thread: every DX tool is built from the same information the framework already has — the route tree, the module graph, the type definitions. The runtime framework _knows_ your routes, your loaders, your server functions. The DX layer just makes that knowledge accessible to the developer in the right place at the right time.
