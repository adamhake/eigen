---

## What's wrong with `pushState`/`popstate`

Since Part 4, our client-side router has used this pattern (in `packages/eigen/router.tsx` since Part 11):

```typescript
window.history.pushState({}, "", href);
window.dispatchEvent(new PopStateEvent("popstate"));
```

This works, but it's a hack. `pushState` is a low-level history manipulation API that was never designed for application routing. The problems are well-known: `popstate` doesn't fire on `pushState` (we manually dispatch it), there's no way to intercept or cancel navigations, no built-in loading states, no abort signals, and back/forward button handling requires careful state management.

The Navigation API, standardized as part of the HTML spec and now available in Chrome and Edge (102+), Firefox (147+), and Safari (26.2+), was designed specifically for what frameworks have been building ad hoc for a decade.

## The core API

```typescript
// Listen to ALL navigations — link clicks, back/forward, form submissions, programmatic
navigation.addEventListener("navigate", (event: NavigateEvent) => {
  // Only handle same-document-capable navigations (same origin, etc.)
  if (!event.canIntercept) return;

  const url = new URL(event.destination.url);

  // Decide BEFORE intercepting. Once intercept() is called, the browser
  // commits to an SPA navigation — returning early from the handler would
  // leave the new URL showing the old page.
  const match = matchRoute(url.pathname, routes);
  if (!match) return; // Not ours: let the browser do a normal page load

  event.intercept({
    // This async handler replaces the navigation with your SPA logic.
    // While its promise is pending, the browser shows its loading
    // indicator and exposes the navigation as `navigation.transition`.
    async handler() {
      // Fetch data, update React state, etc.
      const data = await fetchLoaderData(url.pathname);
      await renderRoute(match, data); // resolves once the new page is in the DOM
    },

    // Move focus and restore/reset scroll once the handler settles, so the
    // handler must not resolve before the new page has rendered
    focusReset: "after-transition",
    scroll: "after-transition",
  });
});

// Programmatic navigation — replaces pushState
navigation.navigate("/posts/42");

// With state
navigation.navigate("/dashboard", { state: { tab: "analytics" } });

// Replace current entry (instead of pushing)
navigation.navigate("/login", { history: "replace" });
```

The fundamental shift: instead of the framework _performing_ navigations (`pushState`, dispatch event, manually handle the response), the framework _intercepts_ navigations that the browser initiates. Links, form submissions, `navigation.navigate()`, and back/forward buttons all fire the same `navigate` event. The framework handles them uniformly.

## Rewriting Eigen's router

In Part 11, we extracted `Router` and `Link` into `packages/eigen/router.tsx` using the `pushState`/`popstate` pattern, and Part 13 reshaped `Router` around a single `{ pathname, data }` state and `RouteTree`, so layouts persist across navigations. Now we'll swap the `popstate` effect for a `navigate` listener. Everything else stays: the props (the server still renders `Router` through `<App>`, so nothing may touch `window` during render), the combined state, `RouteTree`, and Part 18's `parseRouteData`.

```tsx title="packages/eigen/router.tsx"
import { useState, useEffect, useLayoutEffect, useRef, startTransition, Suspense } from "react";
import { matchRoute } from "eigen/match-route";
import { routes } from "eigen/routes";
import type { RouteData } from "eigen/route-data";

interface RouterProps {
  initialPathname: string;
  initialData: unknown;
}

interface RouterState {
  pathname: string;
  data: RouteData | null;
}

async function fetchRouteData(href: string, signal: AbortSignal): Promise<unknown> {
  const res = await fetch(`/_eigen/data?path=${encodeURIComponent(href)}`, { signal });
  // A 404/500 becomes a failed navigation (navigateerror), not a confusing parse error
  if (!res.ok) throw new Error(`Loading ${href} failed: ${res.status}`);
  return res.json();
}

export function Router({ initialPathname, initialData }: RouterProps) {
  const [state, setState] = useState<RouterState>({
    pathname: initialPathname,
    data: initialData as RouteData | null,
  });

  // Resolves the in-flight navigation once React has committed its state
  const onCommit = useRef<(() => void) | null>(null);
  useLayoutEffect(() => {
    onCommit.current?.();
    onCommit.current = null;
  }, [state]);

  /** Render `next` in a transition; resolves when it's in the DOM */
  const commit = (next: RouterState) =>
    new Promise<void>((resolve) => {
      onCommit.current = resolve;
      startTransition(() => setState(next));
    });

  useEffect(() => {
    // Feature detection: without the Navigation API, Link renders a plain
    // <a> and nothing intercepts it, so every click is a full page load
    // (still correct, just not SPA).
    if (!("navigation" in window)) return;

    const handleNavigate = (event: NavigateEvent) => {
      // Only intercept same-origin page navigations: not fragment jumps,
      // not downloads (<a download>), not form POSTs (Part 38 handles those)
      if (!event.canIntercept || event.hashChange || event.downloadRequest !== null || event.formData !== null) return;

      const url = new URL(event.destination.url);

      // Only handle routes we know about — checked before intercept()
      const match = matchRoute(url.pathname, routes);
      if (!match) return; // Let the browser handle it (server 404 page)

      event.intercept({
        async handler() {
          // event.signal aborts the fetch when a newer navigation starts
          const json = await fetchRouteData(url.pathname, event.signal);
          const data = parseRouteData(match, json) as RouteData | null; // Part 18
          event.signal.throwIfAborted(); // Superseded while parsing? Don't render it.

          // Don't settle before React has committed the new page: focusReset
          // and scroll run when this promise resolves, and startTransition
          // only schedules the render (a React.lazy page may still be loading)
          await commit({ pathname: url.pathname, data });
        },
        focusReset: "after-transition",
        scroll: "after-transition",
      });
    };

    navigation.addEventListener("navigate", handleNavigate);
    return () => navigation.removeEventListener("navigate", handleNavigate);
  }, []);

  const match = matchRoute(state.pathname, routes);
  if (!match) return <h1>404</h1>;

  return (
    <Suspense fallback={<div>Loading...</div>}>
      <RouteTree match={match} data={state.data} />
    </Suspense>
  );
}
```

Two things changed besides the event source. The handler resolves only after the commit: the `useLayoutEffect` keyed on `state` resolves the pending promise once React has applied the new route to the DOM, so the browser restores scroll on back/forward against the _new_ page, not the old one. (It's a layout effect so the promise resolves before the browser paints; Part 24's `<ViewTransition>` depends on that too.) And Part 13's `loading` flag is gone. A boolean set in the handler and cleared in `finally` can flicker off when a newer navigation aborts an older one, and the browser already tracks the in-flight navigation for us, as `navigation.transition` (below).

### The `Link` component simplifies dramatically

Compare this to the Part 11 version, which needed `onClick`, `preventDefault`, and manual `pushState`:

```tsx
// Same props type as Part 11: `params` is required exactly when the route has
// params (static routes map to Record<string, never>)
type LinkProps<T extends RoutePaths> = {
  to: T;
  children: React.ReactNode;
} & (RouteParamsMap[T] extends Record<string, never> ? { params?: never } : { params: RouteParamsMap[T] });

export function Link<T extends RoutePaths>({ to, params, children }: LinkProps<T>) {
  let href: string = to;
  if (params) {
    href = to.replace(/:(\w+)/g, (_, key: string) => {
      return (params as Record<string, string>)[key] ?? `:${key}`;
    });
  }

  // That's it. A regular anchor tag.
  // The Navigation API's navigate event intercepts the click.
  // No onClick handler, no preventDefault, no manual pushState.
  return <a href={href}>{children}</a>;
}
```

This is the key simplification. The `Link` component no longer needs `onClick` / `preventDefault` / `pushState`. It renders a plain `<a>` tag. The Navigation API's `navigate` event fires when the user clicks it, and our intercept handler takes over. The link works with or without JavaScript — it's progressively enhanced by default.

## Abort signals: free cancellation

Notice `{ signal: event.signal }` on the fetch call. The `NavigateEvent` provides an `AbortSignal` that fires when the user initiates a _new_ navigation before the current one completes. If a user clicks three links quickly, the first two fetches are automatically aborted. No manual cleanup needed.

Compare this to our `popstate` router, where we had no cancellation at all — every fetch ran to completion even if the user had already navigated away.

## Transition state: `navigation.transition`

The Navigation API tracks the current in-progress navigation via `navigation.transition`: a `NavigationTransition` object (with `navigationType`, the `from` entry, and a `finished` promise) that exists from the moment a navigation is intercepted until its handler settles, and is `null` otherwise. Any component can observe it — no prop drilling, no router context:

```tsx
// In a global loading indicator component
function GlobalProgress() {
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    // currententrychange fires when an intercepted navigation commits —
    // by then navigation.transition describes it
    const onEntryChange = () => {
      const transition = navigation.transition;
      if (!transition) return;

      setLoading(true);
      transition.finished
        .catch(() => {}) // Aborted or failed — navigateerror has the details
        .finally(() => {
          // Superseded by a newer navigation? Then that one owns the spinner.
          if (navigation.transition === null) setLoading(false);
        });
    };

    navigation.addEventListener("currententrychange", onEntryChange);
    return () => navigation.removeEventListener("currententrychange", onEntryChange);
  }, []);

  return loading ? <progress className="global-nav-progress" /> : null;
}
```

For the success and failure details, the browser also fires `navigatesuccess` and `navigateerror` events on `navigation`. Together they replace the ad hoc loading state management that every SPA framework currently implements.

## History entries with typed state

The Navigation API's `NavigationHistoryEntry` objects carry state that persists across navigations and survives page reloads (unlike React state):

```typescript
// Store scroll position, form state, etc. in the history entry
navigation.navigate("/dashboard", {
  state: { scrollY: window.scrollY, activeTab: "analytics" },
});

// Read it back
const entry = navigation.currentEntry;
const state = entry?.getState() as { scrollY?: number; activeTab?: string };
```

A framework plugin could generate typed state interfaces per route:

```typescript
// In the generated .d.ts
declare module "eigen/route-types" {
  export interface RouteStateMap {
    "/dashboard": { scrollY?: number; activeTab?: string };
    "/posts/:id": { commentDraft?: string };
  }
}
```

## Plugin integration: generating a Navigation API-aware router

The route plugin can generate the intercept handler as part of the virtual module, so the user doesn't write routing logic at all:

```javascript
// In the client virtual module, the plugin generates (plain JS):
export function setupRouter(renderFn) {
  if ("navigation" in window) {
    navigation.addEventListener("navigate", (event) => {
      if (!event.canIntercept || event.hashChange) return;
      if (event.downloadRequest !== null || event.formData !== null) return;
      const url = new URL(event.destination.url);
      const match = matchRoute(url.pathname, routes);
      if (!match) return;

      event.intercept({
        async handler() {
          const res = await fetch(`/_eigen/data?path=${encodeURIComponent(url.pathname)}`, { signal: event.signal });
          if (!res.ok) throw new Error(`Loading ${url.pathname} failed: ${res.status}`);
          // renderFn returns a promise that resolves after the commit, as above
          await renderFn(url.pathname, await res.json());
        },
      });
    });
  }
}
```

## What to observe

1. **Click a link, then quickly click another.** In the Network tab, the first request shows as "cancelled" — the abort signal from the Navigation API killed it automatically.

2. **Use the browser's back/forward buttons.** The same `navigate` event fires, with `event.navigationType === 'traverse'`. No separate `popstate` handler needed.

3. **Disable JavaScript** and click a link. The page still navigates — it's a real `<a>` tag with a real `href`. The Navigation API is progressive enhancement over standard HTML.

4. **Check `navigation.entries()`.** It returns this tab's same-origin history entries as `NavigationHistoryEntry` objects — each with its `url`, `key`, `index` and `getState()` — something `window.history` never exposed (it only gives you `length` and the current `state`).

## Key insight

The Navigation API moves routing from "framework concern" to "browser primitive." Instead of every framework reimplementing `pushState` wrappers, click interception, scroll restoration, and abort handling, the browser provides a single event-driven model. The framework's job narrows: match routes, fetch data, render components. The transport layer (intercepting navigations, managing history, aborting in-flight requests) is handled by the platform.

For Vite plugin authors, this means the generated router code gets simpler. Less JavaScript in the client bundle, fewer edge cases to handle, and better integration with browser features like the back/forward cache (bfcache).
