_This is the twentieth installment in a series where we build a toy Next.js on top of Vite. In [Part 18](/18-runtime-validation), we added runtime validation. Now we'll use the Environment API (introduced in Vite 6, and still labelled a release candidate in Vite 8's docs) to add a third environment targeting Cloudflare Workers — a fundamentally different runtime with different global APIs, different constraints, and different deployment characteristics._

---

## Why a third environment matters

<Callout type="info" title="Environment vs. runtime">
  In this series, **environment** refers to a Vite build/dev target (client, ssr, edge) — each with its own module graph
  and resolve conditions. **Runtime** refers to the actual execution context where the code runs (browser, Node.js,
  Cloudflare Workers, Deno). A single environment targets a specific runtime.
</Callout>

So far, Eigen has two environments: `client` (browser) and `ssr` (Node.js). But modern deployment platforms don't just run Node. Cloudflare Workers, Deno Deploy, Vercel Edge Functions, and Netlify Edge all run JavaScript in lightweight V8 isolates with Web API globals (`Request`, `Response`, `fetch`) instead of Node APIs (`http.IncomingMessage`, `fs`, `Buffer`).

These edge runtimes have different constraints: no filesystem access, limited CPU time, restricted `node:` built-ins, and different module resolution. A framework that deploys to the edge needs Vite to process server code for this target — which means a third environment with its own resolve conditions, its own module graph, and its own build output.

This is exactly the problem the Environment API was designed to solve.

---

## Defining the edge environment

In `vite.config.ts`, add a custom environment:

```typescript title="vite.config.ts"
import { defineConfig, createRunnableDevEnvironment } from "vite";
import react from "@vitejs/plugin-react";
import eigen from "./packages/eigen/plugin"; // a package import from Part 40 on

export default defineConfig({
  plugins: [eigen(), react()],
  environments: {
    // The default 'client' and 'ssr' environments are still here.
    // We add a third one:
    edge: {
      // A server-side environment (the default for any env not named 'client')
      consumer: "server",
      resolve: {
        // Setting conditions REPLACES Vite's defaults, so re-add 'module'
        // and the dev/prod placeholder alongside the edge conditions
        conditions: ["workerd", "worker", "edge-light", "module", "browser", "development|production"],
        mainFields: ["module", "main"],
        // Edge bundles must be self-contained — there is no node_modules
        // on a Worker, so bundle every dependency instead of externalizing it
        noExternal: true,
      },
      build: {
        outDir: "dist/edge",
        rolldownOptions: {
          input: "src/entry-edge.tsx",
        },
        // Target modern JS (V8 isolates support recent syntax)
        target: "es2022",
      },
      dev: {
        // The DevEnvironment factory: Vite calls this once per server start
        // to create the object that owns this environment's module graph
        // and runs its code. This is what Vite does by default for a
        // server environment — a RunnableDevEnvironment whose ModuleRunner
        // executes modules in the Vite (Node) process.
        createEnvironment(name, config) {
          return createRunnableDevEnvironment(name, config);
        },
      },
    },
  },
});
```

The `dev.createEnvironment` factory is the seam that decides _where_ an environment's code runs during development. The default above runs edge code in Node — the right resolve conditions, but the wrong runtime: a `node:fs` import would quietly work in dev and then fail on a Worker that doesn't enable Node compatibility. A runtime-specific plugin replaces this factory with one that returns a `DevEnvironment` talking to the real runtime over a transport. That's exactly what `@cloudflare/vite-plugin` does (see [below](#using-cloudflarevite-plugin)).

### Resolve conditions

The `conditions` array is critical. When Vite resolves an import like `import { renderToReadableStream } from 'react-dom/server'`, it checks the package's `exports` map against these conditions. `react-dom`'s `package.json` exports different `./server` entry points for different conditions:

- `"node"` → Node.js build (Node-specific internals; exports both `renderToPipeableStream` and, in React 19, `renderToReadableStream`)
- `"workerd"` / `"worker"` / `"edge-light"` → edge builds (Web APIs only — no `node:` imports, no `renderToPipeableStream`)
- `"browser"` → Browser build

The `react` package itself has one more: a `"react-server"` condition that selects the RSC server build (we'll use this in Part 21).

By putting `workerd`, `worker` and `edge-light` first, the edge environment gets Web API-compatible builds of React and other packages.

## The edge entry point

Edge runtimes use Web standard APIs. The route matching (Part 3's `eigen/match-route`) and the middleware → loader pipeline (Part 14's `runRoute`) are plain TypeScript with no Node dependencies, so the edge entry reuses them unchanged. Since Part 12, the Node server renders with Web streams too — so the rendering code is the same on both sides, and only the module shape differs:

<Tabs items={["Edge (Web APIs)", "Node SSR (for comparison)"]}>
<Tab value="Edge (Web APIs)">

```tsx title="src/entry-edge.tsx"
import { renderToReadableStream } from "react-dom/server";
import { matchRoute } from "eigen/match-route";
import { runRoute } from "eigen/run-route";
import { routes } from "eigen/routes";
import { serializeForScript } from "eigen/serialize";

// A Worker is a module whose default export has a fetch handler:
// (request: Request) => Promise<Response>. No server, no port.
export default {
  async fetch(request: Request): Promise<Response> {
    const url = new URL(request.url);
    const match = matchRoute(url.pathname, routes);

    if (!match) {
      return new Response("<h1>404</h1>", {
        status: 404,
        headers: { "Content-Type": "text/html" },
      });
    }

    // Middleware + loader, exactly as on Node (Part 14)
    const result = await runRoute(match, request);
    if ("response" in result) return result.response;
    const { data } = result;

    const Component = match.route.component;

    // Web Streams, same as the Node server since Part 12. A real entry would
    // render the full document from the template (Part 6); this shows the moving parts.
    const stream = await renderToReadableStream(<Component params={match.params} data={data} />, {
      bootstrapScriptContent: `window.__EIGEN_DATA__ = ${serializeForScript(data)}`,
      onError(error: unknown) {
        console.error("Edge SSR error:", error);
      },
    });

    // For bots, wait for all content
    const isBot = /bot|crawler|spider/i.test(request.headers.get("user-agent") ?? "");
    if (isBot) {
      await stream.allReady;
    }

    return new Response(stream, {
      status: 200,
      headers: { "Content-Type": "text/html" },
    });
  },
};
```

</Tab>
<Tab value="Node SSR (for comparison)">

```tsx title="server.ts (simplified)"
import { H3, serve } from "h3";
import { renderToReadableStream } from "react-dom/server";
import { matchRoute } from "eigen/match-route";
import { runRoute } from "eigen/run-route";
import { routes } from "eigen/routes";
import { serializeForScript } from "eigen/serialize";

const app = new H3();

// H3 handlers already speak Request/Response (Part 3), and React 19's
// Node build exports renderToReadableStream (Part 12) — so the body of
// this handler is the same Web-streams code as the Worker's fetch()
app.all("/**", async (event) => {
  const request = event.req;
  const match = matchRoute(event.url.pathname, routes);
  if (!match) return new Response("<h1>404</h1>", { status: 404 });

  const result = await runRoute(match, request);
  if ("response" in result) return result.response;

  const Component = match.route.component;
  const stream = await renderToReadableStream(<Component params={match.params} data={result.data} />, {
    bootstrapScriptContent: `window.__EIGEN_DATA__ = ${serializeForScript(result.data)}`,
  });
  return new Response(stream, { headers: { "Content-Type": "text/html" } });
});

// The real difference: a long-running process that owns a port
serve(app, { port: 3000 });
```

</Tab>
</Tabs>

Because Eigen chose H3 back in Part 3 and Web streams in Part 12, the code is Web-standard on both sides — `Request` in, `renderToReadableStream`, `Response` out. What differs is everything _around_ that code: the Node server is a long-running process that calls `serve()` on a port, while a Worker is just a module with a `fetch` export that the platform invokes per request. And the two are built differently: the edge environment resolves `react-dom/server` and every other dependency through the `workerd`/`worker`/`edge-light` conditions and bundles them all (`noExternal: true`), while the `ssr` build resolves the `node` builds and leaves `node_modules` external. Same source, different resolve conditions and bundling — that's what an environment is.

## Environment-polymorphic types

Our framework types need to support both Node and edge handlers. This is where a TypeScript discriminated union earns its keep:

```typescript title="packages/eigen/handler-types.ts"
import type { ApiContext } from "eigen/api-types";

/** Node.js handler (Express/Hono/Fastify style) */
export interface NodeHandler {
  (req: import("http").IncomingMessage, res: import("http").ServerResponse): Promise<void> | void;
}

/** Edge handler (Cloudflare Workers / Web standard) */
export interface EdgeHandler {
  fetch(request: Request): Promise<Response>;
}

/** API handler that works in either environment */
export type UniversalApiHandler<TResponse = unknown> =
  | {
      runtime: "node";
      handler: (ctx: ApiContext) => Promise<TResponse>;
    }
  | {
      runtime: "edge";
      handler: (request: Request) => Promise<Response>;
    };

/**
 * The framework's createHandler helper adapts to the target environment.
 * The plugin generates different code per environment, so at runtime
 * only one branch exists in the bundle.
 */
export function createHandler<T>(handlers: {
  node?: (ctx: ApiContext) => Promise<T>;
  edge?: (request: Request) => Promise<Response>;
}): NodeHandler | EdgeHandler {
  // Naive runtime sniffing — shown only to motivate the build-time approach
  // below. It's also wrong: Workers with the `nodejs_compat` flag define
  // `process`, so this would pick the Node branch on Cloudflare.
  if (typeof globalThis.process !== "undefined") {
    // Node environment
    return handlers.node as any;
  } else {
    // Edge environment
    return { fetch: handlers.edge! } as any;
  }
}
```

The cleaner approach: the virtual module generates different handler wiring per environment, so the runtime check disappears and only one branch exists in each bundle. The edge environment's `eigen/routes` imports the edge-compatible handler directly.

## Plugin behavior per environment

The `applyToEnvironment` hook (introduced in Part 7) becomes essential when you have three environments. Some plugins should only run in specific environments:

```typescript
// Example: a plugin that polyfills Node APIs for edge
export function edgePolyfills(): Plugin {
  return {
    name: "eigen-edge-polyfills",
    applyToEnvironment(env) {
      return env.name === "edge";
    },
    resolveId(id, importer) {
      // Redirect Node built-in imports to edge-compatible polyfills.
      // Returning the bare string would make it the final id; this.resolve
      // runs it through the normal resolution (alias, exports, etc.).
      if (id === "node:crypto") {
        return this.resolve("eigen/polyfills/crypto", importer, { skipSelf: true });
      }
      if (id === "node:buffer") {
        return this.resolve("eigen/polyfills/buffer", importer, { skipSelf: true });
      }
    },
  };
}
```

The virtual route module also needs to generate edge-appropriate code:

```typescript
// In the load() hook — three-way branch
load(id: string) {
  if (id !== resolvedVirtualModuleId) return

  const routes = discoverRoutes(pagesDir)
  const envName = this.environment?.name

  if (envName === 'edge') {
    // Edge: static imports, loaders included, no React.lazy
    // (same as SSR, but resolve conditions differ)
    return generateRouteCode(routes, { lazy: false, includeLoaders: true })
  } else if (envName === 'ssr') {
    return generateRouteCode(routes, { lazy: false, includeLoaders: true })
  } else {
    // Client: lazy imports, no loaders
    return generateRouteCode(routes, { lazy: true, includeLoaders: false })
  }
}
```

## Build orchestration with three environments

The `buildApp` hook now coordinates three builds:

```typescript
buildApp: {
  order: 'pre' as const,
  async handler(builder) {
    // 1. Client build (generates manifest)
    await builder.build(builder.environments.client)
    // 2. Node SSR build (for traditional server hosting)
    await builder.build(builder.environments.ssr)
    // 3. Edge build (for Cloudflare/Deno deployment)
    if (builder.environments.edge) {
      await builder.build(builder.environments.edge)
    }
  },
}
```

## Using `@cloudflare/vite-plugin`

In a real deployment, you'd use Cloudflare's official Vite plugin instead of configuring the edge environment by hand. It reads the Worker's entry and settings from a Wrangler config file:

```jsonc title="wrangler.jsonc"
{
  "name": "eigen-app",
  "main": "./src/entry-edge.tsx",
  "compatibility_date": "2026-10-01",
}
```

```typescript title="vite.config.ts"
import { defineConfig } from "vite";
import { cloudflare } from "@cloudflare/vite-plugin";
import react from "@vitejs/plugin-react";
import eigen from "./packages/eigen/plugin"; // a package import from Part 40 on

export default defineConfig({
  plugins: [
    eigen(),
    // By default the environment is named after the Worker ("eigen_app").
    // Name it 'edge' so Eigen's load() and buildApp branches still match.
    cloudflare({ viteEnvironment: { name: "edge" } }),
    react(),
  ],
  // No hand-written environments.edge block: the plugin supplies the
  // resolve conditions, the build input (from "main") and the dev factory.
});
```

This maps directly to the pattern we've built. The plugin configures the environment's resolve conditions and build, and — the important part — replaces the `dev.createEnvironment` factory with one backed by `workerd` (the actual Workers runtime, via Miniflare). Your edge code runs in the real runtime during development — not a Node.js approximation — so an unsupported `node:` import fails in dev the same way it fails in production. This is the "dev matches prod" promise of the Environment API.

## What to observe

1. **Run `vite build`** with the edge environment configured. You get three output directories. The edge bundle is self-contained — no `require('pg')` or other Node dependencies.

2. **Compare the edge and SSR bundles.** Both call `renderToReadableStream` and return a `Response`, but the edge bundle has React's edge build (and every other dependency) inlined, while the SSR bundle imports `react-dom/server` from `node_modules`, resolved to its Node build. Same app, different runtime targets.

3. **Check resolve behavior.** Import something that has different exports for Node vs. edge (like `react-dom/server`). The edge environment resolves to the workerd-compatible build.

4. **Try importing `node:fs` in an edge-targeted file.** With the default (Node-backed) dev environment it quietly works in dev; under `@cloudflare/vite-plugin`'s workerd-backed environment it fails, as it will in production (our `wrangler.jsonc` doesn't enable the `nodejs_compat` flag, so there are no `node:` modules) — unless the polyfill plugin redirects it.

## Key insight

The Environment API is the Vite feature that makes multi-runtime frameworks possible. Before the Environment API, supporting edge runtimes meant running separate Vite instances or using a meta-framework like Vinxi to coordinate multiple builds. Now it's a configuration object with its own resolve conditions, build config, and plugin filtering.

For a framework author, the three environments — client, ssr, edge — are three different _compilation targets_ for the same source code. The plugin pipeline is shared (one set of plugins), but each environment gets its own module graph, its own resolved imports, and its own build output. The virtual module generates different code per environment. The `applyToEnvironment` hook lets plugins opt in or out. And `buildApp` orchestrates the whole thing.

This is the architectural foundation for React Server Components, which we'll explore in [Part 21](/21-react-server-components).
