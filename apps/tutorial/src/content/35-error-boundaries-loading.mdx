## _This module builds Eigen's error and loading state system — route-scoped error boundaries that preserve type safety, file-based `error.tsx` and `loading.tsx` conventions with generated types, granular error recovery, streaming-aware loading states, and pending UI for client-side navigations._

## The design challenge

Error handling in a framework has several dimensions that a simple `try/catch` doesn't address:

**Where did the error happen?** A loader error, a render error, a server function error, and a streaming error all need different handling. A loader error means the component never renders. A render error means the component started rendering and threw. A streaming error means the shell rendered fine but a Suspense boundary failed mid-stream.

**How much of the page should break?** If the sidebar's loader fails, should the entire page show an error? Or should just the sidebar show an error while the rest of the page works? Next.js's per-segment `error.tsx` handles this — the error boundary wraps the segment, not the page.

**Can the user recover?** A transient network error should offer a retry button. A 404 should show a not-found page. A permission error should redirect to login. The error component needs enough context to decide.

**What types are available?** When the error component renders, it should know the route's params (so it can offer a "go back" link or retry the loader with the correct params). Generic `Error` objects lose this context.

Eigen discovers error and loading components alongside pages and layouts:

        <File name="layout.tsx" />
        <File name="index.tsx" />
        <Folder name="analytics" defaultOpen>

          <File name="loading.tsx" />
          <File name="index.tsx" />
        </Folder>
      </Folder>

The hierarchy works like CSS cascade — the most specific error boundary catches first. If `analytics/error.tsx` doesn't exist, the error bubbles up to `dashboard/error.tsx`, then to the root `error.tsx`.

## Typed error component props

When the route plugin discovers an `error.tsx` file, it generates typed props for that error component based on its position in the route tree:

```typescript title="packages/eigen/error-types.ts"
import type { RouteParams } from "eigen/types";

export interface ErrorBoundaryProps<TPath extends string = string> {
  /** The error that was caught */
  error: Error;
  /** Reset the error boundary and retry rendering */
  reset: () => void;
  /** The route params at the time of the error */
  params: RouteParams<TPath>;
  /** The pathname that errored */
  pathname: string;
  /** Which phase the error occurred in */
  phase: "loader" | "render" | "stream";
  /**
   * Re-run the route's loaders and, if they succeed, clear the error
   * (available when phase is 'loader')
   */
  retryLoader?: () => Promise<void>;
}

export interface LoadingProps<TPath extends string = string> {
  /** The route params being loaded */
  params: RouteParams<TPath>;
  /** The pathname being loaded */
  pathname: string;
}

export interface NotFoundProps {
  /** The pathname that wasn't matched */
  pathname: string;
}
```

The generated declarations give each error component its route-specific types:

```typescript title="node_modules/.eigen/eigen-error-types.d.ts"
declare module "eigen/error-types" {
  // Dashboard error component knows about dashboard params
  export interface DashboardErrorProps extends ErrorBoundaryProps<"/dashboard"> {}

  // Analytics error component knows about analytics params
  export interface AnalyticsErrorProps extends ErrorBoundaryProps<"/dashboard/analytics"> {}
}
```

## Writing error components

```tsx title="src/pages/dashboard/error.tsx"
import type { ErrorBoundaryProps } from "eigen/error-types";

export default function DashboardError({ error, reset, params, phase, retryLoader }: ErrorBoundaryProps<"/dashboard">) {
  return (
    <div role="alert">
      <h2>Something went wrong in the dashboard</h2>

      {phase === "loader" ? (
        <>
          <p>Failed to load dashboard data: {error.message}</p>
          <button onClick={() => retryLoader?.()}>Retry loading</button>
        </>
      ) : (
        <>
          <p>A rendering error occurred: {error.message}</p>
          <button onClick={reset}>Try again</button>
        </>
      )}

      <a href="/">Go home</a>
    </div>
  );
}
```

import type { LoadingProps } from "eigen/error-types";

            <div key={i} className="skeleton-card" />

## How error boundaries compose with layouts

The critical architectural decision: where does the error boundary sit relative to the layout?

```
Option A: Error boundary INSIDE the layout
  <DashboardLayout>
    <ErrorBoundary>        ← Layout renders even if content errors
      <AnalyticsPage />
    </ErrorBoundary>
  </DashboardLayout>

Option B: Error boundary OUTSIDE the layout
  <ErrorBoundary>          ← Layout is replaced by error UI
    <DashboardLayout>
      <AnalyticsPage />
    </DashboardLayout>
  </ErrorBoundary>
```

Eigen follows Next.js's model: the error boundary wraps the **segment content**, not the layout. If the analytics page's loader fails, the dashboard layout (sidebar, navigation) still renders — only the content area shows the error. This preserves navigation context so the user can click away to a working page.

But if the _layout's_ loader fails, the error boundary above it catches it, replacing the entire layout and its children with the error UI.

The virtual module generates this nesting (each segment: layout → error boundary → loading boundary → children, the same order Next.js uses):

```typescript
// Generated component for /dashboard/analytics
function DashboardAnalyticsRoute(props) {
  return (
    <GlobalErrorBoundary>                    {/* Framework default: the only boundary that can catch RootLayout's own errors */}
      <RootLayout>
        <RootErrorBoundary>                  {/* pages/error.tsx: errors below RootLayout */}
          <DashboardLayout>
            <DashboardErrorBoundary>         {/* dashboard/error.tsx: dashboard content errors */}
              <Suspense fallback={<DashboardLoading />}>
                <AnalyticsErrorBoundary>     {/* analytics/error.tsx: analytics errors */}
                  <Suspense fallback={<AnalyticsLoading />}>
                    <AnalyticsPage />
                  </Suspense>
                </AnalyticsErrorBoundary>
              </Suspense>
            </DashboardErrorBoundary>
          </DashboardLayout>
        </RootErrorBoundary>
      </RootLayout>
    </GlobalErrorBoundary>
  )
}
```

An error boundary only catches errors in its _children_, so a segment's `error.tsx` can never catch an error thrown by the layout of that same segment — `DashboardLayout` failing is handled by `RootErrorBoundary`, and `RootLayout` failing can only be handled by a boundary outside it. That's why the framework adds a last-resort `GlobalErrorBoundary` (Next.js exposes the same slot as `global-error.tsx`); since it replaces the root layout, its fallback must render a complete page shell on its own.

## The error boundary component

React has no built-in error boundary component — a boundary is any class component that implements `static getDerivedStateFromError` (and optionally `componentDidCatch`); function components can't be boundaries. Eigen's boundary adds the framework's route context:

```tsx title="packages/eigen/error-boundary.tsx"
import { Component, type ComponentType, type ErrorInfo, type ReactNode } from "react";
import type { ErrorBoundaryProps } from "eigen/error-types";

type Phase = "loader" | "render" | "stream";

interface Props {
  fallback: ComponentType<ErrorBoundaryProps<any>>;
  params: Record<string, string>;
  pathname: string;
  /** A loader error the framework already caught (during SSR or from /_eigen/data) */
  initialError?: { error: Error; phase: Phase };
  /** Re-runs the current route's loaders and updates its data (provided by the router) */
  reloadData?: () => Promise<void>;
  onError?: (error: Error, phase: Phase) => void;
  children: ReactNode;
}

interface State {
  error: Error | null;
  phase: Phase;
}

export class RouteErrorBoundary extends Component<Props, State> {
  constructor(props: Props) {
    super(props);
    this.state = props.initialError
      ? { error: props.initialError.error, phase: props.initialError.phase }
      : { error: null, phase: "render" };
  }

  static getDerivedStateFromError(error: unknown): Partial<State> {
    // Anything can be thrown; normalize so the fallback always gets an Error
    return { error: error instanceof Error ? error : new Error(String(error)), phase: "render" };
  }

  componentDidCatch(error: Error, info: ErrorInfo) {
    this.props.onError?.(error, this.state.phase);

    // Report to error tracking (PostHog, Sentry, etc.)
    if (typeof window !== "undefined" && (window as any).posthog) {
      (window as any).posthog.captureException(error, {
        route: this.props.pathname,
        phase: this.state.phase,
        componentStack: info.componentStack,
      });
    }
  }

  reset = () => {
    this.setState({ error: null, phase: "render" });
  };

  retryLoader = async () => {
    try {
      // Fetch fresh loader data for this URL; the router re-renders the route with it
      await this.props.reloadData?.();
      this.setState({ error: null, phase: "render" });
    } catch (error) {
      // Still failing — stay in the error state with the new error
      this.setState({ error: error instanceof Error ? error : new Error(String(error)), phase: "loader" });
    }
  };

  render() {
    if (this.state.error) {
      const Fallback = this.props.fallback;
      return (
        <Fallback
          error={this.state.error}
          reset={this.reset}
          params={this.props.params}
          pathname={this.props.pathname}
          phase={this.state.phase}
          retryLoader={this.state.phase === "loader" ? this.retryLoader : undefined}
        />
      );
    }
    return this.props.children;
  }
}
```

The generated route component renders each boundary with `key={pathname}`. Without the key, a boundary that caught an error on `/posts/1` would keep showing it after the user navigates to `/posts/2`, because the same component instance is reused.

## Loader errors vs. render errors

Loader errors happen _before_ the component renders — the data fetch failed. Render errors happen _during_ rendering — a component threw while rendering (null reference, bad data shape, etc.).

The framework distinguishes these. There's an important catch on the server: **React's error boundaries don't run during server rendering.** `getDerivedStateFromError` is a client-side mechanism — when a component throws inside `renderToString`, the whole call throws. So the SSR pipeline handles both phases itself and hands the result to the boundary as `initialError`:

```tsx title="entry-server.tsx"
import { runRoute } from "eigen/run-route";
import { serializeForScript } from "eigen/serialize";

export async function render(request: Request): Promise<RenderResult> {
  const { pathname } = new URL(request.url);
  const match = matchRoute(pathname, routes);
  if (!match) return { html: "<h1>404</h1>", status: 404, data: null, head: "" };

  // Phase 1: middleware + loaders
  let data: unknown = null;
  let routeError: SerializedRouteError | undefined;
  try {
    const result = await runRoute(match, request);
    if ("response" in result) return result; // redirects, 403s, ...
    data = result.data;
  } catch (error) {
    routeError = toSerializedError(error, "loader", match);
  }

  // Phase 2: rendering. The generated route component passes initialError to
  // the nearest boundary, which renders its fallback instead of its children.
  let html: string;
  try {
    html = renderToString(<App match={match} data={data} initialError={routeError} />);
  } catch (error) {
    // A component threw during SSR. No boundary caught it (they can't on the
    // server), so re-render with the error handed to the nearest boundary.
    routeError = toSerializedError(error, "render", match);
    html = renderToString(<App match={match} data={null} initialError={routeError} />);
  }

  // Metadata (Part 30) and session/query state (Parts 33–34) are omitted here
  const head = routeError ? `<script>window.__EIGEN_ERROR__=${serializeForScript(routeError)}</script>` : "";
  return { html, status: routeError ? 500 : 200, data, head };
}
```

(As elsewhere after Part 12, `renderToString` keeps the snippet short; the real pipeline streams. With streaming, a component that throws inside a `<Suspense>` boundary makes React send that boundary's fallback and retry the subtree on the client — where the error boundary _does_ catch it if it throws again. Errors outside every Suspense boundary fail the shell, which is where the fallback re-render above applies.)

On client-side navigations, the router does the same thing for `/_eigen/data` failures: it passes the error to the route as `initialError` with `phase: 'loader'`, and passes `reloadData` so the error component's retry button works.

## Loading states and Suspense integration

The `loading.tsx` convention maps directly to Suspense fallbacks. The route plugin wraps each segment in a `<Suspense>` boundary with the corresponding loading component:

```typescript
// Generated: loading.tsx becomes the Suspense fallback
<Suspense fallback={<DashboardLoading params={params} pathname={pathname} />}>
  <DashboardPage />
</Suspense>
```

This works seamlessly with streaming SSR (Part 12): the loading component is sent as HTML in the initial shell, and the real content streams in when the loader resolves. The loading component is a React component, not a static spinner — it can show skeletons that match the page layout.

### Client-side navigation loading

During client-side navigations (Part 22), the loading state appears while the new route's data is being fetched. The framework uses React's `useTransition` to keep the current page visible while loading:

```typescript
// In the router — pending state during navigation
function Router() {
  const [isPending, startTransition] = useTransition()

  function handleNavigate(pathname: string) {
    startTransition(async () => {
      const data = await fetchLoaderData(pathname)
      // State updates after an `await` are not automatically part of the
      // transition (a current React limitation), so wrap them again —
      // otherwise they're urgent updates and the Suspense fallback can flash
      startTransition(() => {
        setPathname(pathname)
        setData(data)
      })
    })
  }

  return (
    <>
      {/* Show a progress bar during transitions */}
      {isPending && <NavigationProgress />}

      {/* Current page stays visible until new page is ready */}
      <Suspense fallback={<CurrentRouteLoading />}>
        <CurrentRoute />
      </Suspense>
    </>
  )
}
```

The `isPending` state from `useTransition` gives the framework two options for loading UX:

1. **Instant transition** — Immediately show the new route's `loading.tsx` skeleton (like Next.js)
2. **Delayed transition** — Keep the current page visible with a progress bar, switch to the new page when data arrives (like Remix/TanStack)

Eigen defaults to the delayed transition (keep current page visible) because it feels less jarring, but makes it configurable per-link:

```tsx
// Immediate transition — show skeleton right away
<Link to="/dashboard" transition="instant">Dashboard</Link>

// Delayed transition — keep current page, show progress bar (default)
<Link to="/dashboard" transition="pending">Dashboard</Link>
```

## Not-found handling

The `not-found.tsx` convention handles 404s at any level of the route tree:

```tsx title="src/pages/dashboard/not-found.tsx"
// Renders when a path under /dashboard doesn't match any route
export default function DashboardNotFound({ pathname }: NotFoundProps) {
  return (
    <div>
      <h2>Dashboard page not found</h2>
      <p>
        No dashboard section exists at <code>{pathname}</code>
      </p>
      <a href="/dashboard">Back to dashboard</a>
    </div>
  );
}
```

The root `not-found.tsx` is the global 404 page. Segment-level not-found components handle missing child routes while preserving the parent layout — so `DashboardLayout` still renders with its sidebar when a bad URL like `/dashboard/nonexistent` is visited.

## Error serialization for SSR

When an error occurs during SSR, the client must hydrate the _same_ error UI, so the error is serialized into the page. Two rules apply: it goes through `serializeForScript` (an error message can contain user input — `Post "</script><script>…" not found` — so raw `JSON.stringify` would be an XSS hole), and in production it doesn't carry the real message at all. Internal error text (SQL, hostnames, file paths, stack traces) stays in the server logs, linked by a short digest:

```typescript title="entry-server.tsx"
interface SerializedRouteError {
  message: string;
  digest: string;
  phase: "loader" | "render";
  route: string;
  params: Record<string, string>;
}

function toSerializedError(error: unknown, phase: "loader" | "render", match: RouteMatch): SerializedRouteError {
  const digest = crypto.randomUUID().slice(0, 8);
  // The full error, with its stack, goes to the server log only
  console.error(`[eigen] ${phase} error ${digest} on ${match.route.path}`, error);

  return {
    message:
      import.meta.env.DEV && error instanceof Error ? error.message : `Something went wrong (reference ${digest})`,
    digest,
    phase,
    route: match.route.path,
    params: match.params,
  };
}
```

The server renders the fallback from this sanitized object too (via `initialError` above), so server HTML and client hydration agree. The client entry reads it and hands it to the same boundary:

```tsx title="entry-client.tsx"
const serialized = (window as any).__EIGEN_ERROR__ as SerializedRouteError | undefined;
const initialError = serialized
  ? { error: Object.assign(new Error(serialized.message), { digest: serialized.digest }), phase: serialized.phase }
  : undefined;

hydrateRoot(document.getElementById("root")!, <App initialError={initialError} />);
```

## Typed error recovery

The most powerful pattern: the error component can retry the loader with the original typed params:

```tsx title="src/pages/posts/[id]/error.tsx"
export default function PostError({
  error,
  params, // params.id: string — typed from the route
  phase,
  retryLoader,
}: ErrorBoundaryProps<"/posts/:id">) {
  if (phase === "loader") {
    return (
      <div>
        <p>Couldn't load post {params.id}.</p>
        <button onClick={() => retryLoader?.()}>Try loading post {params.id} again</button>
      </div>
    );
  }

  return (
    <div>
      <p>
        Failed to load post {params.id}: {error.message}
      </p>
      <a href="/posts">Back to all posts</a>
    </div>
  );
}
```

The `params.id` is typed as `string` because the error component knows it's scoped to the `/posts/:id` route. This is only possible because the route plugin generates the error boundary with the correct generic parameter. A generic `error.tsx` that handles all routes would have `params: Record<string, string>` — less useful.

## What to observe

1. **Throw an error in a loader** (e.g., `throw new Error('Database unavailable')`). The error boundary renders with `phase: 'loader'` and a retry button — and the response status is 500. Click retry — `reloadData` re-requests `/_eigen/data`, the loader re-executes, and the page appears once it succeeds.

2. **Throw an error in a component's render** (e.g., access a property on `null`). Load the page directly: the SSR fallback path renders the error UI. Then trigger the same error after a client-side navigation: this time the React error boundary catches it with `phase: 'render'`. Either way, the layout above the boundary still renders.

3. **Run a production build and view source on an errored page.** `window.__EIGEN_ERROR__` holds a generic message and a digest; the real message is only in the server log next to the same digest.

4. **Remove `error.tsx`** from a segment. The error bubbles up to the parent segment's error boundary — demonstrating the cascade.

5. **Check the types** — hover over `params` in an error component. It knows the route's dynamic segments, not just `Record<string, string>`.

6. **Navigate to a non-existent route under a layout.** The layout renders normally, and the segment's `not-found.tsx` (or the global one) shows inside the layout's content area.

---

## Key insight

Error handling in a framework isn't `try/catch` — it's a _hierarchy of error boundaries_ that mirrors the route tree. Each boundary knows its segment's params, can distinguish loader errors from render errors, and can offer typed recovery actions. The loading state system is the same hierarchy but for the pending state — each segment can show its own skeleton while data loads.

The type safety angle is what makes Eigen's approach distinct. Because the route plugin generates the error boundary wiring and the type declarations together, the error component for `/posts/:id` knows that `params.id` is a string. This is the same "types from the filesystem" pattern that powers the rest of Eigen — the plugin sees `src/pages/posts/[id]/error.tsx`, infers the route path, and generates `ErrorBoundaryProps<'/posts/:id'>`.

The framework handles the plumbing (boundary placement, server-side error rendering, safe error serialization, loader retry, Suspense integration). The developer writes the UI (what the error looks like, what recovery actions to offer). Both sides are type-safe.
