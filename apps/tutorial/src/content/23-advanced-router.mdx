## The limitations of our current router

Since Part 2, our route matching has been a linear scan with simple string comparison:

```typescript
for (const route of routes) {
  // Check each segment...
}
```

This breaks in several real-world scenarios. When both `/posts/:id` and `/posts/new` exist, which matches `/posts/new`? Our current router matches whichever comes first in the array. When `/docs/:category/:page` and `/docs/:slug` both exist, the more specific route should win — but our router can't distinguish specificity.

---

## Ranked route matching

Production routers rank routes by specificity. A static segment beats a dynamic segment, which beats an optional segment, which beats a catch-all. The comparison has to be made _segment by segment, left to right_ — summing points per route looks tempting, but it produces ties exactly where you need a decision (`/posts/:id` and `/:section/new` would both "score" the same for `/posts/new`):

```typescript title="packages/eigen/router/matcher.ts"
export interface RouteSegment {
  type: "static" | "dynamic" | "optional" | "catch-all";
  value: string; // The literal value ('posts') or param name ('id')
}

export interface CompiledRoute {
  path: string;
  segments: RouteSegment[];
  component: React.ComponentType<any>;
  loader?: (args: any) => unknown;
  searchSchema: import("zod").ZodType | null;
}

/** Parse a route path ('/docs/:slug*', '/users/:id?') into typed segments */
export function compileRoute(path: string): RouteSegment[] {
  return path
    .split("/")
    .filter(Boolean)
    .map((seg): RouteSegment => {
      if (seg === "*") return { type: "catch-all", value: "*" };
      if (seg.startsWith(":") && seg.endsWith("*")) return { type: "catch-all", value: seg.slice(1, -1) }; // ':slug*' → 'slug'
      if (seg.startsWith(":") && seg.endsWith("?")) return { type: "optional", value: seg.slice(1, -1) }; // ':id?'   → 'id'
      if (seg.startsWith(":")) return { type: "dynamic", value: seg.slice(1) }; // ':id'    → 'id'
      return { type: "static", value: seg };
    });
}

// Higher rank = more specific. "No segment here" sits between dynamic and
// optional, so '/users' beats '/users/:id?' and '/docs' beats '/docs/:slug*'.
const RANK = { static: 4, dynamic: 3, end: 2, optional: 1, "catch-all": 0 } as const;

/** Sort comparator: more specific routes first */
export function compareRoutes(a: RouteSegment[], b: RouteSegment[]): number {
  const len = Math.max(a.length, b.length);
  for (let i = 0; i < len; i++) {
    const ra = RANK[a[i]?.type ?? "end"];
    const rb = RANK[b[i]?.type ?? "end"];
    if (ra !== rb) return rb - ra;
  }
  return 0; // Identical shapes (e.g. '/posts/:id' vs '/posts/:slug') — the plugin warns
}

/** Match a pathname against compiled, pre-sorted routes */
export function matchRoute(
  pathname: string,
  compiledRoutes: CompiledRoute[],
): { route: CompiledRoute; params: Record<string, string> } | null {
  const pathSegments = pathname.split("/").filter(Boolean).map(decodeURIComponent);

  // Routes are pre-sorted most-specific-first, so the first match wins
  for (const route of compiledRoutes) {
    const params = tryMatch(route.segments, pathSegments);
    if (params !== null) {
      return { route, params };
    }
  }

  return null;
}

function tryMatch(routeSegments: RouteSegment[], pathSegments: string[]): Record<string, string> | null {
  const params: Record<string, string> = {};

  for (let i = 0; i < routeSegments.length; i++) {
    const routeSeg = routeSegments[i];

    if (routeSeg.type === "catch-all") {
      // Catch-all consumes the rest of the path — at least one segment,
      // matching the [...slug] convention ('/docs' alone doesn't match)
      if (i >= pathSegments.length) return null;
      params[routeSeg.value] = pathSegments.slice(i).join("/");
      return params;
    }

    if (i >= pathSegments.length) {
      // Path is shorter than route — only a trailing optional may be missing
      if (routeSeg.type === "optional") continue;
      return null;
    }

    if (routeSeg.type === "static") {
      if (routeSeg.value !== pathSegments[i]) return null;
    } else {
      params[routeSeg.value] = pathSegments[i];
    }
  }

  // If path has more segments than route (and no catch-all), no match
  if (pathSegments.length > routeSegments.length) return null;

  return params;
}
```

Optional segments are only allowed in the last position — the route plugin rejects `/users/:id?/posts` at discovery time, because "missing in the middle" has no unambiguous meaning.

### Route compilation in the virtual module

The route plugin pre-compiles and sorts routes at code generation time, not at runtime. The generated module is code, not data — components and loaders are module references, so we can't `JSON.stringify` the route objects (functions would silently disappear). Only the segments are serialized; everything else is emitted as expressions:

```typescript
// In the load() hook
const compiled = routes
  .map((r, i) => ({ r, i, segments: compileRoute(r.path) }))
  .sort((a, b) => compareRoutes(a.segments, b.segments));

const imports = routes.map((r, i) => `import * as RouteMod${i} from ${JSON.stringify(r.componentPath)}`);

const entries = compiled.map(
  ({ r, i, segments }) => `  {
    path: ${JSON.stringify(r.path)},
    segments: ${JSON.stringify(segments)},
    component: RouteMod${i}.default,
    loader: RouteMod${i}.loader,
    searchSchema: RouteMod${i}.searchParams ?? null,
  }`,
);

return `${imports.join("\n")}\n\nexport const routes = [\n${entries.join(",\n")}\n]`;
```

Now `/posts/new` always matches before `/posts/:id`: the first segments tie (both static), and at the second segment static (`new`) outranks dynamic (`:id`).

## Type-safe search params

TanStack Router's standout feature is type-safe search params — URL query strings validated at compile time. When you navigate to `/products?category=shoes&sort=price`, the `category` and `sort` parameters are typed, validated, and defaulted.

### Defining search param schemas per route

```tsx title="src/pages/products.tsx"
import { z } from "zod";
import { defineLoader } from "eigen/helpers";
import type { PageProps } from "eigen/types";
import { db } from "../lib/db";

// Define the search params schema for this route (Zod 4)
export const searchParams = z.object({
  category: z.string().optional(),
  sort: z.enum(["price", "name", "rating"]).default("name"),
  page: z.coerce.number().int().min(1).default(1), // z.coerce converts "3" → 3
  // Not z.coerce.boolean(): Boolean("false") is true. stringbool parses
  // "true"/"false"/"1"/"0"/"yes"/"no" the way a query string means them.
  inStock: z.stringbool().default(false),
});

export type SearchParams = z.infer<typeof searchParams>;

// SQL can't bind identifiers, so ORDER BY comes from a whitelist, never from a parameter
const ORDER_BY = { price: "price", name: "name", rating: "rating DESC" } as const;

export const loader = defineLoader("/products", async ({ search }) => {
  // search is typed as SearchParams — validated and defaulted
  const products = await db.query(
    `SELECT *, count(*) OVER () AS total_count FROM products
     WHERE ($1::text IS NULL OR category = $1)
       AND (NOT $2 OR in_stock)
     ORDER BY ${ORDER_BY[search.sort]}
     LIMIT 20 OFFSET $3`,
    [search.category ?? null, search.inStock, (search.page - 1) * 20],
  );
  return {
    products: products.rows,
    total: Number(products.rows[0]?.total_count ?? 0),
  };
});

export default function ProductsPage({ data, search }: PageProps<"/products"> & { search: SearchParams }) {
  return (
    <div>
      <h1>Products {search.category ? `— ${search.category}` : ""}</h1>
      <p>
        Sorted by {search.sort}, page {search.page}
      </p>
      {/* ... */}
    </div>
  );
}
```

### Parsing search params in the router

The route plugin reads the optional `searchParams` export through the same namespace import as everything else — that's the `searchSchema: RouteMod${i}.searchParams ?? null` line in the generated routes module above. Part 7's client-stripping transform removes `loader` but leaves `searchParams` alone, so the schema ships to the browser, where the router needs it.

One shared function parses and validates search params — the router calls it on every navigation, and `runRoute` (Part 14) calls it on the server with `new URL(request.url)` before invoking the loader, passing the result as a third loader argument, `search`, next to `params` and `ctx`:

```typescript title="packages/eigen/router/search.ts"
import type { z } from "zod";

export function parseSearchParams(url: URL, schema: z.ZodType | null): Record<string, unknown> {
  if (!schema) return {};

  const raw = Object.fromEntries(url.searchParams);
  const result = schema.safeParse(raw);
  if (result.success) return result.data as Record<string, unknown>;

  // On validation failure, don't crash: drop the offending keys and
  // re-parse, so each bad field falls back to its default.
  console.warn("Search param validation failed:", result.error.issues);
  const bad = new Set(result.error.issues.map((issue) => String(issue.path[0])));
  const cleaned = Object.fromEntries(Object.entries(raw).filter(([key]) => !bad.has(key)));
  const retry = schema.safeParse(cleaned);
  return retry.success ? (retry.data as Record<string, unknown>) : {};
}
```

Because the loader now depends on the query string, the client must send it too: the `/_eigen/data` request from Part 22's intercept handler uses `path=${encodeURIComponent(url.pathname + url.search)}`, and the data endpoint builds its `Request` from that full path.

### Type-safe navigation with search params

The `Link` component extends to accept typed search params. `params` stays required exactly when the route has params, and `search` takes the _parsed_ shape (numbers as numbers, booleans as booleans), all optional — `Link` serializes it to strings:

```tsx title="packages/eigen/router.tsx"
import type { RoutePaths, RouteParamsMap, SearchParamsMap } from "eigen/route-types";

type ParamsProp<T extends RoutePaths> =
  RouteParamsMap[T] extends Record<string, never> ? { params?: never } : { params: RouteParamsMap[T] };

type LinkProps<T extends RoutePaths> = ParamsProp<T> & {
  to: T;
  search?: Partial<SearchParamsMap[T]>; // ← NEW: typed search params per route
  preload?: "intent" | "viewport" | "render" | "none";
  children: React.ReactNode;
};

export function buildHref(to: string, params?: Record<string, string>, search?: Record<string, unknown>): string {
  let href = to;
  if (params) {
    // ':id' → value, ':slug*' → 'a/b/c', ':id?' → value or nothing
    href = href.replace(/\/:(\w+)([*?]?)/g, (_, key: string, mod: string) => {
      const value = params[key];
      if (value === undefined) return mod === "?" ? "" : `/:${key}`;
      return mod === "*" ? "/" + value.split("/").map(encodeURIComponent).join("/") : "/" + encodeURIComponent(value);
    });
  }
  if (search) {
    const qs = new URLSearchParams();
    for (const [key, value] of Object.entries(search)) {
      if (value !== undefined) qs.set(key, String(value));
    }
    const searchString = qs.toString();
    if (searchString) href += `?${searchString}`;
  }
  return href;
}

// Usage — fully type-checked:
<Link to="/products" search={{ category: "shoes", sort: "price" }}>
  Shoes by price
</Link>;

// Type error: 'invalid' is not assignable to 'price' | 'name' | 'rating'
// <Link to="/products" search={{ sort: 'invalid' }}>Oops</Link>
```

### Generating `SearchParamsMap`

The route plugin doesn't try to translate zod schemas into TypeScript by hand. It points the declaration file at the schema itself and lets zod's own `output` type do the work. For routes without a `searchParams` export, it writes `Record<string, never>`:

```typescript title="node_modules/.eigen/eigen-routes.d.ts"
declare module "eigen/route-types" {
  export type RoutePaths = "/" | "/products" | "/posts/:id";

  export interface RouteParamsMap {
    "/": Record<string, never>;
    "/products": Record<string, never>;
    "/posts/:id": { id: string };
  }

  export interface SearchParamsMap {
    "/": Record<string, never>;
    // Path is relative to node_modules/.eigen/
    "/products": import("zod").output<typeof import("../../src/pages/products").searchParams>;
    // → { category?: string; sort: 'price' | 'name' | 'rating'; page: number; inStock: boolean }
    "/posts/:id": Record<string, never>;
  }
}
```

The loader's `search` argument is `SearchParamsMap[TPath]` (fully defaulted); `Link`'s `search` prop is `Partial<SearchParamsMap[T]>`. `defineLoader` (Part 5, updated in Part 14) gains the field:

```typescript title="packages/eigen/helpers.ts"
export function defineLoader<TPath extends RoutePaths, TData>(
  _path: TPath,
  fn: (args: {
    params: RouteParamsMap[TPath];
    ctx: EigenContext;
    search: SearchParamsMap[TPath]; // ← NEW
  }) => Promise<TData> | TData,
) {
  return fn;
}
```

## Catch-all and optional segments

The file convention extends to support catch-all and optional segments:

```
src/pages/
├── docs/[...slug].tsx      → /docs/:slug* (catch-all, one or more segments)
├── users/[[id]].tsx        → /users/:id?  (optional param)
```

Part 2's `fileToRoute` only knows `[name]`, so it gains two replacements that run _before_ the plain-param one (otherwise `[[id]]` would become `[:id]`):

```typescript
const name = filename
  .replace(/\.tsx$/, "")
  .replace(/\[\.\.\.(\w+)\]/g, (_, p: string) => {
    paramNames.push(p);
    return `:${p}*`;
  })
  .replace(/\[\[(\w+)\]\]/g, (_, p: string) => {
    paramNames.push(p);
    return `:${p}?`;
  })
  .replace(/\[(\w+)\]/g, (_, p: string) => {
    paramNames.push(p);
    return `:${p}`;
  });
```

The virtual module generates the appropriate segments:

```typescript
// /docs/:slug* → catch-all route
{ path: '/docs/:slug*', segments: [
  { type: 'static', value: 'docs' },
  { type: 'catch-all', value: 'slug' },
]}

// /users/:id? → optional param
{ path: '/users/:id?', segments: [
  { type: 'static', value: 'users' },
  { type: 'optional', value: 'id' },
]}
```

The param types reflect this. The declaration generator writes these entries from the compiled segments (it knows which params are catch-all or optional), rather than deriving them from the path string with `RouteParams<T>`:

```typescript
// RouteParamsMap entry for catch-all
'/docs/:slug*': { slug: string }  // "guides/getting-started/install"

// RouteParamsMap entry for optional
'/users/:id?': { id?: string }    // undefined if visiting /users
```

## Route preloading

Preloading fetches a route's loader data _before_ the user navigates, so the page appears instantly on click:

```typescript title="packages/eigen/router/preload.ts"
// Keyed by the full href (pathname + search) — '/posts/42', '/products?sort=price'
const preloadCache = new Map<string, Promise<unknown>>();

export function preloadRoute(href: string): void {
  if (preloadCache.has(href)) return;

  const promise = fetch(`/_eigen/data?path=${encodeURIComponent(href)}`).then((res) => {
    if (!res.ok) throw new Error(`Preload failed: ${res.status}`);
    return res.json();
  });

  // A failed preload must not poison the cache — the click will refetch
  promise.catch(() => preloadCache.delete(href));
  preloadCache.set(href, promise);

  // Clear after 30 seconds (stale data)
  setTimeout(() => preloadCache.delete(href), 30_000);
}

/** Take (and remove) a preloaded result, so each preload is used at most once */
export function takePreloadedData(href: string): Promise<unknown> | undefined {
  const promise = preloadCache.get(href);
  preloadCache.delete(href);
  return promise;
}
```

Preloading only helps if navigation _uses_ the preloaded data. The intercept handler from Part 22 checks the cache before going to the network:

```typescript title="packages/eigen/router.tsx (intercept handler)"
event.intercept({
  async handler() {
    const href = url.pathname + url.search;
    const newData = await (takePreloadedData(href) ??
      fetch(`/_eigen/data?path=${encodeURIComponent(href)}`, { signal: event.signal }).then((res) => res.json()));

    startTransition(() => {
      setLocation({ pathname: url.pathname, search: url.search });
      setData(newData);
    });
  },
});
```

(The router now keeps `search` in state alongside `pathname`, and passes `parseSearchParams(url, match.route.searchSchema)` to the page as its `search` prop.)

Preloading strategies (configurable per-link):

```tsx
// Preload on hover (default)
<Link to="/products" preload="intent">Products</Link>

// Preload when visible in viewport
<Link to="/about" preload="viewport">About</Link>

// Preload immediately (for critical navigation paths)
<Link to="/dashboard" preload="render">Dashboard</Link>

// No preloading
<Link to="/settings" preload="none">Settings</Link>
```

The `Link` component builds the real href first (a route pattern like `/posts/:id` isn't fetchable), then adds listeners based on the strategy:

```tsx title="packages/eigen/router.tsx"
import { useEffect, useRef } from "react";
import { preloadRoute } from "./router/preload";

export function Link<T extends RoutePaths>(props: LinkProps<T>) {
  const { to, params, search, preload = "intent", children } = props;
  const href = buildHref(
    to,
    params as Record<string, string> | undefined,
    search as Record<string, unknown> | undefined,
  );
  const ref = useRef<HTMLAnchorElement>(null);

  useEffect(() => {
    if (preload === "render") {
      preloadRoute(href);
    } else if (preload === "viewport") {
      const observer = new IntersectionObserver(([entry]) => {
        if (entry.isIntersecting) {
          preloadRoute(href);
          observer.disconnect();
        }
      });
      if (ref.current) observer.observe(ref.current);
      return () => observer.disconnect();
    }
  }, [href, preload]);

  const onIntent = preload === "intent" ? () => preloadRoute(href) : undefined;

  return (
    <a ref={ref} href={href} onMouseEnter={onIntent} onFocus={onIntent}>
      {children}
    </a>
  );
}
```

## The `URLPattern` API

The `URLPattern` API is a web standard that provides built-in pattern matching for URLs. It has been Baseline since September 2025 (Chrome, Edge, Firefox and Safari all ship it), and it's a global in Node 24+ and Deno, so the same matcher can run on both sides:

```typescript
// Using URLPattern for route matching
const pattern = new URLPattern({ pathname: "/posts/:id" });
const result = pattern.exec({ pathname: "/posts/42" });
// result.pathname.groups = { id: '42' }
```

The framework could use `URLPattern` as the per-route matching engine (its syntax already covers `:id`, `:id?` and `:slug*`), with a polyfill for older browsers. What it doesn't do is _ranking_: `URLPattern` answers "does this one pattern match?", so you still sort routes with `compareRoutes` and test them in order. This is another example of the browser platform absorbing framework responsibilities — partially.

## What to observe

1. **Create routes that overlap** (`/posts/new` and `/posts/:id`). Navigate to `/posts/new` and confirm the static route wins: at the second segment, static outranks dynamic.

2. **Add search params to a route.** Navigate with different query strings and watch the search params get validated and defaulted. Invalid values (`?sort=bogus`) fall back to that field's default while valid ones are kept. Try `?inStock=false` and confirm it parses to `false`.

3. **Hover over a `Link` with `preload="intent"`.** Watch the Network tab — the loader data is fetched on hover, before you click. When you click, no second `/_eigen/data` request is made: the intercept handler takes the preloaded promise.

4. **Check type safety** — in your editor, type `<Link to="/products" search={{ sort: ` and confirm autocomplete shows `'price' | 'name' | 'rating'`.

## Key insight

The router is where type safety, performance, and UX converge. Ranked matching ensures correctness. Search param schemas ensure data integrity. Preloading eliminates perceived latency. And the type system — generated by the route plugin from the filesystem — gives developers compile-time guarantees over paths, params, and search params.

This is the layer where TanStack Router differentiates itself most. Its fully-inferred type system for routes, params, search params, and loader data is generated by `@tanstack/router-plugin/vite` — the same pattern we've built throughout this series, pushed to its most sophisticated expression.
