## From path aliases to workspaces

Since [Part 1](/01-bare-vite-spa), the framework's source has lived flat in `packages/eigen/*.ts(x)` and been imported as `eigen/<name>`. Two separate mechanisms make that work, because TypeScript and Vite resolve imports independently — and since Part 1, every module has needed **both, one pair per module**. Part 1 added the first pair for `eigen/types`: a `paths` entry so the type checker finds it, and a `resolve.alias` entry so Vite does:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "paths": {
      "eigen/types": ["./packages/eigen/types.ts"],
      "eigen/match-route": ["./packages/eigen/match-route.ts"],
      "eigen/serialize": ["./packages/eigen/serialize.ts"]
      // ...one entry per module
    }
  }
}
```

```typescript title="vite.config.ts"
resolve: {
  alias: {
    'eigen/types': resolve(__dirname, 'packages/eigen/types.ts'),
    'eigen/match-route': resolve(__dirname, 'packages/eigen/match-route.ts'),
    'eigen/serialize': resolve(__dirname, 'packages/eigen/serialize.ts'),
    // ...and every pair added along the way:
    // eigen/helpers, eigen/router, eigen/middleware, eigen/run-route, eigen/server,
    // eigen/server-fn-client, eigen/server-fn-endpoint, eigen/cookies, eigen/adapter,
    // eigen/auth, eigen/auth/session, eigen/csrf, eigen/query, eigen/image, ...
  },
},
```

[Part 3](/03-server-side-rendering) added the `eigen/match-route` and `eigen/serialize` pairs, and nearly every part since has added more. Both halves are needed because Vite doesn't read tsconfig `paths` unless you opt in with `resolve.tsconfigPaths: true` (it defaults to `false`). Every new module meant two more lines in two files — and neither one describes how the code is consumed after publishing. A real monorepo replaces both with ordinary package resolution.

The one import that never went through an alias is the plugin itself. `vite.config.ts` is bundled and run by Node _before_ `resolve.alias` exists, so until now it imported the plugin by file path: `import eigen from './packages/eigen/plugin'`. That changes in Step 3.

### Step 1: Add `pnpm-workspace.yaml`

```yaml title="pnpm-workspace.yaml"
packages:
  - "packages/*"
  - "apps/*"
```

Move the app (`src/`, `index.html`, `vite.config.ts`) into `apps/demo/`. `packages/eigen/` stays where it is.

### Step 2: Give `eigen` a `package.json`

```json title="packages/eigen/package.json"
{
  "name": "eigen",
  "version": "0.1.0",
  "type": "module",
  "scripts": {
    "build": "tsdown",
    "dev": "tsdown --watch",
    "typecheck": "tsc --noEmit"
  },
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    },
    "./typescript-plugin": {
      "types": "./dist-cjs/typescript-plugin.d.cts",
      "require": "./dist-cjs/typescript-plugin.cjs"
    },
    "./auth/session": {
      "types": "./dist/auth-session.d.ts",
      "default": "./dist/auth-session.js"
    },
    "./theme.css": "./theme.css",
    "./package.json": "./package.json",
    "./*": {
      "types": "./dist/*.d.ts",
      "default": "./dist/*.js"
    }
  },
  "bin": {
    "eigen": "./dist/cli/index.js"
  },
  "files": ["dist", "dist-cjs", "theme.css"],
  "peerDependencies": {
    "react": "^19.0.0",
    "react-dom": "^19.0.0",
    "vite": "^8.0.0"
  },
  "devDependencies": {
    "tsdown": "^0.23.0",
    "typescript": "^6.0.0"
  }
}
```

A few details in that `exports` map matter:

- **The `"./*"` pattern** maps every `eigen/<name>` — including nested ones like `eigen/auth/session` and `eigen/adapters/netlify` — to its built file. Because the build mirrors the source tree one file per module (below), the map is complete by construction: a new module needs no new `exports` entry. Exact keys take precedence over the pattern — which is how `eigen/auth/session` keeps pointing at `auth-session.tsx`, the one alias whose name doesn't match its file path.
- **`"types"` comes first** in every condition object. Conditions are matched in order, and TypeScript stops at the first one it recognizes; `types` after `default` only works by accident (when the `.d.ts` happens to sit next to the `.js`), and tools like [publint](https://publint.dev) flag it.
- **`./typescript-plugin` is CommonJS-only** (`require`), because `tsserver` loads plugins with `require()` ([Part 39](/39-developer-experience-cli#plugin-structure)).
- **`bin`** makes `npx eigen generate ...` from Part 39 work.
- **Virtual modules aren't exported.** `eigen/routes`, `eigen/server-fns`, and `eigen/styles` are resolved by the `eigen()` plugin's `resolveId` before package resolution happens, so they never reach the `exports` map.

### Step 3: Replace aliases with the workspace protocol

Update the app's `package.json` to reference the workspace package:

```json title="apps/demo/package.json"
{
  "name": "eigen-demo",
  "private": true,
  "type": "module",
  "dependencies": {
    "eigen": "workspace:*",
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  },
  "devDependencies": {
    "vite": "^8.0.0"
  }
}
```

Then delete the `eigen/*` entries from `resolve.alias` in `vite.config.ts` and from `paths` in `tsconfig.json`. **This is also the moment the config's plugin import changes** from the file path to the package name:

```typescript title="apps/demo/vite.config.ts"
import { defineConfig } from "vite";
import eigen from "eigen/plugin"; // was: './packages/eigen/plugin'

export default defineConfig({
  plugins: [eigen()],
});
```

Now `import eigen from 'eigen/plugin'` resolves through Node's package resolution — pnpm symlinks `apps/demo/node_modules/eigen` to `packages/eigen` — the same way it will work for end users after publishing.

Because `exports` points at `dist/`, the package has to be built before the app can import it. In development, `tsdown --watch` keeps `dist/` current, and Turborepo (below) starts it alongside Vite. Since the workspace package is a symlink outside `node_modules`, Vite treats it as source: it watches `dist/` and isn't pre-bundled.

<Callout type="info" title="Why workspaces over path aliases?">
  Path aliases let you import code as if it were a package, but they don't validate the `exports` map, don't test
  package resolution, and don't catch missing dependencies. With workspaces, you're developing against the same
  resolution strategy your users will experience.
</Callout>

### One plugin change: keep `eigen` away from the dependency optimizer

Once `eigen` is a real package, the code inside it imports virtual modules (`eigen/routes`, `eigen/server-fns`) that only the `eigen()` plugin can resolve. Two Vite features would otherwise bypass plugins for a package in `node_modules`: dependency pre-bundling on the client, and SSR externalization (Node `import()`s the package directly). Add both opt-outs to the `config()` hook from [Part 11](/11-framework-plugin):

```typescript title="packages/eigen/plugin.ts (inside config())"
optimizeDeps: {
  exclude: ['eigen'], // don't pre-bundle: its imports need our resolveId
},
ssr: {
  noExternal: ['eigen'], // transform it through the plugin pipeline on the server
},
```

In the monorepo this is invisible (linked workspace packages are already treated as source), which is exactly why it's easy to miss until the first user installs from npm.

### Shared TypeScript config

```json title="tsconfig.base.json"
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",

    "strict": true,
```

## Build pipeline with `tsdown`

The demo app uses Vite (with Rolldown) to bundle the application. But `packages/eigen` is a **library** — it needs to be compiled to JavaScript with TypeScript declarations so other projects can consume it. [`tsdown`](https://tsdown.dev) does this.

### Why tsdown?

tsdown is the Rolldown project's library bundler — the same engine Vite 8 uses, configured for libraries: `dependencies` and `peerDependencies` stay external by default (React, Vite, and friends are resolved by the consuming app), declaration files are generated alongside the JavaScript, and an **unbundle** mode emits one output file per source file instead of a single bundle. It's also the successor to `tsup`, whose README now says it is no longer actively maintained and recommends tsdown; the configuration is close enough that migrating is mostly renaming the file.

### `tsdown` configuration

```typescript title="packages/eigen/tsdown.config.ts"
import { defineConfig } from "tsdown";

export default defineConfig([
  {
    // Every module is a public entry: eigen/<name> → dist/<name>.js
    entry: [
      "**/*.{ts,tsx}",
      "!**/__tests__/**",
      "!**/*.d.ts",
      "!typescript-plugin.ts",
      "!tsdown.config.ts",
      "!{node_modules,dist,dist-cjs}/**",
    ],
    unbundle: true, // mirror the source tree — matches the "./*" export pattern
    format: "esm",
    dts: true, // dist/<name>.d.ts next to each file
    fixedExtension: false, // ".js" / ".d.ts" (the package is "type": "module")
    outDir: "dist",
    copy: ["*.d.ts"], // ambient declarations (virtual modules, globals) ship as-is
  },
  {
    // tsserver plugins are loaded with require(): build this one as CommonJS
    entry: ["typescript-plugin.ts"],
    format: "cjs",
    dts: true,
    fixedExtension: true, // typescript-plugin.cjs + .d.cts
    outDir: "dist-cjs", // separate dir, so neither config's clean step touches the other
  },
]);
```

tsdown cleans each config's `outDir` before building (`clean` defaults to `true`), which is why the CommonJS build gets its own `dist-cjs/` instead of sharing `dist/`. A single `export default` in a CJS entry becomes `module.exports = init`, which is the shape `tsserver` expects. tsdown can also check the result for you: `publint: true` validates the `exports` map against the files that were actually built.

`create-eigen` and `eslint-plugin-eigen` get small configs of their own — one entry each (`src/index.ts`), ESM, `dts: true` for the ESLint plugin.

## Turborepo orchestration

With multiple packages, you need a task runner that understands the dependency graph — building `eigen` before the demo app, type-checking everything in parallel, caching results.

### Setup

```bash
pnpm add -Dw turbo
```

Turborepo requires the root `package.json` to declare the package manager:

```json title="package.json (root)"
{
  "name": "eigen-monorepo",
  "private": true,
  "packageManager": "pnpm@12.9.1",
  "scripts": {
    "build": "turbo run build",
    "typecheck": "turbo run typecheck",
    "test": "turbo run test",
    "lint": "turbo run lint",
    "dev": "turbo run dev --filter=eigen-demo..."
  }
}
```

`--filter=eigen-demo...` selects the demo app _and its workspace dependencies_, so `pnpm dev` starts `tsdown --watch` in `packages/eigen` and `vite` in `apps/demo` together. (Filters match package names; a directory filter would be written `--filter=./apps/demo...`.)

```json title="turbo.json"
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", "dist-cjs/**"]
    },
    "typecheck": {
      "dependsOn": ["^build"]
    },
    "test": {
      "dependsOn": ["build"]
    },
    "lint": {},
    "dev": {
      "dependsOn": ["^build"],
      "cache": false,
      "persistent": true
    }
  }
}
```

`dev` depends on `^build` so that `packages/eigen/dist/` exists before Vite starts; from then on `tsdown --watch` keeps it current.

### How the dependency graph works

```
turbo run build

  1. eigen                → tsdown (no workspace deps)
     eslint-plugin-eigen  → tsdown (no workspace deps)
     create-eigen         → tsdown (no workspace deps)
  2. eigen-demo           → vite build (depends on eigen)
```

`"dependsOn": ["^build"]` means "build my workspace dependencies first." Turbo figures out the order automatically from `package.json` dependencies, and runs everything in step 1 in parallel.

### Local and remote caching

Turbo caches task outputs. If nothing in `packages/eigen/` has changed since the last build, `turbo run build` replays it from cache:

```
$ turbo run build
eigen:build: cache hit, replaying logs
create-eigen:build: cache hit, replaying logs
eigen-demo:build: cache miss, executing
```

For CI, enable remote caching so builds are shared across machines. Signing artifacts protects against cache poisoning; it requires a `TURBO_REMOTE_CACHE_SIGNATURE_KEY` environment variable:

```json title="turbo.json (excerpt)"
{
  "remoteCache": {
    "signature": true
  }
}
```

## Versioning with changesets

`@changesets/cli` manages semver versioning across packages — it tracks what changed, bumps versions, generates changelogs, and coordinates multi-package releases.

### Setup

```bash
pnpm add -Dw @changesets/cli && pnpm changeset init
```

`changeset init` asks a few questions (changelog style, auto-commit, public or restricted access, base branch) and writes `.changeset/config.json`:

```json title=".changeset/config.json"
{
  "$schema": "https://unpkg.com/@changesets/config@4.0.1/schema.json",
  "baseBranch": "main",
  "access": "public",
  "format": "auto",
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "ignore": [],
  "fixed": [["eigen", "create-eigen", "eslint-plugin-eigen"]],
  "linked": [],
  "updateInternalDependencies": "patch"
}
```

Private packages such as `eigen-demo` aren't versioned (the changesets v3 default), so only the three published packages matter here. The `"fixed"` group makes the three packages version together: when `eigen` gets a minor bump, so do `create-eigen` and `eslint-plugin-eigen` — even if nothing changed in them — and all three always share one version number. That's what you want when users install them side by side (`create-eigen@0.3.0` scaffolds a project with `eigen@^0.3.0` and `eslint-plugin-eigen@^0.3.0`).

`"linked"` is the looser alternative: linked packages share a version number only among the packages that are actually released together. If only `eigen` has a changeset, only `eigen` is bumped; when several linked packages are bumped in the same release, they all move to the highest resulting version.

### The changeset workflow

**During development** — when you make a change worth noting:

```bash
pnpm changeset
```

This prompts:

1. Which packages changed? → `eigen`
2. Semver bump? → `minor` (new feature)
3. Summary? → "Add CSS Modules type generation"

It creates a markdown file in `.changeset/`:

```markdown title=".changeset/cool-lions-dance.md"
---
"eigen": minor
---

Add CSS Modules type generation
```

**At release time** — usually done by CI (below), but the commands are:

```bash
# Consume changesets: bump versions, update changelogs
# (exits with an error if there are no pending changesets)
pnpm changeset version

# Review the changes
git diff

# Commit and publish
git add -A && git commit -m "chore: release v0.2.0"
pnpm changeset publish
```

`changeset version` reads all pending changeset files, determines the highest bump for each package (applying the `fixed` group), updates `package.json` versions, and writes `CHANGELOG.md` entries. `changeset publish` publishes every package whose current version isn't on the registry yet, using your workspace's package manager (`pnpm publish` here, which runs the `prepublishOnly` script), and tags the release in git.

## Publishing to npm

### Pre-publish checks

Add a `prepublishOnly` script that runs the full validation pipeline:

```json title="packages/eigen/package.json"
{
  "scripts": {
    "build": "tsdown",
    "typecheck": "tsc --noEmit",
    "prepublishOnly": "pnpm run build && pnpm run typecheck"
  }
}
```

### Dry-run verification

Always dry-run before publishing:

```bash
cd packages/eigen && pnpm publish --dry-run
```

This shows exactly what files will be published and the package size. Check for:

- Only `dist/`, `dist-cjs/`, `theme.css`, `package.json`, and the README — no `.ts` sources
- No test files or fixtures
- No `.env` or credentials
- Reasonable package size

### Trusted publishing and provenance

As of 2026, the recommended way to publish from CI is **trusted publishing**: instead of storing a long-lived npm token as a repository secret, you tell npm which GitHub Actions workflow may publish each package. At publish time, the npm CLI exchanges the workflow's short-lived OIDC token for a one-off publish credential.

Trusted publishing also generates **provenance** automatically — a signed attestation linking the published version to the repository, commit, and workflow run that built it — so there's no `--provenance` flag to remember. npm's requirements:

- npm CLI **11.5.1 or later** and Node **22.14.0 or later** in the publishing job
- `permissions: id-token: write` in the workflow
- A trusted publisher configured on npmjs.com for each package (package settings → _Trusted Publisher_ → GitHub Actions → owner, repository, and workflow file name, e.g. `release.yml`)

Trusted publishers are configured on a package that already exists, so the very first version of each package is published once by hand (`npm login`, then `pnpm publish` in the package directory). After that, revoke any tokens you created; CI no longer needs one.

### Scoped vs. unscoped

|                  | Scoped (`@your-org/eigen`)                                                                 | Unscoped (`eigen`)                       |
| ---------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------- |
| **Availability** | Always available within a scope you own                                                    | Must be unique across the whole registry |
| **Import style** | `import eigen from '@your-org/eigen/plugin'`                                               | `import eigen from 'eigen/plugin'`       |
| **npm access**   | Private by default; publish with `"access": "public"` (set in the changesets config above) | Public                                   |

For a framework, unscoped is typical (Next.js is `next`, not `@vercel/next`). For a company or org, scoped prevents naming conflicts — and in practice, short unscoped names are usually taken. (`eigen` itself is already taken on npm; a real release of this series' framework would need a scope or a different name. The tutorial keeps `eigen` for readability.)

## GitHub Actions release workflow

Automate the release process with a GitHub Actions workflow:

```yaml title=".github/workflows/release.yml"
name: Release

on:
  push:
    branches: [main]

concurrency: ${{ github.workflow }}-${{ github.ref }}

permissions:
  contents: write # commit version bumps, push tags
  pull-requests: write # open the release PR
  id-token: write # OIDC token for npm trusted publishing

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: pnpm/action-setup@v6 # reads "packageManager" from package.json
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          registry-url: "https://registry.npmjs.org"
          cache: pnpm

      # Trusted publishing needs npm >= 11.5.1
      - run: npm install -g npm@latest

      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo run build typecheck test lint

      - name: Create release PR or publish
        uses: changesets/action@v2
        with:
          version-script: pnpm changeset version
          publish-script: pnpm changeset publish
          commit-message: "chore: release"
          pr-title: "chore: release"
```

There's no `NPM_TOKEN` secret: the `id-token: write` permission is what authenticates the publish. In the repository settings (_Actions → General_), also allow GitHub Actions to create pull requests, or the action can't open the release PR.

This workflow:

1. Runs the full build/typecheck/test/lint pipeline
2. If there are pending changesets → creates a "chore: release" PR that bumps versions and updates changelogs
3. When that PR is merged → publishes the updated packages to npm, with provenance

## Key insight

The monorepo was hiding in plain sight. From [Part 1](/01-bare-vite-spa), `packages/eigen/` behind `eigen/*` aliases was a workspace waiting to be formalized. The conversion is mechanical — add `pnpm-workspace.yaml`, give the package a `package.json` with an `exports` map, replace the aliases with the workspace protocol. Publishing is the natural conclusion: `tsdown` compiles the library, `changesets` manages versions, and trusted publishing from CI makes it real — with provenance proving where it came from. The loop is closed — you built a framework from scratch, and now anyone can `npm install` it.

**This concludes the Eigen Series.** Over 41 parts (0–40), you've built a fully-featured React meta-framework on top of Vite's plugin API — from a bare SPA through SSR, streaming, server functions, React Server Components, and every modern web feature in between. The framework isn't magic anymore. It's just code generation, coordinated by plugins.
