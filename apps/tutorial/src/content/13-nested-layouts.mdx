Now we'll implement nested layouts — a `layout.tsx` convention where each directory level can wrap its child routes in shared UI, like Next.js App Router's layout system._

## The design goal

Next.js App Router's layout convention is one of its most powerful ideas. Each directory segment can have a `layout.tsx` that wraps all routes beneath it:

<Files>
  <Folder name="src" defaultOpen>
    <Folder name="pages" defaultOpen>
      <File name="layout.tsx" comment="Root layout (wraps every route)" />
      <File name="Home.tsx" comment="/" />
      <File name="About.tsx" comment="/about" />
      <Folder name="dashboard" defaultOpen>
        <File name="layout.tsx" comment="Dashboard layout (sidebar)" />
        <File name="index.tsx" comment="/dashboard (Part 12's Dashboard.tsx, moved here)" />
        <File name="settings.tsx" comment="/dashboard/settings" />
        <Folder name="analytics" defaultOpen>
          <File name="layout.tsx" comment="Analytics sub-layout (tabs)" />
          <File name="index.tsx" comment="/dashboard/analytics" />
        </Folder>
      </Folder>
    </Folder>
  </Folder>
</Files>

Page files follow the same naming rules as [Part 2](/02-route-discovery-plugin)'s `fileToRoute`: `Home.tsx` and `index.tsx` map to their directory's path, other files add a lowercased segment, and `[param]` becomes `:param`. The only new rule: a file named `layout.tsx` is never a page.

When a user visits `/dashboard/analytics`, the rendered component tree is:

```
<RootLayout>
  <DashboardLayout>
    <AnalyticsLayout>
      <AnalyticsPage />
    </AnalyticsLayout>
  </DashboardLayout>
</RootLayout>
```

Each layout persists across sibling route navigations — navigating from `/dashboard/settings` to `/dashboard/analytics` doesn't remount `DashboardLayout`. As we'll see, that property doesn't come for free: it depends on _how_ the tree is assembled.

## Extending route discovery

The route plugin from Part 2 discovers page files as a flat list. Now it also needs to discover layout files and know which directory each page lives in. A recursive scan produces a tree:

```typescript title="packages/eigen/plugins/route-tree.ts"
import { readdirSync } from "node:fs";
import { join } from "node:path";
import { fileToRoute } from "./eigen-routes";

export interface LayoutEntry {
  /** URL path of the directory this layout wraps (e.g. '/dashboard') */
  path: string;
  /** Import URL for the virtual module (e.g. '/src/pages/dashboard/layout.tsx') */
  url: string;
  /** Absolute file path, for generated type declarations */
  file: string;
}

export interface RouteNode {
  /** The layout.tsx in this directory, if any */
  layout: LayoutEntry | null;
  /** Page files directly in this directory */
  pages: Array<{ path: string; url: string }>;
  /** Subdirectories */
  children: RouteNode[];
}

export function buildRouteTree(pagesDir: string, pagesUrl: string): RouteNode {
  return scanDirectory(pagesDir, pagesUrl, "");
}

function scanDirectory(pagesDir: string, pagesUrl: string, relDir: string): RouteNode {
  const prefix = relDir ? `${relDir}/` : "";
  const node: RouteNode = { layout: null, pages: [], children: [] };

  const entries = readdirSync(join(pagesDir, relDir), { withFileTypes: true });
  for (const entry of entries) {
    const relFile = prefix + entry.name;
    if (entry.isDirectory()) {
      node.children.push(scanDirectory(pagesDir, pagesUrl, relFile));
    } else if (entry.name === "layout.tsx") {
      node.layout = {
        // The directory's own path: what an index.tsx here would map to
        path: fileToRoute(`${prefix}index.tsx`).path,
        url: `${pagesUrl}/${relFile}`,
        file: join(pagesDir, relFile),
      };
    } else if (entry.name.endsWith(".tsx")) {
      node.pages.push({ path: fileToRoute(relFile).path, url: `${pagesUrl}/${relFile}` });
    }
  }

  return node;
}
```

`pagesUrl` is the root-relative import prefix for the pages directory (`/src/pages` by default) — the same value `discoverRoutes` uses since [Part 11](/11-framework-plugin#the-unified-plugin) made the directory configurable.

The flat `discoverRoutes` still feeds `RoutePaths` and `RouteParamsMap`, so it has to learn the new rule too — otherwise `layout.tsx` would show up as a `/layout` route:

```typescript title="packages/eigen/plugins/eigen-routes.ts"
	const files = readdirSync(pagesDir, { recursive: true })
		.filter((f): f is string => typeof f === "string" && f.endsWith(".tsx"))
		// readdirSync returns backslash-separated paths on Windows
		.map((f) => f.replaceAll("\\", "/")); // [!code --]
		.map((f) => f.replaceAll("\\", "/")) // [!code ++]
		// layout.tsx files wrap routes; they aren't routes themselves // [!code ++]
		.filter((f) => !/(^|\/)layout\.tsx$/.test(f)); // [!code ++]
```

## Generating the nested virtual module

This is where the virtual module generation becomes recursive. Walking the tree, we carry a _layout stack_: every directory with a `layout.tsx` pushes one entry, and every page records the stack it was found under.

The generated code must be plain JavaScript. The virtual module's ID (`\0eigen/routes`) has no `.tsx` extension, so neither Vite's Oxc transform nor `@vitejs/plugin-react` compiles it — JSX in generated code would be a syntax error. So instead of generating wrapper _components_, we generate _data_: one object per layout, declared once at module level, and referenced from each route's `layouts` array.

```typescript title="packages/eigen/plugins/route-tree.ts"
export function generateRouteCode(tree: RouteNode, isSSR: boolean): string {
  const declarations: string[] = [];
  const routes: string[] = [];
  let n = 0;

  function walk(node: RouteNode, layoutStack: string[]) {
    if (node.layout) {
      const name = `layout${n++}`;
      if (isSSR) {
        // Server: static namespace import, keep the loader
        declarations.push(
          `import * as ${name}Mod from '${node.layout.url}'`,
          `const ${name} = { path: '${node.layout.path}', component: ${name}Mod.default, loader: ${name}Mod.loader }`,
        );
      } else {
        // Client: lazy component, no loader (Part 7 strips it anyway)
        declarations.push(
          `const ${name} = { path: '${node.layout.path}', component: React.lazy(() => import('${node.layout.url}')) }`,
        );
      }
      layoutStack = [...layoutStack, name];
    }

    for (const page of node.pages) {
      const layouts = `[${layoutStack.join(", ")}]`;
      if (isSSR) {
        const mod = `RouteMod${n++}`;
        declarations.push(`import * as ${mod} from '${page.url}'`);
        routes.push(
          `  { path: '${page.path}', component: ${mod}.default, loader: ${mod}.loader, layouts: ${layouts} }`,
        );
      } else {
        routes.push(
          `  { path: '${page.path}', component: React.lazy(() => import('${page.url}')), layouts: ${layouts} }`,
        );
      }
    }

    for (const child of node.children) walk(child, layoutStack);
  }

  walk(tree, []);

  return [
    isSSR ? "" : `import React from 'react'`,
    ...declarations,
    `export const routes = [\n${routes.join(",\n")}\n]`,
  ].join("\n");
}
```

## Layout components with typed children

A layout component receives `children` and optionally its own loader data:

```tsx title="src/pages/dashboard/layout.tsx"
import type { LayoutProps } from "eigen/types";
import { defineLoader } from "eigen/helpers";
import { Link } from "eigen/router";
import { getUser, getNotificationCount } from "../../lib/db"; // your data layer

export const loader = defineLoader("/dashboard", async () => {
  const user = await getUser();
  return { user, notifications: await getNotificationCount(user.id) };
});

type Data = Awaited<ReturnType<typeof loader>>;

export default function DashboardLayout({ children, data }: LayoutProps<Data>) {
  return (
    <div className="dashboard">
      <aside>
        <p>Welcome, {data.user.name}</p>
        <span>{data.notifications} notifications</span>
        <nav>
          <Link to="/dashboard">Overview</Link>
          <Link to="/dashboard/settings">Settings</Link>
          <Link to="/dashboard/analytics">Analytics</Link>
        </nav>
      </aside>
      <main>{children}</main>
    </div>
  );

```

`getUser` and `getNotificationCount` stand in for your data layer. To follow along, stub them in `src/lib/db.ts`, e.g. `export async function getUser() { return { id: "1", name: "Ada" }; }` and `export async function getNotificationCount(userId: string) { return 3; }`.

## The layout loader pipeline

When the server renders `/dashboard/analytics`, it needs to call loaders for every layout in the stack _plus_ the page, and keep the results apart. The route's data stops being "the page's data" and becomes a small record:

```typescript title="packages/eigen/route-data.ts"
import type { RouteMatch } from "./match-route";
import { resolveDeferred } from "./deferred";

export interface RouteData {
  /** Loader data per layout, keyed by layout path ('/', '/dashboard', ...) */
  layouts: Record<string, unknown>;
  /** The page's own loader data */
  page: unknown;
}

export async function loadRouteData({ route, params }: RouteMatch): Promise<RouteData> {
  // Every loader in the stack runs concurrently
  const [layoutEntries, page] = await Promise.all([
    Promise.all(
      route.layouts.map(
        async (layout) => [layout.path, layout.loader ? await layout.loader({ params }) : null] as const,
      ),
    ),
    route.loader ? route.loader({ params }) : null,
  ]);
  return { layouts: Object.fromEntries(layoutEntries), page };
}

/** Part 12's resolveDeferred, applied to each loader's result */
export async function resolveRouteData(data: RouteData, signal?: AbortSignal): Promise<RouteData> {
  const layouts = await Promise.all(
    Object.entries(data.layouts).map(async ([path, value]) => [path, await resolveDeferred(value, signal)] as const),
  );
  return { layouts: Object.fromEntries(layouts), page: await resolveDeferred(data.page, signal) };
}
```

<LayoutLoadersDiagram />

### Parallel vs. sequential loader execution

The obvious implementation loops over `route.layouts` and awaits each loader in turn, parent → child. That makes the response time the _sum_ of every loader in the stack. Layout loaders don't depend on each other's results, so `loadRouteData` starts them all at once with `Promise.all` — the response time becomes the _slowest_ loader instead.

This is what Remix does — all loaders for a matched route run in parallel. It's significantly faster when layouts fetch independent data. (If a child really needs a parent's data to load its own, that's a sign the shared query belongs in a helper both loaders call, or in middleware — [Part 14](/14-framework-middleware).)

## Rendering the stack, and why layouts persist

The router assembles the tree at runtime from `match.route.layouts`. This replaces the bare `<Component />` from [Part 11](/11-framework-plugin#extracting-the-runtime):

```tsx title="packages/eigen/router.tsx"
import type { ReactNode } from "react";
import type { RouteMatch } from "eigen/match-route";
import type { RouteData } from "eigen/route-data";
import { LayoutDataProvider } from "eigen/layout-context";

function RouteTree({ match, data }: { match: RouteMatch; data: RouteData | null }) {
  const Page = match.route.component;
  let element: ReactNode = <Page params={match.params} data={data?.page ?? null} />;

  // Wrap from the innermost layout outwards
  for (let i = match.route.layouts.length - 1; i >= 0; i--) {
    const layout = match.route.layouts[i];
    const Layout = layout.component;
    const layoutData = data?.layouts[layout.path] ?? null;
    element = (
      <LayoutDataProvider key={layout.path} path={layout.path} data={layoutData}>
        <Layout data={layoutData}>{element}</Layout>
      </LayoutDataProvider>
    );
  }

  return element;
}
```

Now trace a navigation from `/dashboard/settings` to `/dashboard/analytics` through React's reconciler, which reuses a component instance when the element at the same position has the same type and key:

| Depth | `/dashboard/settings`                         | `/dashboard/analytics`                        | Result                       |
| ----- | --------------------------------------------- | --------------------------------------------- | ---------------------------- |
| 0     | Provider `'/'` → `layout0.component`          | Provider `'/'` → `layout0.component`          | Same type and key — **kept** |
| 1     | Provider `'/dashboard'` → `layout3.component` | Provider `'/dashboard'` → `layout3.component` | Same type and key — **kept** |
| 2     | `SettingsPage`                                | Provider `'/dashboard/analytics'` → …         | Different type — replaced    |

<LayoutPersistenceDiagram />

Only the part of the tree below the shared layouts changes. That works _because_ the layout objects are shared module-level constants: `layout3.component` is the same function for every `/dashboard/*` route.

<Callout type="warn" title="Why not generate a wrapper component per route?">
A tempting design is to have the virtual module emit one wrapper per route — `function Route7() { return <Layout0><Layout3><Page6 /></Layout3></Layout0> }`. It reads nicely, but it defeats persistence: `Route7` and `Route8` are *different component types* at the root of the tree, so React unmounts everything — every layout included — on each navigation. The layouts must appear as the same types at the same positions, which is why the stack is rendered from data by one stable `RouteTree` component.
</Callout>

There's a second way to lose persistence: unmounting the tree while data loads. Part 5's `Router` replaced the page with `<div>Loading...</div>` during a fetch — with layouts, that would unmount them too. And if the pathname changed before the new data arrived, the new route's layouts would briefly render with the _old_ route's data. So the router now commits pathname and data together, once the fetch completes, and renders the loading indicator _next to_ the tree instead of in place of it:

```tsx title="packages/eigen/router.tsx"
export function Router({ initialPathname, initialData }: RouterProps) {
  const [pathname, setPathname] = useState(initialPathname); // [!code --]
  const [data, setData] = useState<unknown>(initialData); // [!code --]
  // Pathname and data change together, so a route never renders // [!code ++]
  // with another route's layout data // [!code ++]
  const [state, setState] = useState({ // [!code ++]
    pathname: initialPathname, // [!code ++]
    data: initialData as RouteData | null, // [!code ++]
  }); // [!code ++]
  const [loading, setLoading] = useState(false);
  const [isPending, startTransition] = useTransition(); // [!code ++]

  useEffect(() => {
    const handler = async () => {
      const newPath = window.location.pathname;
      setPathname(newPath); // [!code --]
      setLoading(true);
      try {
        const res = await fetch(`/_eigen/data?path=${encodeURIComponent(newPath)}`);
        setData(await res.json()); // [!code --]
        const data = (await res.json()) as RouteData | null; // [!code ++]
        // A transition keeps the current tree on screen while a React.lazy // [!code ++]
        // page or layout that hasn't loaded yet suspends // [!code ++]
        startTransition(() => setState({ pathname: newPath, data })); // [!code ++]
      } finally {
        setLoading(false);
      }
    };
    window.addEventListener("popstate", handler);
    return () => window.removeEventListener("popstate", handler);
  }, []);

  const match = matchRoute(pathname, routes); // [!code --]
  const match = matchRoute(state.pathname, routes); // [!code ++]
  if (!match) return <h1>404</h1>;
  const Component = match.route.component; // [!code --]

  return (
    <Suspense fallback={<div>Loading...</div>}>
      {loading ? ( // [!code --]
        <div>Loading...</div> // [!code --]
      ) : ( // [!code --]
        <Component params={match.params} data={data} /> // [!code --]
      )} {/* [!code --] */}
      {(loading || isPending) && <div className="eigen-loading">Loading...</div>} {/* [!code ++] */}
      <RouteTree match={match} data={state.data} /> {/* [!code ++] */}
    </Suspense>
  );
}
```

Add `useTransition` to the `react` import. The transition matters the first time each route is visited. On the client, pages and layouts are `React.lazy` components, and a lazy component whose chunk hasn't loaded yet suspends. Committed as an ordinary update, that suspension would make the `Router`'s `<Suspense>` swap the whole visible tree, layouts included, for its fallback until the chunk arrives. Inside a transition, React keeps showing the current tree, and `isPending` keeps the loading indicator up until the new route can render.

The server renders the same `Router` (through `<App>`), so `RouteTree` produces identical provider, layout, and Suspense structure on both sides of hydration.

## Typing the layout data chain

The type challenge with nested layouts: a child component might need access to data from a parent layout. For example, the page at `/dashboard/analytics` might need the `user` object from the dashboard layout's loader.

`RouteTree` already wraps every layout in a `LayoutDataProvider`. Here is the context behind it:

```tsx title="packages/eigen/layout-context.tsx"
import { createContext, useContext, type ReactNode } from "react";
import type { LayoutDataMap } from "eigen/route-types";

const LayoutDataContext = createContext<Record<string, unknown>>({});

export function LayoutDataProvider({ path, data, children }: { path: string; data: unknown; children: ReactNode }) {
  const parentData = useContext(LayoutDataContext);
  const merged = { ...parentData, [path]: data };
  return <LayoutDataContext.Provider value={merged}>{children}</LayoutDataContext.Provider>;
}

/**
 * Access a parent layout's loader data from a child route.
 * The path is checked against the layouts that exist (LayoutDataMap),
 * and the return type is that layout's loader data.
 */
export function useLayoutData<P extends keyof LayoutDataMap>(path: P): LayoutDataMap[P] {
  const allData = useContext(LayoutDataContext);
  if (!(path in allData)) {
    throw new Error(`useLayoutData('${String(path)}'): no layout at that path wraps this component`);
  }
  return allData[path as string] as LayoutDataMap[P];
}
```

The file contains JSX, so it's a `.tsx` file; add `eigen/layout-context` to the aliases. Usage in a page component:

## Generating layout-aware type declarations

Extend `generateRouteDeclarations` to emit a `LayoutDataMap`. The plugin doesn't need to analyze the loader's source to find its return type: it can emit a type-level `import()` of the layout file and let TypeScript infer the rest. `import()` types inside the generated `.d.ts` resolve relative to the declaration file, so we compute a path from `node_modules/.eigen/` to each layout:

```typescript title="packages/eigen/plugins/eigen-routes.ts"
import { relative } from "node:path"; // [!code ++]
import type { LayoutEntry } from "./route-tree"; // [!code ++]

function generateRouteDeclarations(
	routes: DiscoveredRoute[],
	layouts: LayoutEntry[], // [!code ++]
	outDir: string,
): void {
	// ...pathUnion and paramEntries as before

	const layoutEntries = layouts // [!code ++]
		.map((l) => { // [!code ++]
			const spec = relative(outDir, l.file).replaceAll("\\", "/").replace(/\.tsx$/, ""); // [!code ++]
			return `    '${l.path}': LoaderData<typeof import('${spec}')>`; // [!code ++]
		}) // [!code ++]
		.join("\n"); // [!code ++]

	const layoutTypes = [ // [!code ++]
		"  /** A module's loader return type, or undefined if it has no loader */", // [!code ++]
		"  type LoaderData<M> = M extends { loader: (...args: any[]) => infer R } ? Awaited<R> : undefined", // [!code ++]
		"", // [!code ++]
		"  /** Maps layout paths to their loader data types */", // [!code ++]
		"  export interface LayoutDataMap {", // [!code ++]
		layoutEntries, // [!code ++]
		"  }", // [!code ++]
	].join("\n"); // [!code ++]

	const dts = `// Auto-generated by eigen — do not edit
// ...the 'eigen/routes' module as before

declare module 'eigen/route-types' {
  export type RoutePaths = ${pathUnion}
  export interface RouteParamsMap {
${paramEntries}
  }

${layoutTypes} // [!code ++]
}
`;
```

Collect the layouts with a small walk over the tree (`node.layout` plus each child's layouts), and pass them in at every call site — `configResolved` and the `add`/`unlink` watcher from [Part 9](/09-hmr#debouncing). Creating or deleting a `layout.tsx` is already handled: it fires the same watcher and `hotUpdate` events as a page file.

## Key insight

Nested layouts transform the route plugin from a flat list generator into a tree-walking code generator. The virtual module's `load` hook walks the directory tree and emits a layout stack per route, as plain data the router can render. The developer writes flat files in a directory structure, and the plugin synthesizes the nesting at build time — but _how_ it's synthesized matters: shared layout objects plus a single rendering component are what let React keep layouts mounted.

The type challenge deepens too. With flat routes, you type `params` and `data` per route. With layouts, you have a _chain_ of typed data flowing from parent to child — each level's loader contributes to the data available downstream. Making this fully type-safe requires a `LayoutDataMap` that knows each layout's loader return type. Generating `typeof import(...)` references lets TypeScript infer those types from the source files themselves, with no compiler-API analysis in the plugin. TanStack Router's `routeTree.gen.ts` takes the same approach: the generated file only wires up imports, and TypeScript's inference does the rest.
