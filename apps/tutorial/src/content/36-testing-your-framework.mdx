## Why framework code is unusually testable

Framework code has a property that application code often lacks: **most of the interesting logic is pure functions.** Route matching takes a string and returns a match. Transforms take source code and return modified source code. Middleware takes a context and returns an extended context. Loaders take params and return data. Validation schemas take unknown input and return typed output.

This purity isn't accidental — it's a consequence of the plugin architecture. Vite plugins are functions that receive well-defined inputs (module IDs, source code, config objects) and produce well-defined outputs (resolved IDs, generated code, transformed code). The side effects (file watching, WebSocket messages, HTTP responses) live at the edges.

This means we can test the framework's core logic without starting a dev server, without a browser, and without any I/O. The tests run in milliseconds.

## Setting up Vitest

Vitest is the natural choice for testing Vite-based projects — it runs tests through Vite's own transform pipeline, understands TypeScript natively, and resolves aliases and virtual modules the same way Vite does, as long as it sees the same config. The examples use Vitest 4 or later.

```bash
npm i -D vitest
```

```typescript title="vitest.config.ts"
import { defineConfig, mergeConfig } from "vitest/config";
import viteConfig from "./vite.config";

// Extend the app's Vite config instead of replacing it
export default mergeConfig(
  viteConfig,
  defineConfig({
    test: {
      environment: "node",
    },
  }),
);
```

When a `vitest.config.ts` exists, Vitest reads it _instead of_ `vite.config.ts`. A config that only says `defineConfig({ test: … })` would drop the framework plugin and the `eigen/*` aliases, and the inline tests from earlier parts that import `eigen/middleware` or `eigen/match-route` would fail with "Failed to resolve import". `mergeConfig` keeps them. (Putting the `test` block straight into `vite.config.ts` works too.) There's no `include` here: Vitest's default finds every `*.test.ts` and `*.test.tsx` file.

Add a test script to `package.json`:

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  }
}
```

## The testing pyramid for a Vite framework

A framework's test suite naturally falls into four layers:

<TestingPyramidDiagram />

| Layer           | What it tests                                                 | Speed       | Example                                                                         |
| --------------- | ------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------- |
| **Unit**        | Pure functions (route parsing, matching, ID generation)       | ~1ms each   | `fileToRoute('posts/[id].tsx')` → `/posts/:id`                                  |
| **Plugin**      | Vite plugin hooks in isolation (resolveId, load, transform)   | ~10ms each  | Transform strips `loader` from client output                                    |
| **Integration** | Full render pipeline (middleware → loader → component → HTML) | ~100ms each | `render(new Request('http://localhost/posts/42'))` returns HTML with post title |
| **E2E**         | Browser behavior (navigation, hydration, interactivity)       | ~1s each    | Click link, see new page without full reload                                    |

The inline test sections throughout the series focused on unit tests. This chapter builds upward through plugin and integration tests, and ends with the browser layer.

## Unit tests: the foundation

We covered unit tests in earlier chapters. Here's a quick reference for the testable functions across the framework:

| Function            | Location                | What to test                                              |
| ------------------- | ----------------------- | --------------------------------------------------------- |
| `fileToRoute`       | Route plugin            | Filename → route path conversion, param extraction        |
| `matchRoute`        | `eigen/match-route`     | Static matches, dynamic params, 404 returns               |
| `generateFnId`      | Server functions plugin | ID stability, uniqueness across files                     |
| `executeMiddleware` | `eigen/middleware`      | Context accumulation, short-circuiting, redirect handling |
| Schema `.parse()`   | Page components         | Valid data, type transforms, rejection of invalid input   |

These functions have no external dependencies. They're the fastest, most reliable tests in the suite.

## Plugin tests: testing Vite hooks

Plugin hooks are harder to test than pure functions because they interact with Vite's module graph, environment context, and configuration. There are two approaches.

### Approach 1: Extract and test the logic

The simplest approach — extract the hook's logic into a testable function, and test that function directly. This is what we did for `fileToRoute` and `matchRoute`, and the route plugin's code generation is already shaped this way: since [Part 13](/13-nested-layouts#generating-the-nested-virtual-module), the `load` hook only calls `generateRouteCode(tree, isSSR)` from `packages/eigen/plugins/route-tree.ts`. Test that function with a hand-built `RouteNode` (the shape from [Part 35](/35-error-boundaries-loading#file-conventions)), so the test exercises the same code the plugin runs:

```typescript title="packages/eigen/plugins/__tests__/route-codegen.test.ts"
import { describe, it, expect } from "vitest";
import { generateRouteCode, type RouteNode } from "../route-tree";

const dir = (path: string, rest: Partial<RouteNode>): RouteNode => ({
  path,
  layout: null,
  error: null,
  loading: null,
  notFound: null,
  pages: [],
  children: [],
  ...rest,
});

// pages/layout.tsx, pages/Home.tsx, pages/posts/[id].tsx
const tree = dir("/", {
  layout: { path: "/", url: "/src/pages/layout.tsx", file: "/app/src/pages/layout.tsx" },
  pages: [{ path: "/", url: "/src/pages/Home.tsx" }],
  children: [dir("/posts", { pages: [{ path: "/posts/:id", url: "/src/pages/posts/[id].tsx" }] })],
});

describe("generateRouteCode (client)", () => {
  const code = generateRouteCode(tree, false);

  it("uses React.lazy for code splitting", () => {
    expect(code).toContain("React.lazy");
    expect(code).toContain("import('/src/pages/posts/[id].tsx')");
  });

  it("does not include loader or middleware references", () => {
    expect(code).not.toContain("loader");
    expect(code).not.toContain("middleware");
  });
});

describe("generateRouteCode (SSR)", () => {
  const code = generateRouteCode(tree, true);

  it("uses static namespace imports", () => {
    expect(code).toMatch(/import \* as RouteMod\d+ from '\/src\/pages\/Home\.tsx'/);
    expect(code).not.toContain("React.lazy");
  });

  it("includes loader and middleware references", () => {
    expect(code).toMatch(/loader: RouteMod\d+\.loader/);
    expect(code).toMatch(/middleware: RouteMod\d+\.middleware/); // Part 14
  });

  it("declares each layout once and shares it between routes", () => {
    // Layout persistence (Part 13) depends on this object identity
    expect(code.match(/const layout\d+ =/g)).toHaveLength(1);
  });
});
```

The variable names carry counters (`RouteMod1`, `layout0`), so the assertions match patterns rather than exact names; a refactor that renumbers them shouldn't fail the suite. `globalMiddleware` is emitted by the `load` hook itself, because it needs the project root, so it's covered by the module-runner tests below.

This tests the code generation logic without any Vite involvement. The trade-off: you're not testing the hook integration (does `resolveId` correctly intercept the virtual module ID? does `load` check the environment correctly?). For most cases, this coverage is sufficient — the glue code is thin enough to verify by inspection.

### Approach 2: Test with a real Vite build

For higher confidence, create a minimal Vite project in your test fixtures (its `vite.config.ts` uses `eigen()` from [Part 11](/11-framework-plugin)) and build both environments with Vite's builder API — the same `createBuilder` that `vite build` uses under the hood:

```typescript title="packages/eigen/plugins/__tests__/plugin-integration.test.ts"
import { describe, it, expect } from "vitest";
import { createBuilder, type ViteBuilder } from "vite";
import { fileURLToPath } from "node:url";

const fixtureDir = fileURLToPath(new URL("./fixtures/basic-app", import.meta.url));

type BuildResult = Awaited<ReturnType<ViteBuilder["build"]>>;

// build() can return one output, several, or a watcher — narrow to chunks
function chunksOf(result: BuildResult) {
  const output = Array.isArray(result) ? result[0] : result;
  if (!("output" in output)) throw new Error("Expected build output, got a watcher");
  return output.output.flatMap((file) => (file.type === "chunk" ? [file] : []));
}

describe("eigen-routes plugin (integration)", () => {
  it("generates different code for client and SSR", async () => {
    const builder = await createBuilder({
      root: fixtureDir,
      logLevel: "silent",
      build: { write: false }, // Don't write to disk — return in-memory
    });

    const clientChunks = chunksOf(await builder.build(builder.environments.client));
    const ssrChunks = chunksOf(await builder.build(builder.environments.ssr));

    // Client: every page is a React.lazy() dynamic import → its own chunk.
    // Assert by source module, not by count: layouts are lazy chunks too.
    const pageChunks = clientChunks.filter((c) => c.isDynamicEntry);
    expect(pageChunks.map((c) => c.facadeModuleId)).toEqual(
      expect.arrayContaining([expect.stringContaining("Home.tsx"), expect.stringContaining("[id].tsx")]),
    );

    // Client: the loader (and its server-only marker string) is gone
    const clientCode = clientChunks.map((c) => c.code).join("\n");
    expect(clientCode).not.toContain("FIXTURE_LOADER_MARKER");

    // SSR: static namespace imports — no dynamic page chunks, loader intact
    expect(ssrChunks.some((c) => c.isDynamicEntry)).toBe(false);
    const ssrCode = ssrChunks.map((c) => c.code).join("\n");
    expect(ssrCode).toContain("FIXTURE_LOADER_MARKER");
  });
});
```

<TestingBuildOutputsDiagram />

The fixture's `posts/[id].tsx` exports a loader that returns the string `'FIXTURE_LOADER_MARKER'`, which gives the test something unambiguous to search for. (Searching for a word like `lazy` doesn't work: React's own source contains it, so it is in every client bundle.) The assertions target what the plugins actually generate — separate dynamic chunks for lazy pages on the client, and the loader surviving only on the server ([Part 7](/07-transform-hook) strips it from the client).

This is slower (~500ms per test) but tests the full plugin lifecycle. Use it sparingly — for the critical path (does the virtual module resolve correctly?) and for regression tests when you fix a bug.

## Snapshot testing transforms

Transform hooks are the highest-risk code in a framework — a bug silently corrupts application code. Snapshot tests provide a safety net by recording the exact output of every transform.

```typescript title="packages/eigen/plugins/__tests__/transforms.test.ts"
import { describe, it, expect } from "vitest";

// Import your transform function
import { stripLoaderForClient } from "../eigen-strip-loaders";

describe("loader stripping snapshots", () => {
  it("handles const loader with defineLoader", () => {
    const input = `
import { defineLoader } from 'eigen/helpers'
import { db } from '../lib/database' // server-only

export const loader = defineLoader('/posts/:id', async ({ params }) => {
  return db.query('SELECT * FROM posts WHERE id = $1', [params.id])
});

export default function PostPage({ data }) {
  return <h1>{data.title}</h1>
}
`;
    const output = stripLoaderForClient(input, "posts/[id].tsx");
    expect(output).toMatchSnapshot();
    // Targeted checks alongside the snapshot: the server-only import is pruned
    expect(output).not.toContain("../lib/database");
    expect(output).toContain("/* [eigen] loader stripped for client bundle */");
  });

  it("handles async function loader", () => {
    const input = `
import { db } from '../lib/database' // server-only

export async function loader({ params }) {
  return db.query('SELECT * FROM posts WHERE id = $1', [params.id])
}

export default function PostPage({ data }) {
  return <h1>{data.title}</h1>
}
`;
    expect(stripLoaderForClient(input)).toMatchSnapshot();
  });

  it("handles loader with satisfies", () => {
    const input = `
import type { LoaderFn } from 'eigen/types'

export const loader = (async ({ params }) => {
  return { title: 'Hello' }
}) satisfies LoaderFn<'/posts/:id'>;

export default function PostPage({ data }) {
  return <h1>{data.title}</h1>
}
`;
    expect(stripLoaderForClient(input)).toMatchSnapshot();
  });
});
```

When the transform output changes, Vitest shows a diff:

```diff
- /* [eigen] loader stripped for client bundle */
+ /* [eigen] loader removed for client */
```

If the change is intentional, run `npx vitest run --update` to accept the new snapshots. If it's accidental, you've caught a regression before it reaches users.

### When snapshots break down

Snapshots become brittle when transforms produce non-deterministic output (timestamps, random IDs) or when the output includes content that changes frequently (import paths that depend on the test runner's working directory). Use `expect.stringContaining()` or targeted assertions for those cases instead.

## Integration tests: the full render pipeline

Integration tests verify that the pieces work together — middleware runs, loaders fetch data, components render HTML. To catch a regression in the framework, they have to run the framework's own code: `runRoute`, `executeMiddleware`, `loadRouteData`, the generated `eigen/routes` and the router, not a re-implementation written in the test file.

`render(request)` from [Part 14](/14-framework-middleware#the-middleware-execution-engine) is the natural entry point, but `entry-server.tsx` imports the `eigen/routes` virtual module and the `eigen/*` aliases, so it only loads inside a Vite module graph. The test gets one the same way the dev server does: it starts Vite on the fixture app in middleware mode and imports the server entry through the SSR environment's `ModuleRunner` ([Part 3](/03-server-side-rendering)).

The fixture from the build test grows one page for the middleware case:

```tsx title="packages/eigen/plugins/__tests__/fixtures/basic-app/src/pages/dashboard.tsx"
import { defineLoader } from "eigen/helpers";
import { defineMiddleware } from "eigen/middleware";

// No cookie → redirect; otherwise put a user on the context
const requireCookie = defineMiddleware((ctx) =>
  ctx.request.headers.get("cookie")
    ? { user: { name: "Alice" } }
    : new Response(null, { status: 302, headers: { Location: "/login" } }),
);

export const middleware = [requireCookie];

export const loader = defineLoader("/dashboard", ({ ctx }) => ({
  viewer: (ctx as typeof ctx & { user: { name: string } }).user.name,
}));

export default function Dashboard({ data }: { data: { viewer: string } }) {
  return <p>Viewer: {data.viewer}</p>;
}
```

Its `posts/[id].tsx` loader returns ``{ title: `Post ${params.id}`, marker: 'FIXTURE_LOADER_MARKER' }`` and renders the title in an `<h1>`. The fixture's `entry-server.tsx` is the app's own; what the test exercises is everything it imports from the framework.

```typescript title="packages/eigen/plugins/__tests__/render.integration.test.ts"
import { describe, it, expect, beforeAll, afterAll } from "vitest";
import { createServer, isRunnableDevEnvironment, type RunnableDevEnvironment, type ViteDevServer } from "vite";
import { fileURLToPath } from "node:url";

// The contract of render() from Part 14 (head added in Part 30)
type RenderResult = { response: Response } | { html: string; status: number; data: unknown; head: string };
type Render = (request: Request) => Promise<RenderResult>;

let server: ViteDevServer;
let render: Render;

beforeAll(async () => {
  server = await createServer({
    root: fileURLToPath(new URL("./fixtures/basic-app", import.meta.url)),
    // No HTTP listener; ws: false also skips the HMR WebSocket, so the
    // tests don't fight a running `vite dev` for its port
    server: { middlewareMode: true, ws: false },
    appType: "custom",
    logLevel: "silent",
  });
  const env = server.environments.ssr;
  if (!isRunnableDevEnvironment(env)) throw new Error("SSR environment is not runnable");
  ({ render } = (await (env as RunnableDevEnvironment).runner.import("/src/entry-server.tsx")) as { render: Render });
});

afterAll(async () => {
  await server.close();
});

// Test helpers: build a Request, and unwrap the HTML branch
const req = (path: string, init?: RequestInit) => new Request(new URL(path, "http://localhost"), init);

function expectPage(result: RenderResult) {
  if ("response" in result) throw new Error(`Expected a page, got ${result.response.status}`);
  return result;
}

describe("render pipeline", () => {
  it("renders a static page", async () => {
    const result = expectPage(await render(req("/")));
    expect(result.status).toBe(200);
  });

  it("renders a dynamic page with loader data", async () => {
    const result = expectPage(await render(req("/posts/42")));
    expect(result.status).toBe(200);
    expect(result.html).toContain("Post 42");
    // Part 13's RouteData shape: { layouts, page }
    expect(result.data).toMatchObject({ page: { title: "Post 42" } });
  });

  it("returns 404 for unmatched routes", async () => {
    const result = expectPage(await render(req("/nonexistent")));
    expect(result.status).toBe(404);
  });

  it("passes middleware context to the loader", async () => {
    const result = expectPage(await render(req("/dashboard", { headers: { cookie: "session=abc" } })));
    expect(result.status).toBe(200);
    expect(result.html).toContain("Alice");
  });

  it("short-circuits when middleware returns a Response", async () => {
    const result = await render(req("/dashboard"));
    if (!("response" in result)) throw new Error("Expected the middleware's response");
    expect(result.response.status).toBe(302);
    expect(result.response.headers.get("Location")).toBe("/login");
  });
});
```

These tests exercise the full pipeline — matching, middleware, loading, rendering — without any HTTP server or browser, through the same modules the app runs. Because the loader reads `ctx.user`, the "passes middleware context" test fails if `runRoute` stops running middleware before the loaders or stops handing its context to them. They're the best tool for catching integration bugs like "middleware context doesn't reach loaders" or "loader data isn't passed to components." (`toContain("Alice")` rather than `"Viewer: Alice"`: React separates adjacent text nodes with `<!-- -->` in server HTML.) Starting Vite costs a few hundred milliseconds, once per file, so keep the `beforeAll` setup shared and the individual tests cheap.

## Testing serialization boundaries

The most subtle framework bugs live at serialization boundaries — where data crosses from server to client via JSON. Test these explicitly:

```typescript title="src/__tests__/serialization.test.ts"
import { describe, it, expect } from "vitest";
import { z } from "zod";

describe("serialization boundary", () => {
  it("Date survives round-trip with schema transform", () => {
    const schema = z.object({
      createdAt: z.string().transform((s) => new Date(s)),
    });

    // Server-side: loader returns a Date
    const serverData = { createdAt: new Date("2026-06-01T00:00:00Z") };

    // Serialization (server → HTML → client)
    const serialized = JSON.parse(JSON.stringify(serverData));

    // Without validation: createdAt is a string
    expect(serialized.createdAt).toBe("2026-06-01T00:00:00.000Z");
    expect(typeof serialized.createdAt).toBe("string");

    // With validation: createdAt is a Date again
    const validated = schema.parse(serialized);
    expect(validated.createdAt).toBeInstanceOf(Date);
    expect(validated.createdAt.getFullYear()).toBe(2026);
  });

  it("detects schema drift between server and client", () => {
    // Server returns a field that the client schema doesn't expect
    const serverData = {
      title: "Hello",
      body: "World",
      internalField: "should-not-leak",
    };

    const clientSchema = z.object({
      title: z.string(),
      body: z.string(),
    });

    // Zod strips unknown fields by default
    const parsed = clientSchema.parse(JSON.parse(JSON.stringify(serverData)));
    expect(parsed).toEqual({ title: "Hello", body: "World" });
    expect(parsed).not.toHaveProperty("internalField");
  });
});
```

The "schema drift" test catches a real-world scenario: the server adds a field (maybe containing sensitive data), but the client schema doesn't know about it. Zod's default behavior strips unknown fields, which is both a safety feature and a potential source of confusion. The test documents this behavior explicitly.

## Testing with the SSR module runner

The same setup tests the plugin's output directly: import the virtual module itself through the SSR environment's `ModuleRunner`, so it passes through the full plugin pipeline:

```typescript title="packages/eigen/plugins/__tests__/ssr-load.test.ts"
import { describe, it, expect, beforeAll, afterAll } from "vitest";
import { createServer, isRunnableDevEnvironment, type RunnableDevEnvironment, type ViteDevServer } from "vite";
import { fileURLToPath } from "node:url";

describe("virtual module via the SSR module runner", () => {
  let server: ViteDevServer;
  let ssrEnv: RunnableDevEnvironment;

  beforeAll(async () => {
    server = await createServer({
      root: fileURLToPath(new URL("./fixtures/basic-app", import.meta.url)),
      server: { middlewareMode: true, ws: false },
      appType: "custom",
      logLevel: "silent",
    });
    const env = server.environments.ssr;
    if (!isRunnableDevEnvironment(env)) throw new Error("SSR environment is not runnable");
    ssrEnv = env;
  });

  afterAll(async () => {
    await server.close();
  });

  it("resolves the eigen/routes virtual module", async () => {
    const mod = await ssrEnv.runner.import("eigen/routes");
    expect(mod.routes).toBeDefined();
    expect(Array.isArray(mod.routes)).toBe(true);
  });

  it("generates routes with correct paths", async () => {
    const mod = await ssrEnv.runner.import("eigen/routes");
    const paths = mod.routes.map((r: any) => r.path);
    expect(paths).toContain("/");
  });

  it("exports the global middleware list (Part 14)", async () => {
    const mod = await ssrEnv.runner.import("eigen/routes");
    expect(Array.isArray(mod.globalMiddleware)).toBe(true);
  });

  it("includes loaders in SSR module", async () => {
    const mod = await ssrEnv.runner.import("eigen/routes");
    const routeWithLoader = mod.routes.find((r: any) => r.loader !== undefined);
    // If any page exports a loader, it should be present
    if (routeWithLoader) {
      expect(typeof routeWithLoader.loader).toBe("function");
    }
  });
});
```

This spins up a real Vite dev server (in middleware mode, so no HTTP listener; `ws: false` also skips the HMR socket) and loads modules through the full pipeline. It's slower than unit tests but provides complete confidence that your plugin integrates correctly with Vite.

## Browser and end-to-end tests

Everything so far runs in Node. The bugs this framework is most prone to don't: hydration mismatches, the `React.lazy` and Suspense handshake from [Part 4](/04-hydration), client-side navigation through the Navigation API, error boundaries catching on the client. Those need a real browser, at two levels.

**Component tests in a browser.** Vitest's browser mode runs ordinary test files in a real browser through Playwright. Split the suite into projects, so Node tests and browser tests each run in their environment from one `vitest run`:

```bash
npm i -D @vitest/browser-playwright vitest-browser-react
npx playwright install chromium
```

```typescript title="vitest.config.ts"
import { defineConfig, mergeConfig } from "vitest/config";
import { playwright } from "@vitest/browser-playwright";
import viteConfig from "./vite.config";

export default mergeConfig(
  viteConfig,
  defineConfig({
    test: {
      projects: [
        {
          // extends: inherit the plugins and aliases from the root config
          // (the default since Vitest 5; required in Vitest 4)
          extends: true,
          test: { name: "node", environment: "node", include: ["**/*.test.ts"] },
        },
        {
          extends: true,
          test: {
            name: "browser",
            include: ["**/*.browser.test.tsx"],
            browser: { enabled: true, provider: playwright(), headless: true, instances: [{ browser: "chromium" }] },
          },
        },
      ],
    },
  }),
);
```

A browser test renders real components with `vitest-browser-react`. Part 35's error boundary is a good candidate: `getDerivedStateFromError` is the client-only half of its behavior, which no Node test can reach:

```tsx title="src/__tests__/error-boundary.browser.test.tsx"
import { expect, it } from "vitest";
import { render } from "vitest-browser-react";
import { RouteErrorBoundary } from "eigen/error-boundary";

function Boom(): never {
  throw new Error("boom");
}

it("catches a render error and shows the fallback with phase 'render'", async () => {
  const screen = await render(
    <RouteErrorBoundary fallback={({ error, phase }) => <p>{`${phase}: ${error.message}`}</p>} params={{}} pathname="/x">
      <Boom />
    </RouteErrorBoundary>,
  );
  await expect.element(screen.getByText("render: boom")).toBeInTheDocument();
});
```

**End-to-end tests against the built app.** Hydration and navigation are properties of the whole app, so test them with [Playwright](https://playwright.dev) against a production build. Playwright starts the server itself:

```typescript title="playwright.config.ts"
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "e2e",
  use: { baseURL: "http://localhost:3000" },
  // Build both environments, then start the production server from Part 6
  webServer: { command: "npm run build && npm start", url: "http://localhost:3000" },
});
```

```typescript title="e2e/navigation.spec.ts"
import { test, expect } from "@playwright/test";

test("hydrates without errors and navigates without a full reload", async ({ page }) => {
  // Hydration mismatches surface as console errors (Part 35's onRecoverableError logs them)
  const errors: string[] = [];
  page.on("console", (msg) => msg.type() === "error" && errors.push(msg.text()));
  page.on("pageerror", (error) => errors.push(error.message));

  await page.goto("/posts/42");
  await expect(page.getByRole("heading", { name: "Post 42" })).toBeVisible();
  // Clicking before hydration would be an ordinary page load; the app's root
  // component sets this attribute in a useEffect, which only runs once hydrated
  await page.waitForFunction(() => document.documentElement.dataset.hydrated === "true");

  // A full page load would replace `window` and lose this marker
  await page.evaluate(() => ((window as any).__sameDocument = true));
  await page.getByRole("link", { name: "Home" }).click();
  await expect(page).toHaveURL("/");
  expect(await page.evaluate(() => (window as any).__sameDocument)).toBe(true);

  expect(errors).toEqual([]);
});
```

Keep this layer thin: one test per behavior that only a browser can show, with everything else pushed down to the faster layers.

<Callout type="info" title="Test file colocation">
Tests live close to the code they test — plugin tests in `packages/eigen/plugins/__tests__/`, runtime tests in `src/__tests__/`. The `__tests__` folder is a Jest convention; Vitest's default `include` (`**/*.{test,spec}.?(c|m)[jt]s?(x)`) finds these files by their `.test.ts` suffix wherever they live; once the suite is split into projects, each project's `include` picks its share by suffix instead. (Playwright's `e2e/*.spec.ts` files would match the default too, which is one more reason to give the projects explicit `include`s.) Grouping them like this makes it easy to find tests and keeps them close to the code they verify. The fixture directory contains a minimal app that plugin integration tests build against.
</Callout>

## What to test and what not to

**Always test:**

- Pure functions that implement framework conventions (routing, matching, ID generation)
- Transform hooks — they silently corrupt code if they break
- Serialization boundaries — the server/client data bridge
- Middleware execution order and short-circuiting

**Usually test:**

- Generated code (virtual modules) via snapshots
- The render pipeline end-to-end
- Schema validation with edge cases (missing fields, wrong types, transforms)
- Type-level guarantees — the generated route types are the framework's headline feature (Parts 5 and 35). Vitest has type tests built in: `expectTypeOf` assertions in `*.test-d.ts` files, checked by the TypeScript compiler when you run `vitest --typecheck`. For example, `expectTypeOf(defineLoader).parameter(0).toEqualTypeOf<RoutePaths>()` fails as soon as `defineLoader` accepts a path that isn't a route.

**Rarely test:**

- Vite configuration objects (the config is the test)
- File watcher integration (test discovery logic separately, trust `chokidar`)
- HMR behavior (test the invalidation logic, not the WebSocket transport)
- TypeScript's own inference for application code (test the types the framework promises, not every type an app happens to infer)

## The test-as-documentation pattern

Throughout the inline test sections in this series, every test tells a story. `'does not match when segment count differs'` documents a routing edge case. `'Date survives round-trip with schema transform'` documents a serialization behavior. `'short-circuits on Response return'` documents a middleware guarantee.

When a new developer reads the test suite, they learn the framework's behavior from the test names alone. This is the "test as documentation" pattern — tests that describe _what_ the system guarantees, not _how_ it's implemented. If you find yourself writing a comment to explain a test, move the explanation into the test name instead.

---

## Key insight

A Vite-based framework is uniquely testable because its architecture is built from pure functions connected by a plugin pipeline. Route parsing, route matching, code generation, code transformation, middleware execution, and data validation are all stateless operations with clear inputs and outputs.

The testing strategy follows the architecture: unit-test the pure functions (fast, reliable, documenting), snapshot-test the transforms (catching silent corruption), integration-test the render pipeline (verifying the pieces connect), and leave E2E tests for the behaviors that only a real browser can verify (hydration, navigation, interactivity).

The framework's test suite isn't just quality assurance — it's the specification. Each test documents a guarantee that the framework makes to application developers. When a test fails, it means a guarantee was broken.
