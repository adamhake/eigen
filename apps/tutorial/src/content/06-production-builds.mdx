_This is the seventh installment in a series where we build a toy Next.js on top of Vite. In [Part 5](/05-typed-loaders), we built typed data loaders and a `/_eigen/data` endpoint via Vite's [`configureServer`](https://vite.dev/guide/api-plugin#configureserver) — a dev-only hook ([Part 0](/00-the-mental-model#hook-availability-dev-vs-build)). Now we move to production: two Rolldown builds, an H3 server that imports a pre-built bundle instead of loading source through Vite's module runner, and the data endpoint re-mounted directly on H3 because the plugin middleware no longer exists._

---

## Development vs. production

Everything we've built so far runs on the Vite dev server — the on-demand module transformer from [Part 0](/00-the-mental-model#how-the-dev-server-actually-works). In development, the browser requests modules individually, and Vite transforms each one on the fly. This is great for DX (instant startup, fast HMR) but terrible for production: hundreds of individual HTTP requests, untransformed source files, no minification, no tree-shaking.

In production, Vite switches to a completely different mode: **[Rolldown](https://rolldown.rs) bundling**. Rolldown is a Rust-based bundler ([Rollup](https://rollupjs.org)-compatible) that processes the _entire_ module graph eagerly and produces optimized output:

- **Bundling**: Hundreds of source modules are combined into a handful of chunks, eliminating the HTTP request waterfall.
- **Tree-shaking**: Rolldown analyzes `import`/`export` relationships and removes unused code. If a module exports 10 functions but only 3 are statically imported, the other 7 are eliminated from the output. The word _statically_ matters here, as we'll see [below](#loaders-are-still-in-the-client-bundle): the client branch of `eigen/routes` (from [Part 2](/02-route-discovery-plugin#plugin-hooks)) loads pages with dynamic `import()`, and tree-shaking can't see through that.
- **Scope hoisting**: Instead of wrapping each module in a function (like webpack), Rolldown concatenates modules into a single scope, reducing overhead and enabling better minification.
- **Code splitting**: Dynamic `import()` statements (like our [`React.lazy`](https://react.dev/reference/react/lazy)`(() => import('./Page'))`) create separate chunks that load on demand.
- **Minification**: Variable names are shortened, whitespace is removed, and dead code is eliminated.
- **Hashed filenames**: Output files get content-based hashes (`index-a1b2c3d4.js`), enabling indefinite browser caching — when code changes, the hash changes, and the browser fetches the new version.

<Callout type="info" title="Your plugins run in both modes">
  The same `resolveId`/`load`/`transform` hooks that served modules on-demand in development now process them eagerly
  during Rolldown's build. Your route plugin's virtual module is generated the same way — the only difference is *when*
  it runs (on-demand vs. ahead-of-time) and *what consumes the output* (browser requests vs. Rolldown's module graph).
</Callout>

For a server-rendered framework, we need **two** Rolldown builds — one for the client (browser-targeted, code-split, hashed) and one for the server (Node-targeted, unhashed entry). These are the same two module graphs from [Part 0](/00-the-mental-model#the-two-module-graphs), now producing two output directories instead of two on-demand pipelines. They're connected by the built `index.html` (which already references the hashed client entry) and a manifest file.

## Configuring the builds

```typescript title="vite.config.ts"
import { resolve } from "node:path";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import inspect from "vite-plugin-inspect";
import eigenRoutes from "./plugins/eigen-routes";

export default defineConfig({
  plugins: [react(), eigenRoutes(), inspect()],
  resolve: {
    alias: {
      "eigen/types": resolve(__dirname, "packages/eigen/types.ts"),
      "eigen/match-route": resolve(__dirname, "packages/eigen/match-route.ts"),
      "eigen/serialize": resolve(__dirname, "packages/eigen/serialize.ts"),
      "eigen/helpers": resolve(__dirname, "packages/eigen/helpers.ts"),
      "eigen/run-loader": resolve(__dirname, "packages/eigen/run-loader.ts"),
    },
  },
  build: { // [!code ++]
    manifest: true, // [!code ++]
    rolldownOptions: { // [!code ++]
      onwarn(warning, defaultHandler) { // [!code ++]
        // `RouteModN.loader` on a page without a loader is expected (see below) // [!code ++]
        if (warning.code === "IMPORT_IS_UNDEFINED") return; // [!code ++]
        defaultHandler(warning); // [!code ++]
      }, // [!code ++]
    }, // [!code ++]
  }, // [!code ++]
});
```

**`build.manifest: true`** tells Vite to emit `.vite/manifest.json` alongside the build output. The manifest maps source paths to their built equivalents. We'll look at what it contains below.

**`onwarn`** filters one expected warning. The SSR branch of `eigen/routes` ([Part 2](/02-route-discovery-plugin#plugin-hooks)) reads `RouteMod0.loader` from a namespace import for every page. For pages like `About.tsx` that don't export a loader, Rolldown warns `[IMPORT_IS_UNDEFINED] Import 'loader' will always be undefined`. That's exactly the intended behavior (`loader: undefined`), so we drop that warning code and pass everything else to the default handler. (Rolldown also offers `checks: { importIsUndefined: false }`, which works too.) Without the filter the build still succeeds; you just see one warning per loader-less page.

**The client entry is still `index.html`.** We don't set `build.rolldownOptions.input`, so Vite uses its default: the project's `index.html`. Vite follows its `<script type="module" src="/src/entry-client.tsx">` tag into the module graph, code-splits every `React.lazy` route, and writes a _built_ `dist/client/index.html` whose script tag points at the hashed entry chunk, with the CSS `<link>` tags injected for you. That built file is the production server's template. Setting `input` to `src/entry-client.tsx` instead would still bundle the JavaScript, but Vite would then never process `index.html`, so no `dist/client/index.html` would exist. You'd have to rebuild every tag by hand from the manifest. (If you do need a custom input, it's `build.rolldownOptions.input`. `build.rollupOptions` still works as an alias via Vite 8's compatibility shim, see [Part 0](/00-the-mental-model#vite-is-two-completely-different-things).)

### Build commands

```json title="package.json"
{
  "scripts": {
    "build": "npm run build:client && npm run build:server", // [!code ++]
    "build:client": "vite build --outDir dist/client", // [!code ++]
    "build:server": "vite build --outDir dist/server --ssr src/entry-server.tsx" // [!code ++]
  }
}
```

Two `vite build` invocations against the same config — one per environment. We'll consolidate these into a single command via [`buildApp`](https://vite.dev/guide/api-environment-frameworks#the-buildapp-plugin-hook) in [Part 11](/11-framework-plugin), but two scripts make the asymmetry visible: the only thing that distinguishes a server build from a client build is the `--ssr <entry>` flag and the output directory.

The **`--ssr` flag** changes the build fundamentally:

- **Environment**: The build runs in Vite's `ssr` environment, so `this.environment.name === 'ssr'` in plugin hooks, exactly as in dev.
- **Target**: Node instead of the browser (`platform: 'node'`).
- **Entry**: `src/entry-server.tsx` (the `--ssr` argument) replaces `index.html` as the input.
- **External dependencies**: `node_modules` packages are _not_ bundled by default — they're available at runtime in Node, so bundling them would just bloat the output.
- **Module format**: ESM by default.
- **File names**: The entry is written as `entry-server.js` with no hash, so the production server can import it by a fixed name. Code splitting still works as usual. A dynamic `import()` in server code would produce extra (hashed) chunks. Our server build ends up as one file only because the SSR branch of `eigen/routes` uses static imports (and stays that way as long as nothing in the server graph uses a dynamic `import()` or a non-eager `import.meta.glob`).
- **Plugins**: Both builds run our `eigen-routes` plugin and produce a virtual module — the client gets `React.lazy(...)` references, the server gets route objects with loaders, just like in dev. ([Part 7](/07-transform-hook) introduces `applyToEnvironment` for plugins that should only run in one of the two.)

## The manifest file

After `vite build --outDir dist/client`, the manifest at `dist/client/.vite/manifest.json` looks like this (hashes shortened):

```json
{
  "index.html": {
    "file": "assets/index-a1b2c3d4.js",
    "name": "index",
    "src": "index.html",
    "isEntry": true,
    "dynamicImports": ["src/pages/About.tsx", "src/pages/Home.tsx", "src/pages/posts/[id].tsx"],
    "css": ["assets/index-e5f6g7h8.css"]
  },
  "src/pages/Home.tsx": {
    "file": "assets/Home-m3n4o5p6.js",
    "name": "Home",
    "src": "src/pages/Home.tsx",
    "isDynamicEntry": true,
    "imports": ["index.html"]
  },
  "src/pages/posts/[id].tsx": {
    "file": "assets/_id_-q7r8s9t0.js",
    "name": "_id_",
    "src": "src/pages/posts/[id].tsx",
    "isDynamicEntry": true,
    "imports": ["index.html"]
  }
}
```

(`About.tsx` has an entry too; it's omitted here for space.) Reading it:

- The HTML entry compiled to `assets/index-a1b2c3d4.js`. The chunk is named after `index.html`, the build input, not after `entry-client.tsx`.
- Each page compiled to its own chunk. The client virtual module from [Part 2](/02-route-discovery-plugin#plugin-hooks) uses `React.lazy(() => import(...))`, so Rolldown splits each dynamic import into a separate chunk and lists it under the entry's `dynamicImports`. The `[id]` in the file name is sanitized to `_id_`.
- Shared code (React, the router) lives in the entry chunk. Each page chunk's `imports: ["index.html"]` says "load the entry chunk first". If several pages shared a large dependency that the entry didn't use, Rolldown would split it into its own chunk, with a `_`-prefixed key such as `_shared-x1y2z3.js` (the file itself is `assets/shared-x1y2z3.js`).
- The CSS was extracted to `assets/index-e5f6g7h8.css`.

The built `dist/client/index.html` already contains the entry's `<script type="module" crossorigin src="/assets/index-a1b2c3d4.js">` and the CSS `<link>`, so for the entry itself the production server needs nothing from the manifest. The manifest earns its keep for anything the HTML can't know in advance. The main example is per-route preloading: when the server renders `/posts/1`, it can look up `src/pages/posts/[id].tsx` and emit `<link rel="modulepreload" href="/assets/_id_-q7r8s9t0.js">` so the browser fetches the page chunk in parallel with the entry instead of after it. Doing that requires knowing which source file the matched route came from, which our route objects don't carry yet. Per-route CSS in [Part 37](/37-css-styling-pipeline) is where the framework starts using it: the server build inlines the manifest and walks it for each request.

The hex suffix in each filename (`a1b2c3d4`) is a hash of the file's _content_. Change the source, the hash changes, the filename changes, and the browser is forced to fetch the new version — even if the server set `Cache-Control: max-age=31536000`. This is content-addressed caching, and it's the reason production servers can ship aggressive cache headers without ever serving stale code.

## Exposing the loader for production

The dev `/_eigen/data` middleware in [Part 5](/05-typed-loaders#the-data-endpoint) called `server.environments.ssr.runner.import('eigen/routes')` to grab the route table on every request and ran `runLoader(pathname, routes)` against it. Production has no Vite and no module runner — `eigen/routes` is bundled into `dist/server/entry-server.js` along with the rest of the server code. We expose a small wrapper from the server entry so the production server doesn't have to reach into the bundle's internals:

```tsx title="src/entry-server.tsx"
import { Suspense } from "react";
import { renderToString } from "react-dom/server";
import { matchRoute, type RouteMatch } from "eigen/match-route";
import { routes } from "eigen/routes";
import { runLoader } from "eigen/run-loader"; // [!code ++]

function App({ match, data }: { match: RouteMatch; data: unknown }) {
  const Component = match.route.component;
  return (
    <div>
      <nav>
        <a href="/">Home</a> | <a href="/about">About</a> | <a href="/posts/1">Post 1</a> | <a href="/posts/2">Post 2</a>
      </nav>
      <Suspense fallback={<div>Loading...</div>}>
        <Component params={match.params} data={data} />
      </Suspense>
    </div>
  );
}

export interface RenderResult {
  html: string;
  status: number;
  data: unknown;
}

export async function render(pathname: string): Promise<RenderResult> {
  const match = matchRoute(pathname, routes);
  if (!match) return { html: "<h1>404</h1>", status: 404, data: null };

  let data: unknown = null;
  if (match.route.loader) {
    data = await match.route.loader({ params: match.params });
  }

  const html = renderToString(<App match={match} data={data} />);
  return { html, status: 200, data };
}

export async function loadData(pathname: string): Promise<unknown> { // [!code ++]
  return runLoader(pathname, routes); // [!code ++]
} // [!code ++]
```

`loadData` is a one-liner that takes the place of the `runLoader(pathname, routes)` call in the dev plugin. The production server imports it from the bundle and never has to know about the routes array directly. Because `runLoader` lives in `packages/eigen/run-loader.ts` (a pure function with no Node-specific dependencies, as promised in [Part 5](/05-typed-loaders#the-data-endpoint)), it ports over unchanged — the difference is purely how the routes get loaded into memory.

## The production server

The HTML splicing (rendered markup into the outlet, loader data into a `<script>`) is a pure string function, so we put it in the framework package where it can be tested on its own. It serializes data with `serializeForScript` from [Part 3](/03-server-side-rendering), the same escaping the dev server uses, so a `</script>` inside a blog post's body can't break out of the tag:

```typescript title="packages/eigen/compose-html.ts"
import { serializeForScript } from "./serialize";

export function composeHtml(template: string, appHtml: string, data: unknown): string {
  return template
    .replace("<!--ssr-outlet-->", appHtml)
    .replace("</head>", `  <script>window.__EIGEN_DATA__ = ${serializeForScript(data)}</script>\n</head>`);
}
```

```typescript title="server.prod.ts"
import { readFileSync } from "node:fs";
import { readFile, stat } from "node:fs/promises";
import { join } from "node:path";
import { H3, serve, serveStatic } from "h3";
import { composeHtml } from "./packages/eigen/compose-html";

// The same shape Part 3's server.ts declares. Importing it from
// src/entry-server.tsx would pull JSX and eigen/* imports into
// tsconfig.node.json, which has neither `jsx` nor those paths.
interface RenderResult {
  html: string;
  status: number;
  data: unknown;
}

// The built template: Vite already rewrote its <script> and <link> tags
// to the hashed files in dist/client/assets. Read it once at startup.
const template = readFileSync("dist/client/index.html", "utf-8");

// Top-level await: load the pre-built server bundle once at startup.
// The path is in a variable so TypeScript doesn't try to resolve build
// output that has no type declarations (or doesn't exist before a build).
const serverEntry = "./dist/server/entry-server.js";
const { render, loadData } = (await import(serverEntry)) as {
  render: (pathname: string) => Promise<RenderResult>;
  loadData: (pathname: string) => Promise<unknown>;
};

const app = new H3();

// Serve hashed static assets with year-long caching.
// serveStatic passes the full request path ("/assets/index-a1b2c3d4.js") as `id`.
app.get("/assets/**", (event) =>
  serveStatic(event, {
    getContents: (id) => readFile(join("dist/client", id)),
    getMeta: async (id) => {
      const stats = await stat(join("dist/client", id)).catch(() => undefined);
      if (stats?.isFile()) return { size: stats.size, mtime: stats.mtimeMs };
    },
    // 1 year — content hashes handle cache busting
    headers: { "Cache-Control": "public, max-age=31536000, immutable" },
  }),
);

// Data endpoint — the production equivalent of Part 5's plugin middleware
app.get("/_eigen/data", async (event) => {
  const pathname = event.url.searchParams.get("path") ?? "/";
  try {
    const data = await loadData(pathname);
    return Response.json(data);
  } catch (e) {
    console.error(e);
    return new Response("Internal server error", { status: 500 });
  }
});

// SSR fallback
app.all("/**", async (event) => {
  try {
    const { html: appHtml, status, data } = await render(event.url.pathname);
    return new Response(composeHtml(template, appHtml, data), {
      status,
      headers: { "Content-Type": "text/html; charset=utf-8" },
    });
  } catch (e) {
    console.error(e);
    return new Response("Internal server error", { status: 500 });
  }
});

serve(app, { port: 3000 });
console.log("Production server: http://localhost:3000");
```

Like `server.ts`, this file runs under `tsx` and is type-checked as tooling code, so add it to `tsconfig.node.json` from [Part 1](/01-bare-vite-spa). That's why it declares `RenderResult` itself and loads the bundle through a variable: everything it imports must type-check under the tooling config, and `dist/server/entry-server.js` is untyped build output, so the `as { … }` assertion is the only type information the server has about it.

```json title="tsconfig.node.json"
{
  "include": ["vite.config.ts", "plugins/**/*", "server.ts"] // [!code --]
  "include": ["vite.config.ts", "plugins/**/*", "server.ts", "server.prod.ts"] // [!code ++]
}
```

Compared to the dev server in [Part 3](/03-server-side-rendering#the-custom-dev-server), four things changed:

- **No Vite instance.** No `createViteServer`, no module runner, no [`transformIndexHtml`](https://vite.dev/guide/api-javascript#vitedevserver-transformindexhtml), no [`fromNodeHandler(vite.middlewares)`](https://vite.dev/guide/ssr#setting-up-the-dev-server) glue. Production doesn't import `vite` at all.
- **Static file serving replaces Vite's middleware.** H3's [`serveStatic`](https://h3.dev/examples/serve-static-assets) is called inside a handler with two callbacks. `getMeta` stats the file (a missing file makes `serveStatic` answer 404), and `getContents` reads it. It handles `HEAD`, `Last-Modified`/`If-Modified-Since`, and MIME types; the `headers` option adds our cache policy. We import from `h3` directly here (not `h3/node` like the dev server). `serve` picks the Node adapter at runtime, and the handlers themselves are web-standard code.
- **`import()` instead of `runner.import()`.** The server entry is a pre-built ESM module that Node loads once at startup. Top-level await holds the import promise so subsequent requests pay nothing.
- **The built template replaces `transformIndexHtml`.** In dev, `index.html` still says `<script type="module" src="/src/entry-client.tsx">` and Vite injects `/@vite/client` per request. The build has already rewritten `dist/client/index.html` to point at `/assets/index-a1b2c3d4.js` and added the CSS link. The server reads it once and only splices in the per-request parts.

The data endpoint is the new piece. In dev, [Part 5's plugin middleware](/05-typed-loaders#the-data-endpoint) handled `/_eigen/data` because `configureServer` had a Vite instance whose SSR environment could import `eigen/routes`. Production has no Vite, no plugin, no `configureServer` — but it does have `loadData` exported from the pre-built bundle, which is enough. Same `runLoader` underneath, same JSON contract on the wire, different glue.

<Callout type="info" title="Why a separate file from `server.ts`?">

Splitting the dev server (`server.ts`) and production server (`server.prod.ts`) keeps each file focused on what it actually needs. The dev server's only job is mounting Vite as middleware and rendering through the SSR environment's module runner. The production server's job is reading pre-built files and serving them. Folding both into one file means a `if (process.env.NODE_ENV === 'production') { ... } else { ... }` split that doubles the imports and obscures both paths.

In [Part 17](/17-deployment-adapters), we'll replace `server.prod.ts` entirely. The production server becomes a build artifact — generated by an adapter plugin that wraps `loadData` and `render` in platform-specific glue (Netlify Functions, Cloudflare Workers, Node, etc.). For now, hand-writing it makes the moving parts visible.

</Callout>

The `dist/client/assets/` directory is entirely static — drop it on a CDN and it serves correctly. (`dist/client/index.html` is a _template_ with an unfilled `<!--ssr-outlet-->`, so don't serve it as a page.) The `dist/server/` directory contains an ESM module that any Node-compatible runtime can `import()`.

**Type annotations are stripped.** The production bundles are pure JavaScript. TypeScript was a dev-time concern; the build output has no trace of it. The `.d.ts` files we generated in [Part 2](/02-route-discovery-plugin#type-declarations) live under `node_modules/.eigen/` and are also irrelevant at runtime — they exist to inform the type checker, not the runtime.

### Loaders are still in the client bundle

Search the client output for the body of a loader:

```bash
grep -l jsonplaceholder dist/client/assets/*.js
# dist/client/assets/_id_-q7r8s9t0.js
```

The `posts/[id]` page chunk contains the loader, `fetch("https://jsonplaceholder…")` and all. You might expect tree-shaking to remove it, since the client branch of `eigen/routes` never reads `.loader`. But that branch loads each page with `React.lazy(() => import("/src/pages/posts/[id].tsx"))`. A dynamic `import()` resolves to the module's _namespace object_, and here that object is handed straight to `React.lazy`. Rolldown can't prove which properties of it will be read, so it keeps every export. (Bundlers can tree-shake a dynamic import only when the code destructures specific names right at the call site, such as `import("./x").then(({ default: Page }) => …)`.)

<LazyChunkExportsDiagram />

So in this part, loader code ships to the browser. It never _runs_ there (the client gets data from `/_eigen/data`), but it costs bytes, and it can leak server-side details. Worse, if a loader's file imports a Node-only module (`import { readFile } from "node:fs"`), Vite replaces that module with an empty browser stub and prints a warning ("Module "node:fs" has been externalized for browser compatibility"), and the page chunk carries a broken reference. Removing loaders from the client is a job for the `transform` hook, and that's [Part 7](/07-transform-hook).

## What to observe

1. **Run the build.** `npm run build` produces both directories. Watch the terminal output — Vite reports chunk sizes and warns about chunks larger than 500 KB.

2. **Inspect the manifest and the built HTML.** Open `dist/client/.vite/manifest.json` and trace how source paths map to hashed filenames. Each `src/pages/*.tsx` file becomes its own `isDynamicEntry: true` chunk because of the `React.lazy` import in the client virtual module. Then open `dist/client/index.html`: the dev `<script src="/src/entry-client.tsx">` is gone, replaced by a `<script type="module" crossorigin src="/assets/index-….js">` in `<head>` plus the CSS link, with `<!--ssr-outlet-->` still waiting to be filled.

3. **Run the production server.** With both builds complete, `npx tsx server.prod.ts`. Compare it to the dev server: same HTML structure in the response body, but the asset URLs in `<head>` now point at hashed files in `/assets/`, not `/src/...` or `/@vite/client`.

4. **Verify the data endpoint ported over.** Start on `http://localhost:3000/posts/1`, click "Post 2". The Network tab shows `GET /_eigen/data?path=%2Fposts%2F2` returning the new post's JSON — exactly the same flow as in [Part 5](/05-typed-loaders#what-to-observe), but now served by the H3 route in `server.prod.ts` instead of the plugin middleware.

5. **Find the loader in the client bundle.** `grep -l jsonplaceholder dist/client/assets/*.js` prints the `posts/[id]` page chunk. The same grep against `dist/server/entry-server.js` finds it too. The server is where it belongs; the client copy is the problem [Part 7](/07-transform-hook) fixes.

6. **Cache headers.** The `serveStatic` call sets `Cache-Control: public, max-age=31536000, immutable` (one year) on `/assets/**`. Open DevTools → Network and confirm. Request a file that doesn't exist (`/assets/nope.js`) and you get a 404 from `serveStatic`, not the SSR fallback. Hashed filenames make this safe: when you change a file, its hash changes, so the URL changes, and the browser can't serve the stale version.

## Key insight

The production build is where "two module graphs" becomes "two output directories." The same plugin pipeline that served on-demand modules in dev now produces concrete files; the same `eigen/routes` virtual module emits client-flavored code into `dist/client/` and server-flavored code into `dist/server/`. Nothing about the plugin changes — only when it runs and what consumes its output.

The client build's outputs are the seam. The built `index.html` carries "which hashed files does the entry need" forward to runtime. The manifest carries the rest of the build's knowledge ("which source path became which hashed chunk") for anything the HTML can't know in advance, like per-route preloads and CSS. Every Vite-based SSR framework has this shape: build client → build server → use the client build's outputs to bridge them at request time.

The data endpoint is a smaller version of the same migration. In dev, it's a closure over the SSR environment's module runner, mounted by `configureServer`. In production, it's an H3 route over an `import()`-ed bundle. The middleware code disappears; the work it did (match → run loader → JSON) gets re-expressed against whatever runtime exists. We'll do this migration again, in different forms, for API routes ([Part 8](/08-dev-middleware)), framework middleware ([Part 14](/14-framework-middleware)), and deployment adapters ([Part 17](/17-deployment-adapters)).

In [Part 11](/11-framework-plugin), we'll see how [`buildApp`](https://vite.dev/guide/api-environment-frameworks#the-buildapp-plugin-hook) — the plugin hook for app-level build orchestration — lets the framework coordinate both builds in a single `vite build` command, eliminating the `npm run build:client && npm run build:server` shell glue.

<TestSection title="Testing: HTML composition">

The production server's request-handling code is mostly I/O, but `composeHtml`, which splices rendered markup and serialized data into the built template, is a pure string transformation. Like `buildHref` in [Part 4](/04-hydration), it's worth testing separately, because a typo in the splice logic produces a broken page that may not fail loudly until users see it.

```typescript title="packages/eigen/__tests__/compose-html.test.ts"
import { describe, expect, it } from "vitest";
import { composeHtml } from "../compose-html";

// Shaped like dist/client/index.html after the build
const template = `<!DOCTYPE html>
<html>
  <head><title>Eigen</title>
  <script type="module" crossorigin src="/assets/index-abc.js"></script>
</head>
  <body><div id="root"><!--ssr-outlet--></div></body>
</html>`;

describe("composeHtml", () => {
  it("substitutes the SSR outlet with rendered markup", () => {
    const out = composeHtml(template, "<h1>Hello</h1>", null);
    expect(out).toContain('<div id="root"><h1>Hello</h1></div>');
    expect(out).not.toContain("<!--ssr-outlet-->");
  });

  it("keeps the build's hashed entry script", () => {
    const out = composeHtml(template, "", null);
    expect(out).toContain('<script type="module" crossorigin src="/assets/index-abc.js">');
  });

  it("serializes loader data into __EIGEN_DATA__", () => {
    const data = { id: 1, title: "Post 1" };
    const out = composeHtml(template, "", data);
    expect(out).toContain(`<script>window.__EIGEN_DATA__ = ${JSON.stringify(data)}</script>`);
  });

  it("can't be broken out of by a </script> inside the data", () => {
    const out = composeHtml(template, "", { body: "</script><script>alert(1)</script>" });
    expect(out.match(/<\/script>/g)).toHaveLength(2); // the entry's and ours
    expect(out).toContain("\\u003c/script\\u003e");
  });

  it("inserts the data script before </head>, not after", () => {
    const out = composeHtml(template, "", null);
    const headEnd = out.indexOf("</head>");
    const script = out.indexOf("window.__EIGEN_DATA__");
    expect(script).toBeLessThan(headEnd);
  });
});
```

The `</script>` test is the one that justifies `serializeForScript`. Plain `JSON.stringify` would emit the post body's `</script>` verbatim, the browser's HTML parser would end our script tag there, and whatever followed would run as markup. The last assertion catches a quieter failure mode: writing `'</head><script>…'` instead of `'<script>…</head>'` puts the script outside `<head>`. Browsers tolerate it, but it's invalid HTML. Tests like this make the splice contract explicit.

Run with `pnpm vitest run packages/`.
