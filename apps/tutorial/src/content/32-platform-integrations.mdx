## _In this installment, we explore how a framework connects to external services — databases, analytics, error tracking, and feature flags — through the plugin infrastructure. Rather than treating each service as an isolated npm import, we show how the framework plugin can generate configuration, inject scripts, instrument server functions, and provide typed helpers that make integration seamless._

## The integration pattern

External services interact with the framework at multiple layers:

| Layer                 | Example                            | Hook / mechanism                             |
| --------------------- | ---------------------------------- | -------------------------------------------- |
| **Build time**        | Validate env vars exist            | `configResolved`                             |
| **HTML injection**    | PostHog analytics script           | `transformIndexHtml`                         |
| **Middleware**        | Database connection per request    | Framework middleware (Part 14)               |
| **Loaders**           | Query Neon in data loaders         | Direct import in server code                 |
| **Server functions**  | Track events on mutations          | Instrumentation in `transform` or middleware |
| **Client components** | PostHog event tracking             | Client-side SDK initialization               |
| **Error handling**    | Report errors to PostHog           | Error boundary integration                   |
| **Adapter output**    | Connection string in deploy config | Adapter plugin (Part 17)                     |

A well-designed integration plugin touches many of these layers through a single configuration:

```typescript title="vite.config.ts"
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import eigen from "./packages/eigen/plugin"; // a package import from Part 40 on
import { neonIntegration } from "eigen/integrations/neon";
import { posthogIntegration } from "eigen/integrations/posthog";

export default defineConfig({
  plugins: [
    eigen(),
    neonIntegration(), // Database
    posthogIntegration(), // Analytics + error tracking
    react(),
  ],
});
```

## Neon integration

### The serverless database challenge

Neon is a serverless Postgres provider. In serverless environments (Netlify Functions, Cloudflare Workers, Vercel Edge), traditional connection pooling doesn't work — each function invocation is isolated. Neon's `@neondatabase/serverless` driver uses HTTP or WebSocket connections that work in these environments.

The framework integration handles connection management, so developers just write queries:

```typescript title="packages/eigen/integrations/neon.ts"
import { loadEnv, type Plugin, type ResolvedConfig } from "vite";

export function neonIntegration(): Plugin {
  return {
    name: "eigen-integration-neon",

    configResolved(config: ResolvedConfig) {
      // Vite only exposes VITE_-prefixed variables to client code, and it does
      // not copy .env files into process.env. Load them here so the server
      // (dev SSR, and validation below) sees DATABASE_URL from .env.local.
      // In production the platform provides real environment variables.
      const env = loadEnv(config.mode, config.envDir || config.root, "");
      if (env.DATABASE_URL && !process.env.DATABASE_URL) {
        process.env.DATABASE_URL = env.DATABASE_URL;
      }

      const dbUrl = process.env.DATABASE_URL;
      if (!dbUrl) {
        console.warn(
          "⚠ DATABASE_URL not set. Neon integration requires a connection string.\n" +
            "  Set it in .env.local: DATABASE_URL=postgresql://...",
        );
      }

      // Validate it looks like a Neon URL
      if (dbUrl && !dbUrl.includes("neon.tech") && !dbUrl.includes("localhost")) {
        console.warn("⚠ DATABASE_URL does not appear to be a Neon connection string.");
      }
    },

    // Generate a database helper that handles connection lifecycle
    resolveId(id) {
      if (id === "eigen/db") return "\0eigen/db";
    },

    load(id) {
      if (id !== "\0eigen/db") return;

      const envName = this.environment.name;

      if (envName === "client") {
        // Client environment. Part 7's transform strips loaders and prunes the
        // imports only they used, so a page whose loader imports eigen/db never
        // pulls this module into the browser. If something else does import it,
        // fail loudly — but only when called, so merely importing it can't crash
        // the whole page at module evaluation.
        return `
          function serverOnly() {
            throw new Error(
              'eigen/db is server-only. Query the database from a loader or server function.'
            )
          }
          export function query() { serverOnly() }
          export const sql = null
        `;
      }

      if (envName === "edge") {
        // Edge: Neon's HTTP driver — one HTTPS request per query, no socket.
        // On Cloudflare Workers, process.env is populated from bindings when
        // the nodejs_compat flag is on (compatibility date 2025-04-01 or later).
        return `
          import { neon } from '@neondatabase/serverless'

          const sql = neon(process.env.DATABASE_URL)

          export { sql }
          export async function query(text, params) {
            // Since @neondatabase/serverless 1.0, sql() is tagged-template only;
            // parameterized strings go through sql.query(). fullResults returns
            // { rows, rowCount, fields, ... } — the same shape as the Node Pool.
            return sql.query(text, params, { fullResults: true })
          }
        `;
      }

      // Node SSR: Neon's WebSocket driver with connection pooling
      return `
        import { Pool, neonConfig } from '@neondatabase/serverless'

        // Node 22+ has a global WebSocket. Older Node needs the 'ws' package.
        if (typeof WebSocket === 'undefined') {
          const { default: ws } = await import('ws')
          neonConfig.webSocketConstructor = ws
        }

        let pool = null

        function getPool() {
          if (!pool) {
            pool = new Pool({
              connectionString: process.env.DATABASE_URL,
              max: 10,
            })
          }
          return pool
        }

        export async function query(text, params) {
          return getPool().query(text, params)
        }

        export const sql = getPool()
      `;
    },
  };
}
```

### Type declarations for the database module

```typescript title="node_modules/.eigen/eigen-db.d.ts"
declare module "eigen/db" {
  /** Execute a parameterized SQL query ($1, $2, … placeholders) */
  export function query<T extends Record<string, unknown> = Record<string, unknown>>(
    text: string,
    params?: unknown[],
  ): Promise<{ rows: T[]; rowCount: number | null }>;

  /** The connection pool (Node) or HTTP query function (Edge) */
  export const sql: unknown;
}
```

The declared return type is the subset both drivers share — the Node `Pool` returns a `pg`-style `QueryResult`, and the edge path asks the HTTP driver for `fullResults` — so `result.rows` works identically in either environment.

### Usage in a loader

```tsx title="src/pages/posts/[id].tsx"
import { query } from "eigen/db";
import { defineLoader } from "eigen/helpers";

export const loader = defineLoader("/posts/:id", async ({ params }) => {
  const result = await query<{ id: string; title: string; body: string }>(
    "SELECT id, title, body FROM posts WHERE id = $1",
    [params.id],
  );
  return result.rows[0];
});
```

The import `eigen/db` is a virtual module that the Neon integration plugin provides. It generates different code per environment — WebSocket-pooled connections for Node, HTTP queries for edge. In the client environment, Part 7's transform removes the `loader` export and then the now-unused `eigen/db` import, so the database module never reaches the browser; and if some other client code imports it by mistake, any call throws a clear error.

### Drizzle ORM integration

For a richer DX, the integration can expose a Drizzle client:

```typescript
// In the virtual module (Node environment), if drizzle-orm is installed:
import { drizzle } from "drizzle-orm/neon-serverless";
import { Pool } from "@neondatabase/serverless";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
export const db = drizzle({ client: pool });
```

## PostHog integration

PostHog serves multiple roles: product analytics, session replay, feature flags, error tracking. The integration plugin handles all of them:

```typescript title="packages/eigen/integrations/posthog.ts"
import { loadEnv, type Plugin } from "vite";

export interface PostHogOptions {
  /** PostHog project API key (public — safe to ship to the browser) */
  apiKey?: string;
  /** PostHog API host (default: https://us.i.posthog.com) */
  apiHost?: string;
  /** Enable session replay */
  sessionReplay?: boolean;
  /** Enable error tracking */
  errorTracking?: boolean;
}

export function posthogIntegration(options: PostHogOptions = {}): Plugin {
  let apiKey = options.apiKey;
  const apiHost = options.apiHost ?? "https://us.i.posthog.com";

  return {
    name: "eigen-integration-posthog",

    configResolved(config) {
      // .env files aren't in process.env at config time — load them explicitly
      const env = loadEnv(config.mode, config.envDir || config.root, "");
      apiKey ??= process.env.POSTHOG_API_KEY ?? env.POSTHOG_API_KEY;
      if (!apiKey) {
        console.warn(
          "⚠ PostHog API key not set. Set POSTHOG_API_KEY in .env.local " + "or pass apiKey to posthogIntegration().",
        );
      }
    },

    // Inject PostHog client-side script
    transformIndexHtml(html) {
      if (!apiKey) return html;

      // JSON.stringify produces valid, quoted JS string literals for the config values
      const posthogScript = `
        <script>
          // PostHog's minified snippet — this is the standard loader script from
          // https://posthog.com/docs/libraries/js that asynchronously loads the
          // full PostHog library and provides stub methods until it's ready.

    resolveId(id) {
      if (id === "eigen/analytics") return "\0eigen/analytics";

    load(id) {

      if (this.environment.name === "client") {
        return `

            if (typeof window !== 'undefined' && window.posthog) {
              window.posthog.capture(event, properties)
            }

            if (typeof window !== 'undefined' && window.posthog) {
              window.posthog.identify(userId, properties)

            if (typeof window !== 'undefined' && window.posthog) {

      // Serverless and edge functions can be frozen as soon as the response is
      // sent, so queued events would be lost. captureImmediate() resolves only
      // after the event has been delivered; flush() drains anything else queued.
      return `
        import { PostHog } from 'posthog-node'
        import { getCookie } from 'eigen/cookies'

          flushAt: 1,
          flushInterval: 0,

        export async function trackEvent(event, properties = {}, distinctId) {
          await client.captureImmediate({ distinctId, event, properties })
        }

        export async function identifyUser(userId, properties = {}) {
          client.identify({ distinctId: userId, properties })
          await client.flush()
        }

        export async function getFeatureFlag(flag, distinctId) {
          const flags = await client.evaluateFlags(distinctId)
          return flags.isEnabled(flag)
        }

        /**
         * The browser SDK's anonymous distinct ID, read from its cookie
         * (ph_<project key>_posthog), so server events join the same person.
         */
        export function getDistinctId(request) {
          const raw = getCookie(request, ${JSON.stringify(`ph_${apiKey ?? ""}_posthog`)})
          if (!raw) return undefined
          try {
            return JSON.parse(raw).distinct_id
          } catch {
            return undefined
          }
        }
      `;
    },
  };
}
```

### Usage in middleware and loaders

```typescript title="src/middleware/analytics.ts"
import { defineMiddleware } from "eigen/middleware";
import { trackEvent, getDistinctId } from "eigen/analytics";

export const analyticsMiddleware = defineMiddleware(async (ctx) => {
  // Track page views server-side (not affected by ad blockers).
  // Use the browser SDK's distinct ID so server and client events belong to
  // the same person. Without one (first visit, no JS yet), skip rather than
  // lumping every anonymous visitor into a single "anonymous" person.
  const distinctId = getDistinctId(ctx.request);
  if (!distinctId) return;

  await trackEvent(
    "$pageview",
    {
      $current_url: ctx.request.url, // PostHog expects the full URL
      $referrer: ctx.request.headers.get("referer") ?? "",
    },
    distinctId,
  );
});
```

```typescript title="src/pages/posts/new.tsx"
// In a server function — track mutations
import { createServerFn } from "eigen/server";
import { query } from "eigen/db";
import { trackEvent } from "eigen/analytics";
import { redirect } from "eigen/middleware";
import { z } from "zod";

export const createPost = createServerFn({ method: "POST" })
  .validator(z.object({ title: z.string().min(1) }))
  .handler(async ({ data, context }) => {
    // context.user comes from global middleware (typed via EigenContext)
    const user = context.user ?? redirect("/login");

    const result = await query<{ id: string }>("INSERT INTO posts (title, author_id) VALUES ($1, $2) RETURNING id", [
      data.title,
      user.id,
    ]);
    const post = result.rows[0];

    await trackEvent("post_created", { post_id: post.id, title: data.title }, user.id);

    return post;
  });
```

### Feature flags in loaders

```tsx title="src/pages/dashboard.tsx"
import { defineLoader } from "eigen/helpers";
import { redirect } from "eigen/middleware";
import { getFeatureFlag } from "eigen/analytics";

export const loader = defineLoader("/dashboard", async ({ ctx }) => {
  const user = ctx.user ?? redirect("/login");

  const showNewUI = await getFeatureFlag("new-dashboard-ui", user.id);
  const data = await getDashboardData(user.id);

  return { ...data, showNewUI };
});

export default function Dashboard({ data }) {
  if (data.showNewUI) {
    return <NewDashboard data={data} />;
  }
  return <LegacyDashboard data={data} />;
}
```

## The integration plugin pattern

Both Neon and PostHog integrations follow the same pattern:

1. **`configResolved`** — Load `.env` values with `loadEnv` and validate that required variables exist and are well-formed
2. **`resolveId` / `load`** — Generate virtual modules with environment-appropriate code (client vs. SSR vs. edge)
3. **`transformIndexHtml`** — Inject client-side scripts (analytics snippets)
4. **Type declarations** — Generate `.d.ts` files for the virtual modules
5. **Middleware** — Provide pre-built middleware for common patterns (connection management, event tracking)

This pattern is extensible to any service: Sentry for error tracking, LaunchDarkly for feature flags, Stripe for payments, Resend for email. Each integration is a Vite plugin that wires the service into the framework at the appropriate layers.

---

## Environment-aware code generation

The most interesting aspect is how the virtual module generates different code per environment:

| Module            | Client                                           | SSR (Node)       | Edge                                  |
| ----------------- | ------------------------------------------------ | ---------------- | ------------------------------------- |
| `eigen/db`        | Throws when called (normally stripped by Part 7) | WebSocket pool   | HTTP driver (`sql.query`)             |
| `eigen/analytics` | `posthog.capture()` (browser SDK)                | PostHog Node SDK | PostHog Node SDK (`captureImmediate`) |

This is the virtual module pattern from Part 2, applied to infrastructure. The developer writes `import { query } from 'eigen/db'` and the framework provides the right implementation for the target runtime.

---

## Key insight

Platform integrations are where the framework's architecture pays off most visibly. Without the framework, connecting Neon to a serverless deployment requires manually configuring connection pooling, handling the WebSocket driver setup, preventing client-side imports, and managing environment variables. With the integration plugin, it's `neonIntegration()` in the config and `import { query } from 'eigen/db'` in your code.

The virtual module pattern ensures the right driver is used per environment. The `configResolved` hook validates configuration at startup. The `transformIndexHtml` hook injects client scripts. And the middleware layer provides request-scoped concerns like analytics tracking.

This is the "batteries-included" experience that makes frameworks valuable beyond their rendering capabilities. The rendering pipeline (Parts 0–20) is the foundation; the integration layer is what makes it practical for real applications.
