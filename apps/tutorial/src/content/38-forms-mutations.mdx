_Forms are where every framework layer converges — routing, server functions, validation, caching. This module builds a forms and mutations system on top of [Part 15](/15-server-functions) (server functions), [Part 14](/14-framework-middleware) (middleware), and [Part 25](/25-use-cache) (`"use cache"`). The guiding principle: progressive enhancement isn't a nice-to-have, it's the foundation the JavaScript-enhanced experience builds on._

---

## The form lifecycle

Every form mutation follows the same cycle:

```
Submit → Validate → Mutate → Revalidate → Update UI
```

In Eigen, this maps directly to existing primitives:

| Step           | Primitive                                                           | Where it runs   |
| -------------- | ------------------------------------------------------------------- | --------------- |
| **Submit**     | `<Form action={serverFn}>`, or calling the server function directly | Client → Server |
| **Validate**   | `.validator()` (from Part 15) + client-side schema                  | Both            |
| **Mutate**     | Server function `.handler()`                                        | Server          |
| **Revalidate** | `revalidateTag()` (from Part 25)                                    | Server          |
| **Update UI**  | `redirect()` or `navigation.reload()` re-fetches loader data        | Client          |

The framework's job is wiring these steps together so they work without JavaScript (progressive enhancement) and feel instant with JavaScript (optimistic UI).

---

## Progressive enhancement

The foundation: a form that works with zero client-side JavaScript. The browser submits a standard HTML form, the server processes it, and the browser follows a redirect to the result.

### Wiring forms to server functions

Every server function already knows its endpoint: [Part 15](/15-server-functions)'s transform sets `.url` (`/_eigen/fn/<id>`) on the server-side function, and the client stub carries the same `.url`. Eigen's `<Form>` component uses it:

```tsx title="src/pages/posts/new.tsx"
import { z } from "zod";
import { createServerFn } from "eigen/server";
import { redirect } from "eigen/middleware";
import { Form } from "eigen/forms";
import { db } from "../../lib/database";

export const createPost = createServerFn()
  .validator(
    z.object({
      title: z.string().min(1),
      body: z.string().min(1),
    }),
  )
  .handler(async ({ data }) => {
    await db.query("INSERT INTO posts (title, body) VALUES ($1, $2)", [data.title, data.body]);
    redirect("/posts");
  });

export default function NewPost() {
  return (
    <Form action={createPost}>
      <label>
        Title
        <input name="title" required />
      </label>
      <label>
        Body
        <textarea name="body" required />
      </label>
      <button type="submit">Create Post</button>
    </Form>
  );
}
```

The server function must be an `export` — Part 15's transform only rewrites exported `createServerFn(...)` chains. `redirect()` from [Part 14](/14-framework-middleware) throws, so the handler's job ends there; the endpoint turns it into the right kind of redirect for each kind of caller.

<Callout type="warning" title="CSRF token for no-JS posts">
If your app uses [Part 33](/33-authentication-authorization)'s auth, its global CSRF middleware also guards this endpoint. The client stub sends the token in the `X-Eigen-CSRF` header, but a plain HTML form can't set headers — so put it in the body: render `<input type="hidden" name="_csrf" value={useCsrfToken()} />` (from `eigen/auth/session`) inside the `<Form>`. The middleware accepts either source.
</Callout>

### How `<Form>` works

`<Form>` renders differently per environment:

**Server (SSR):** a plain HTML form — `action="/_eigen/fn/<id>" method="post"` — pointing at the server function's endpoint. It works before (or without) any JavaScript.

**Client (after hydration):** a React 19 form action. React calls it inside a transition with the form's `FormData`, which is what makes `useFormStatus` and `useOptimistic` work, and resets the form after a successful submission.

<FormEnhancementDiagram />

```tsx title="packages/eigen/forms.tsx"
import type { ComponentProps } from "react";
import type { ServerFn } from "./server";

type FormProps<TResult> = Omit<ComponentProps<"form">, "action" | "method" | "encType" | "onError"> & {
  action: ServerFn<any, TResult>;
  /** JS only: called with the server function's return value */
  onResult?: (result: TResult) => void;
  /** JS only: called instead of the nearest error boundary when the call fails */
  onError?: (error: Error) => void;
};

export function Form<TResult>({ action, onResult, onError, ...props }: FormProps<TResult>) {
  if (import.meta.env.SSR) {
    // No JavaScript yet: a real form that posts to the endpoint
    return <form {...props} action={action.url} method="post" />;
  }

  // Hydrated: a React form action that calls the client stub
  return (
    <form
      {...props}
      action={async (formData: FormData) => {
        // The stub sends the CSRF token as a header (Part 33), not a field
        const { _csrf, ...input } = Object.fromEntries(formData);
        try {
          onResult?.(await action(input));
        } catch (error) {
          if (!onError) throw error; // no handler: the nearest error boundary renders
          onError(error instanceof Error ? error : new Error(String(error)));
        }
      }}
    />
  );
}
```

The server and client render different `action` values, and that's fine: when the client-side `action` is a function, React skips hydration checks for the form's `action`, `method`, and `encType` attributes, precisely because frameworks render their own progressive-enhancement attributes on the server. Both paths send the validator the same shape — a plain object built from the form fields (file inputs would need a multipart path, which this toy leaves out).

Failures take different routes on the two paths. With JavaScript, a 400 or 500 makes the stub reject; `onError` turns that into UI, and without it the rejection escapes the form action and the nearest error boundary ([Part 35](/35-error-boundaries-loading)) replaces the page. Without JavaScript, the endpoint's response _is_ the page, so an invalid submission shows the raw `{"error":"Invalid input"}` JSON, and a value the handler returns is lost when the endpoint redirects back. Production frameworks carry errors across that redirect in a flash cookie or the query string; this toy leaves the no-JS error path out.

### The endpoint accepts form posts

[Part 15](/15-server-functions)'s `handleServerFnRequest` only accepts `application/json`, so a no-JS submission (`application/x-www-form-urlencoded`) would get a 415. Part 38 extends the endpoint with a second, form-specific branch. The Origin check moves to the top so it guards both branches — browsers send `Origin` on every form `POST`, so a cross-site form is still rejected:

```typescript title="packages/eigen/server-fn-endpoint.ts (Part 38 changes)"
export async function handleServerFnRequest(
  request: Request,
  serverFns: Record<string, ServerFnRegistration>,
  globalMiddleware: MiddlewareFn<any, any>[],
): Promise<Response> {
  if (request.method !== "POST") {
    return new Response("Method Not Allowed", { status: 405, headers: { Allow: "POST" } });
  }

  // Now first: applies to JSON calls and form posts alike
  if (!isSameOrigin(request)) {
    return new Response("Forbidden", { status: 403 });
  }

  const pathname = new URL(request.url).pathname;
  const fnId = pathname.slice(SERVER_FN_PREFIX.length);
  const registration = Object.hasOwn(serverFns, fnId) ? serverFns[fnId] : undefined;
  if (!registration) return Response.json({ error: "Server function not found" }, { status: 404 });

  // New: a native form submission (no JavaScript)
  if (isFormSubmission(request)) {
    return handleFormSubmission(request, registration, globalMiddleware, pathname);
  }

  if (!request.headers.get("content-type")?.startsWith("application/json")) {
    return new Response("Unsupported Media Type", { status: 415 });
  }

  // ...the JSON path from Part 15, unchanged
}

function isFormSubmission(request: Request): boolean {
  const type = request.headers.get("content-type") ?? "";
  return type.startsWith("application/x-www-form-urlencoded") || type.startsWith("multipart/form-data");
}

const seeOther = (location: string) => new Response(null, { status: 303, headers: { Location: location } });

/** Send the browser back where it came from — same-origin paths only */
function backTo(request: Request): string {
  const referer = request.headers.get("referer");
  if (!referer) return "/";
  try {
    const url = new URL(referer);
    return url.origin === new URL(request.url).origin ? url.pathname + url.search : "/";
  } catch {
    return "/";
  }
}

async function handleFormSubmission(
  request: Request,
  registration: ServerFnRegistration,
  globalMiddleware: MiddlewareFn<any, any>[],
  pathname: string,
): Promise<Response> {
  // Parse a clone: global middleware (e.g. Part 33's CSRF check, which reads
  // the `_csrf` field) still needs to read the original body
  const { _csrf, ...input } = Object.fromEntries(await request.clone().formData());

  const { context, response } = await executeMiddleware(globalMiddleware, {
    request,
    params: {},
    pathname,
  });
  // A real redirect (e.g. to /login): there's no client stub to read X-Eigen-Redirect
  if (response) return response;

  try {
    await registration.fn(input, context);
    return seeOther(backTo(request)); // Post/Redirect/Get back to the form's page
  } catch (e) {
    // redirect('/posts') in the handler → 303, so the browser follows with a GET
    if (e instanceof RedirectResponse) return seeOther(e.url);
    if (e instanceof Response) return e; // e.g. the 400 for invalid input
    console.error(`Server function ${registration.exportName} (${registration.file}) failed:`, e);
    return new Response("Server function failed", { status: 500 });
  }
}
```

With JavaScript, the same `redirect('/posts')` takes Part 15's JSON path: the endpoint answers with `X-Eigen-Redirect`, and the client stub navigates.

<Callout type="info" title="No JavaScript? No problem.">
  With JS disabled, the browser sends a standard `POST` with form-encoded fields. The endpoint's form branch parses
  them, runs the global middleware, the function's middleware, the validator, and the handler, and responds with a `303
  See Other`. The user sees a full-page navigation to the new state. This is the baseline experience — everything else
  builds on top of it.
</Callout>

## Client-side submission

When JavaScript is available, the framework enhances forms with instant feedback, pending states, and no full-page reloads.

### Calling server functions directly

For programmatic submissions outside of `<form>` elements — or when you need fine-grained control — call the server function. In the client bundle it _is_ the RPC stub from Part 15, so no hook or wrapper is needed:

```tsx title="src/components/LikeButton.tsx"
import { useTransition } from "react";
import { likePost } from "../actions/posts";

export function LikeButton({ postId }: { postId: string }) {
  const [isPending, startTransition] = useTransition();

  return (
    <button
      disabled={isPending}
      onClick={() => {
        startTransition(async () => {
          await likePost({ postId });
        });
      }}
    >
      {isPending ? "Liking..." : "♥ Like"}
    </button>
  );
}
```

The stub has the same signature as the server function but calls the generated endpoint via `fetch` under the hood. Combined with `useTransition`, the UI stays responsive while the mutation runs.

### Pending states with forms

For `<form>`-based submissions, React's `useFormStatus` hook (from `react-dom`) reads the pending state of the parent form:

```tsx title="src/components/SubmitButton.tsx"
import { useFormStatus } from "react-dom";

export function SubmitButton() {
  const { pending } = useFormStatus();
  return (
    <button type="submit" disabled={pending}>
      {pending ? "Saving..." : "Save"}
    </button>
  );
}
```

`useFormStatus` only tracks a parent `<form>` whose `action` is a function — it doesn't see `onSubmit` handlers or manual `startTransition` calls. That's why the hydrated `<Form>` passes a function as `action` rather than intercepting `onSubmit`: React's form-action machinery is what reports `pending`. Render `<SubmitButton />` inside a `<Form>` (it must be a child component, not the component that renders the form).

## Optimistic UI

Optimistic updates show the result of a mutation immediately, before the server confirms it. If the server rejects the mutation, the UI rolls back.

### The `useOptimistic` pattern

```tsx title="src/pages/todos.tsx"
import { startTransition, useOptimistic, useState } from "react";
import { addTodo, type Todo } from "../actions/todos";

export default function TodoList({ data }: { data: { todos: Todo[] } }) {
  // Confirmed state, seeded from the loader
  const [todos, setTodos] = useState(data.todos);
  const [error, setError] = useState<string | null>(null);
  const [optimisticTodos, addOptimistic] = useOptimistic(todos, (state: Todo[], newTodo: Todo) => [...state, newTodo]);

  // A form action: React already runs it inside a transition
  async function addAction(formData: FormData) {
    const title = String(formData.get("title") ?? "");

    // Show the todo immediately
    addOptimistic({ id: `temp-${Date.now()}`, title, completed: false });

    try {
      // Then persist on the server
      const saved = await addTodo({ title });
      setError(null);
      // State updates after an await need their own transition
      startTransition(() => setTodos((current) => [...current, saved]));
    } catch (err) {
      setError(err instanceof Error ? err.message : "Could not add todo");
    }
  }

  return (
    <>
      <ul>
        {optimisticTodos.map((todo) => (
          <li
            key={todo.id}
            style={{
              opacity: todo.id.startsWith("temp-") ? 0.6 : 1,
            }}
          >
            {todo.title}
          </li>
        ))}
      </ul>
      {error && <p role="alert">{error}</p>}
      <form action={addAction}>
        <input name="title" required />
        <button type="submit">Add</button>
      </form>
    </>
  );
}
```

The key: `useOptimistic` state lives only as long as the transition. When the action finishes — successfully or not — React drops the optimistic value and renders from the real state again. That's why the success path must update the confirmed state (`setTodos` with the saved row), or the new todo would vanish the moment the request completes. On failure there's nothing to undo: the temporary todo disappears on its own, and the `catch` turns the error into a message instead of letting it reach the nearest error boundary.

This form uses a client-only action (it needs JavaScript). For a no-JS fallback, use `<Form action={addTodo}>`. In this toy `<Form>` the two paths don't combine: `<Form>` owns its action function, so there's nowhere to call `addOptimistic`, and only the server function has a `.url` to post to. That's a limit of this design, not of forms in general. Frameworks built on React's Server Actions let one action serve both the no-JS post and the optimistic update.

### Error rollback

When a server function fails, the stub throws and the optimistic state unwinds:

```typescript title="src/actions/todos.ts"
import { z } from "zod";
import { createServerFn } from "eigen/server";
import { db } from "../lib/database";

// A type alias, not an interface: Part 15's handler requires a JsonValue
// result, and only type aliases get the implicit index signature that needs
export type Todo = {
  id: string;
  title: string;
  completed: boolean;
};

export const addTodo = createServerFn()
  .validator(
    z.object({
      title: z.string().trim().min(1, "Title required"),
    }),
  )
  .handler(async ({ data }) => {
    const result = await db.query("INSERT INTO todos (title) VALUES ($1) RETURNING id, title, completed", [data.title]);
    return result.rows[0] as Todo;
  });
```

If validation fails, the endpoint answers 400; if the `INSERT` fails (constraint violation, lost connection), it answers 500. Either way the stub rejects, `addAction`'s `catch` shows a message, and `useOptimistic` reverts to the confirmed list when the transition ends. No manual rollback logic needed. The message is the endpoint's, not zod's: Part 15's validator wrapper answers every invalid input with a generic `{ error: "Invalid input" }`, so "Title required" never reaches the client. To show the schema's own messages, validate on the client as well, or return them as a result (both below).

## Validation on both sides

Validation must run on the server (security) and should run on the client (UX). Sharing the schema between both sides avoids drift.

### Shared schema with zod

```typescript title="src/schemas/post.ts"
import { z } from "zod";

export const createPostSchema = z.object({
  title: z.string().min(1, "Title is required").max(200),
  body: z.string().min(1, "Body is required").max(10000),
  tags: z.array(z.string()).max(5, "Maximum 5 tags").optional(),
});

export type CreatePostInput = z.infer<typeof createPostSchema>;
```

This schema is consumed on both sides:

**Server side** — via the server function's `.validator()`, which accepts any object with a `parse()` method:

```typescript title="src/actions/posts.ts"
import { createServerFn } from "eigen/server";
import { redirect } from "eigen/middleware";
import { createPostSchema } from "../schemas/post";
import { db } from "../lib/database";

export const createPost = createServerFn()
  .validator(createPostSchema)
  .handler(async ({ data }) => {
    const result = await db.query("INSERT INTO posts (title, body, tags) VALUES ($1, $2, $3) RETURNING id", [
      data.title,
      data.body,
      data.tags ?? [],
    ]);
    redirect(`/posts/${result.rows[0].id}`);
  });
```

**Client side** — for instant feedback before submission. Client validation layers onto `<Form>` rather than replacing it, so the no-JS path keeps working:

```tsx title="src/pages/posts/new.tsx"
import { useState, type FormEvent } from "react";
import { Form } from "eigen/forms";
import { createPostSchema } from "../../schemas/post";
import { createPost } from "../../actions/posts";

export default function NewPost() {
  const [errors, setErrors] = useState<Record<string, string>>({});

  // Runs before <Form>'s action. preventDefault() cancels the submission,
  // so the action never runs and React doesn't reset what the user typed.
  function validate(event: FormEvent<HTMLFormElement>) {
    const result = createPostSchema.safeParse(Object.fromEntries(new FormData(event.currentTarget)));
    if (result.success) {
      setErrors({});
      return; // let the submission through
    }

    event.preventDefault();
    const fieldErrors: Record<string, string> = {};
    for (const issue of result.error.issues) {
      fieldErrors[String(issue.path[0])] ??= issue.message; // first message per field
    }
    setErrors(fieldErrors);
  }

  return (
    <Form action={createPost} onSubmit={validate}>
      <label>
        Title
        <input name="title" required />
        {errors.title && <span className="error">{errors.title}</span>}
      </label>
      <label>
        Body
        <textarea name="body" required />
        {errors.body && <span className="error">{errors.body}</span>}
      </label>
      <button type="submit">Create</button>
    </Form>
  );
}
```

Without JavaScript, `onSubmit` never runs: the browser posts the form, and the same schema runs in `.validator()` on the server. With JavaScript, `validate` runs first. React only starts a form action if the submit event wasn't cancelled, so invalid input never reaches the network and the fields keep their values. (React resets uncontrolled fields after every form action that completes, so cancelling is what keeps them here.) Valid input goes through `<Form>` as usual, and the handler's `redirect()` takes the user to the new post.

<Callout type="warning" title="Never trust client validation alone">
  Client-side validation is a UX optimization — it gives instant feedback. But the server function's `.validator()` is
  the security boundary. An attacker can bypass client-side checks entirely (or simply call the endpoint). The shared
  schema means you write the rules once, but they're enforced in both places.
</Callout>

### Returning field-level errors from the server

When server validation catches something client validation can't (uniqueness constraints, rate limits), the server function returns structured errors instead of throwing, and still redirects on success:

```typescript title="src/actions/posts.ts"
/** What the page gets back when the post can't be created. Success redirects instead. */
export type CreatePostResult = { fieldErrors: Record<string, string> };

export const createPost = createServerFn()
  .validator(createPostSchema)
  .handler(async ({ data }): Promise<CreatePostResult> => {
    const existing = await db.query("SELECT id FROM posts WHERE title = $1", [data.title]);
    if (existing.rows.length > 0) {
      return { fieldErrors: { title: "A post with this title already exists" } };
    }

    const result = await db.query("INSERT INTO posts (title, body, tags) VALUES ($1, $2, $3) RETURNING id", [
      data.title,
      data.body,
      data.tags ?? [],
    ]);
    redirect(`/posts/${result.rows[0].id}`);
  });
```

`redirect()` returns `never`, so TypeScript knows the function can't fall off the end. The annotation names the contract for the page. It matters more once branches return _different_ shapes, say `{ error: true, fieldErrors }` and `{ error: false, post }`. TypeScript normalizes an inferred union of object literals by adding the missing keys as optional `undefined` (`post?: undefined` on the first branch). `undefined` isn't a `JsonValue`, so Part 15's `handler` constraint rejects it. Declaring the union as a type alias and annotating the return type avoids the normalization.

The page renders the returned errors through `<Form>`'s `onResult`, and a thrown failure (the generic 400, a 500, a network error) through `onError`:

```tsx title="src/pages/posts/new.tsx"
export default function NewPost() {
  const [errors, setErrors] = useState<Record<string, string>>({});
  // React resets the form after every action that completes, and a reset // [!code ++]
  // restores each field's defaultValue: keep the last submitted values // [!code ++]
  const [values, setValues] = useState({ title: "", body: "" }); // [!code ++]

  function validate(event: FormEvent<HTMLFormElement>) {
    const result = createPostSchema.safeParse(Object.fromEntries(new FormData(event.currentTarget))); // [!code --]
    const input = Object.fromEntries(new FormData(event.currentTarget)); // [!code ++]
    setValues({ title: String(input.title ?? ""), body: String(input.body ?? "") }); // [!code ++]
    const result = createPostSchema.safeParse(input); // [!code ++]
    // ...unchanged
  }

  return (
    <Form action={createPost} onSubmit={validate}> {/* [!code --] */}
    <Form // [!code ++]
      action={createPost} // [!code ++]
      onSubmit={validate} // [!code ++]
      onResult={(result) => setErrors(result.fieldErrors)} // [!code ++]
      onError={(error) => setErrors({ form: error.message })} // [!code ++]
    > {/* [!code ++] */}
      {errors.form && <p role="alert">{errors.form}</p>} {/* [!code ++] */}
      <label>
        Title
        <input name="title" required /> {/* [!code --] */}
        <input name="title" defaultValue={values.title} required /> {/* [!code ++] */}
        {errors.title && <span className="error">{errors.title}</span>}
      </label>
      <label>
        Body
        <textarea name="body" required /> {/* [!code --] */}
        <textarea name="body" defaultValue={values.body} required /> {/* [!code ++] */}
        {errors.body && <span className="error">{errors.body}</span>}
      </label>
      <button type="submit">Create</button>
    </Form>
  );
}
```

`onResult`'s parameter is typed `CreatePostResult`, inferred from `action`. Without `defaultValue`, the duplicate-title message would appear next to an empty form: returning a result counts as a completed action, and React resets the fields. Without JavaScript, the returned errors are lost on the redirect back, as described [above](#how-form-works).

## Multi-step forms and wizards

Multi-step forms introduce state management across steps — the framework provides patterns but doesn't prescribe a single approach.

### FormData accumulation

The simplest pattern: accumulate `FormData` across steps, submit everything on the final step.

```tsx title="src/components/MultiStepForm.tsx"
import { useState } from "react";
import { createUser } from "../actions/users";

interface StepData {
  [key: string]: string;
}

export function MultiStepForm() {
  const [step, setStep] = useState(0);
  const [data, setData] = useState<StepData>({});
  const [error, setError] = useState<string | null>(null);

  async function handleStep(formData: FormData) {
    const stepData = Object.fromEntries(formData) as StepData;
    const merged = { ...data, ...stepData };
    setData(merged);

    if (step < 2) {
      setStep(step + 1);
      return;
    }

    // Final step: submit everything, then leave the wizard
    try {
      await createUser(merged);
      navigation.navigate("/dashboard");
    } catch (err) {
      // Stay on the review step, with everything entered so far still in `data`
      setError(err instanceof Error ? err.message : "Could not create the account");
    }
  }

  return (
    <form action={handleStep}>
      {error && <p role="alert">{error}</p>}
      {step === 0 && (
        <>
          <input name="name" defaultValue={data.name} required />
          <input name="email" defaultValue={data.email} required />
        </>
      )}
      {step === 1 && (
        <>
          <input name="company" defaultValue={data.company} />
          <input name="role" defaultValue={data.role} />
        </>
      )}
      {step === 2 && (
        <div>
          <p>Name: {data.name}</p>
          <p>Email: {data.email}</p>
          <p>Company: {data.company}</p>
        </div>
      )}
      <div>
        {step > 0 && (
          <button type="button" onClick={() => setStep(step - 1)}>
            Back
          </button>
        )}
        <button type="submit">{step < 2 ? "Next" : "Submit"}</button>
      </div>
    </form>
  );
}
```

### Typed FormData transforms

For type safety, transform raw `FormData` into typed objects using the shared schema:

```typescript title="packages/eigen/form-data.ts"
import type { ZodType } from "zod";

export function parseFormData<T>(
  formData: FormData,
  schema: ZodType<T>,
): { success: true; data: T } | { success: false; errors: Record<string, string> } {
  const raw: Record<string, unknown> = {};

  for (const [key, value] of formData.entries()) {
    // Handle array fields (name="tags[]")
    if (key.endsWith("[]")) {
      const arrayKey = key.slice(0, -2);
      if (!Array.isArray(raw[arrayKey])) raw[arrayKey] = [];
      (raw[arrayKey] as unknown[]).push(value);
    } else {
      raw[key] = value;
    }
  }

  const result = schema.safeParse(raw);
  if (result.success) {
    return { success: true, data: result.data };
  }

  const errors: Record<string, string> = {};
  for (const issue of result.error.issues) {
    errors[String(issue.path[0])] = issue.message;
  }
  return { success: false, errors };
}
```

## Cache revalidation after mutation

Mutations change server state — the cached data is now stale. Connecting mutations to the cache system from [Part 25](/25-use-cache) closes the loop.

### `revalidateTag` after write

```typescript title="src/actions/posts.ts"
import { z } from "zod";
import { createServerFn } from "eigen/server";
import { revalidateTag } from "eigen/cache";
import { db } from "../lib/database";

export const updatePost = createServerFn()
  .validator(z.object({ id: z.string(), title: z.string(), body: z.string() }))
  .handler(async ({ data }) => {
    await db.query("UPDATE posts SET title = $1, body = $2 WHERE id = $3", [data.title, data.body, data.id]);

    // Invalidate cached data for this post and the posts list
    await revalidateTag(`post-${data.id}`);
    await revalidateTag("posts-list");

    return { success: true };
  });
```

`revalidateTag` is async (Part 25's store may live in Redis or a KV store), so await it: the response shouldn't go out before the stale entries are gone, or the next request could still read them.

Clearing the cache doesn't change what the browser is showing. The page still holds the loader data it rendered with, and Eigen's router only fetches loader data when it navigates. A mutation that ends in `redirect()` (like `createPost`) gets that for free: the stub navigates. One that stays on the page asks for it:

```tsx title="src/pages/posts/[id]/edit.tsx (excerpt)"
await updatePost({ id, title, body });
// Re-run this route's loaders: the Part 22 router intercepts the reload
// like any other navigation and fetches fresh data from /_eigen/data
navigation.reload();
```

Without the Navigation API, `navigation.reload()` isn't available; `window.location.reload()` does the same job with a full page load.

### The revalidation flow

```
1. User submits form
2. Server function validates + mutates (database write)
3. Server function awaits revalidateTag('posts-list')
4. Cache store deletes the entries tagged 'posts-list'
5. Client asks for fresh data: redirect() navigates, or navigation.reload()
   re-runs the current route's loaders through /_eigen/data
6. The posts list loader runs fresh, and the router renders the new data
```

With optimistic UI, steps 5–6 happen in the background. The user already sees the updated state (optimistically) — the server response just confirms or corrects it.

### Stale-while-revalidate

For data that may be slightly out of date, `cacheLife` lets a cached function serve stale data while it refreshes in the background:

```typescript title="src/loaders/posts.ts"
import { cacheTag, cacheLife } from "eigen/cache";
import { db } from "../lib/database";

export async function loadPosts() {
  "use cache";
  cacheTag("posts-list");
  // Fresh for 1 minute; after that, serve the stale copy (for up to
  // 5 minutes total) while a background refresh runs
  cacheLife({ revalidate: 60, expire: 300 });

  return db.query("SELECT * FROM posts ORDER BY created_at DESC");
}
```

The two mechanisms are complementary. `cacheLife` governs _time_: between `revalidate` and `expire`, a request gets the stale result instantly and triggers a refresh. `revalidateTag` governs _events_: after a mutation, Eigen's `revalidateTag` deletes the tagged entries outright, so the next request waits for fresh data instead of seeing the pre-mutation list.

## Key insight

Forms are where all the framework layers converge — routing provides the URL, server functions handle the mutation, validation ensures correctness, middleware provides auth context, and the cache system manages staleness. Progressive enhancement isn't a legacy concern — it's the foundation. The no-JS form submission flow defines the data contract (form fields → server function → redirect), and every enhancement (pending states, optimistic updates, client validation) is layered on top without changing that contract.
