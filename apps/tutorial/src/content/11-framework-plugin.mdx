## From scattered plugins to a single export

Throughout this series, we've built separate plugins and a growing pile of manual configuration:

- **`eigenRoutes`** ([Part 2](/02-route-discovery-plugin), [Part 9](/09-hmr)) — Route discovery, virtual module generation, type declaration generation, file watching, HMR
- **`eigenStripLoaders`** ([Part 7](/07-transform-hook)) — Strips server-only code from client bundles
- **`eigenApi`** ([Part 8](/08-dev-middleware)) — API route handling in development
- **`eigenDevOverlay`** ([Part 10](/10-dev-overlay)) — The dev diagnostics panel
- **Build configuration** ([Part 6](/06-production-builds)) — The manifest, two output directories, and two separate `vite build` invocations

A framework user shouldn't need to know about these internal pieces. They should add one thing to their config. First, move the `plugins/` directory into `packages/eigen/plugins/` so the plugins live with the rest of the framework source. Then:

```typescript title="vite.config.ts"
import { resolve } from "node:path";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
// vite.config.ts is bundled and run by Node before `resolve.alias`
// exists, so the config imports the plugin by file path. Part 40 turns
// Eigen into a real package, and this becomes `from "eigen/plugin"`.
import eigen from "./packages/eigen/plugin";

export default defineConfig({
  plugins: [eigen(), react()],
  resolve: {
    alias: {
      // ...the eigen/* aliases from earlier parts, plus the router:
      "eigen/router": resolve(__dirname, "packages/eigen/router.tsx"),
    },
  },
  // No `build` block: eigen() now owns the build configuration.
});
```

Add the matching `"eigen/router": ["./packages/eigen/router.tsx"]` entry to `paths` in `tsconfig.json`.

With those in place, the framework plugin composes everything:

```typescript title="packages/eigen/plugin.ts"
import type { Plugin } from "vite";
import eigenRoutes from "./plugins/eigen-routes";
import eigenStripLoaders from "./plugins/eigen-strip-loaders";
import eigenApi from "./plugins/eigen-api";
import eigenDevOverlay from "./plugins/eigen-dev-overlay";

export interface EigenOptions {
  /** Directory containing page components. Default: 'src/pages' */
  pagesDir?: string;
  /** Directory containing API routes. Default: 'src/api' */
  apiDir?: string;
}

export default function eigen(options: EigenOptions = {}): Plugin[] {
  return [
    eigenRoutes({ pagesDir: options.pagesDir }),
    eigenStripLoaders(),
    eigenApi({ apiDir: options.apiDir }),
    eigenDevOverlay(),

    {
      name: "eigen",

      config(userConfig) {
        const userClient = userConfig.environments?.client?.build;
        const userSsr = userConfig.environments?.ssr?.build;
        const userOnwarn = userConfig.build?.rolldownOptions?.onwarn;

        return {
          // Opt into "app" builds: `vite build` creates every
          // environment and runs the buildApp hooks below
          builder: {},
          build: {
            rolldownOptions: {
              // Part 6's filter: `RouteModN.loader` is undefined for
              // pages without a loader, by design
              onwarn(warning, defaultHandler) {
                if (warning.code === "IMPORT_IS_UNDEFINED") return;
                if (userOnwarn) userOnwarn(warning, defaultHandler);
                else defaultHandler(warning);
              },
            },
          },
          environments: {
            client: {
              build: {
                // Input defaults to index.html → dist/client/index.html
                outDir: userClient?.outDir ?? "dist/client",
                manifest: userClient?.manifest ?? true,
              },
            },
            ssr: {
              build: {
                outDir: userSsr?.outDir ?? "dist/server",
                rolldownOptions: {
                  input: userSsr?.rolldownOptions?.input ?? "src/entry-server.tsx",
                },
              },
            },
          },
        };
      },

      buildApp: {
        order: "pre",
        async handler(builder) {
          await builder.build(builder.environments.client);
          await builder.build(builder.environments.ssr);
        },
      },
    },
  ];
}
```

### The `config` hook

The framework's [`config`](https://vite.dev/guide/api-plugin#config) hook sets sensible defaults:

- **`builder: {}`** — Switches `vite build` into _app_ mode (the same as `vite build --app`). Without it, Vite uses the legacy single-environment builder: only `client` exists, and our `buildApp` handler would crash on `builder.environments.ssr`.
- **`build.rolldownOptions.onwarn`** — The `IMPORT_IS_UNDEFINED` filter from [Part 6](/06-production-builds#configuring-the-builds), applied to every environment. Because a function is a scalar to the merger, the plugin's `onwarn` would replace one the user wrote — so it delegates to the user's handler for everything else.
- **`environments.client.build`** — `index.html` stays the input (Vite's default), output goes to `dist/client/`, and the manifest is written to `dist/client/.vite/manifest.json` for the production server.
- **`environments.ssr.build`** — The SSR build's own output directory and entry point. Environments named `ssr` default to `build.ssr: true`, so no `--ssr` flag is needed.

Each value checks `userConfig` first. That's not decoration. Vite **deep-merges the object a `config` hook returns on top of the existing config**, so for any scalar the plugin sets, the plugin wins. If the hook returned a bare `outDir: "dist/client"`, a user who wrote `environments: { client: { build: { outDir: "out" } } }` would be silently overridden. Reading `userConfig` and falling back is how a framework sets _defaults_ rather than _mandates_.

The `build:client` / `build:server` scripts from Part 6 can go too. A single `vite build` now produces both outputs.

<TypeDeepDive title="Concept: Deep merge vs. shallow merge">

A shallow merge (`Object.assign` or `{ ...a, ...b }`) only merges top-level properties — if both objects have a `build` key, `b.build` completely replaces `a.build`. A deep merge recurses into nested objects, so `a.build.manifest` and `b.build.outDir` both survive. Vite's [`mergeConfig`](https://vite.dev/guide/api-javascript#mergeconfig) deep-merges plugin configs this way. Two details matter for framework authors. First, when both sides set the same scalar, the later value (the plugin's return value, merged onto the user config) wins — hence the `userConfig` checks above. Second, arrays are **concatenated**, not replaced: if the user sets `optimizeDeps.include: ['a']` and a plugin returns `optimizeDeps.include: ['b']`, the result is `['a', 'b']`. That makes array-valued options safe to extend from a plugin, but impossible to _remove_ entries from by merging — a plugin that needs that must mutate the config in `configResolved` or document the conflict.

</TypeDeepDive>

### The `buildApp` hook

[`buildApp`](https://vite.dev/guide/api-environment-frameworks#the-buildapp-plugin-hook) is a Vite hook (added as a plugin hook in Vite 7) that gives the framework control over the production build process. It exists because SSR frameworks need to orchestrate _multiple coordinated builds_ — a problem that had no clean solution before the Environment API.

**Before `buildApp`:** Frameworks either ran separate `vite build` commands via npm scripts (`build:client && build:server`, exactly what we did in Part 6), or used tools like [Vinxi](https://vinxi.vercel.app) that spawned multiple Vite instances. The problem with separate commands: the builds can't share state. The client build might discover routes that the server build doesn't know about. A shared virtual module has to generate its code independently in each build, potentially producing inconsistent results.

**With `buildApp`:** In app mode, a single `vite build` command creates a `ViteBuilder` instance — the build-time equivalent of `ViteDevServer`. The builder has access to _all_ configured environments and their shared plugin pipeline. The framework's `buildApp` handler controls the build sequence:

```typescript
buildApp: {
	order: "pre",
	async handler(builder) {
		// builder.environments contains all configured environments
		// Each has its own build config (outDir, rolldownOptions, etc.)

		// Build client first — generates manifest.json
		await builder.build(builder.environments.client);

		// Build server second — can reference the client manifest
		// because the client build has already written it to disk
		await builder.build(builder.environments.ssr);
	},
}
```

The handler receives a `builder` object with `builder.environments` — a record of all configured environments. Each environment carries its own build configuration (output directory, Rolldown options, resolve conditions). The framework decides the order: client first (generates the manifest), server second (can reference the manifest). After all `buildApp` hooks run, Vite only builds environments itself if _none_ were built, so there's no double build.

Hooks run in a defined sequence: handlers with `order: 'pre'` (or no order) first, then the `builder.buildApp` config option, then handlers with `order: 'post'`. A framework builds in `'pre'`; anything that post-processes the output — static pre-rendering ([Part 16](/16-static-site-generation)) or a deployment adapter ([Part 17](/17-deployment-adapters)) — uses `order: 'post'` and finds both builds already on disk.

<BuildAppOrderDiagram />

This is how [TanStack Start](https://tanstack.com/start) orchestrates its builds. When TanStack Start migrated from Vinxi to native Vite at version 1.121.0, Vinxi's `vinxi build` command (which managed multiple Vite instances) was replaced by Vite's environment-aware app build, coordinating multiple environments within a single `vite build`. The config file moved from `app.config.ts` to `vite.config.ts`.

In later parts, when we add edge runtimes (Part 19) and RSC (Part 21), the `buildApp` handler will coordinate three or four environments — but the pattern is the same: sequential builds, ordered by dependency, sharing the same plugin pipeline.

## The three-layer type architecture

Looking at what Eigen exports, the framework's type API has three distinct layers:

### Layer 1: Static types (shipped in the npm package)

```
PageProps<TPath, TData>   — Props shape for page components
LoaderFn<TPath, TData>    — Loader function signature
RouteDefinition           — Internal route object shape
ApiHandler<TResponse>     — API route handler signature
RouteParams<TPath>        — Template literal type for param extraction
```

These types are authored by the framework developers and distributed via npm. They define contracts — the shapes that application code must conform to. They don't contain any project-specific information.

### Layer 2: Generated types (written per-project by the plugin)

```
RoutePaths                — Union of all valid route paths
RouteParamsMap            — Maps each path to its params type
```

These types are generated by the plugin at dev-server startup (and whenever the filesystem changes). They live in `node_modules/.eigen/eigen-routes.d.ts`. They contain project-specific information derived from the filesystem scan.

### Layer 3: Virtual module types (bridging runtime and types)

```
declare module 'eigen/routes' {
  export const routes: RouteDefinition[]
}
```

These declarations tell TypeScript about virtual modules — modules that exist at runtime (generated by the plugin's `load` hook) but don't have corresponding files on disk. They bridge Layer 1 (the `RouteDefinition` type) with Layer 2 (the generated route information).

### How the layers connect

<TypeLayersDiagram />

<TypeDeepDive title="TypeScript: How declaration files (`.d.ts`) work">

A `.d.ts` file contains only type information — no runtime code. TypeScript uses it to understand the shape of a module without seeing the implementation. When the plugin generates `eigen-routes.d.ts` with `type RoutePaths = '/' | '/about' | '/posts/:id'`, TypeScript treats those as the available route paths everywhere in your code. Generated `.d.ts` files are the mechanism that connects filesystem state (what files exist) to compile-time type checking (what types are valid). This is why the plugin regenerates the declaration file on every filesystem change — the types must stay in sync with reality.

</TypeDeepDive>

Application code references all three layers:

```tsx twoslash
// @filename: node_modules/eigen/types.ts
export interface PageProps<TPath extends string = string, TData = unknown> {
  params: Record<string, string>;
  data: TData;
}
export interface RouteDefinition {
  path: string;
  component: (props: Record<string, unknown>) => unknown;
}
// @filename: node_modules/eigen/route-types.ts
export type RoutePaths = "/" | "/about" | "/posts/:id";
export interface RouteParamsMap {
  "/": Record<string, never>;
  "/about": Record<string, never>;
  "/posts/:id": { id: string };
}
// @filename: node_modules/eigen/routes.ts
import type { RouteDefinition } from "eigen/types";
export declare const routes: RouteDefinition[];
// @filename: index.tsx
// The `{ ... }` body is elided prose, not code
// @noErrors: 1128
// ---cut---
// Layer 3: import from virtual module
import { routes } from "eigen/routes";

// Layer 2: import generated types
import type { RoutePaths, RouteParamsMap } from "eigen/route-types";

// Layer 1: import framework types
import type { PageProps } from "eigen/types";

// Using all three together:
function Link<T extends RoutePaths>({ to }: { to: T }) { ... }
// RoutePaths (Layer 2) constrains which paths Link accepts,
// PageProps (Layer 1) types the props each page receives,
// and the runtime route table comes from eigen/routes (Layer 3)
```

This three-layer pattern is universal across typed frameworks. [TanStack Router](https://tanstack.com/router) has static types (`RouteOptions`, `Link`), generated types (`routeTree.gen.ts`), and virtual modules. Next.js has static types (`GetServerSideProps`, `NextPage`), limited generated types (the `.next/types` directory), and internal virtual modules.

## Comparing to real frameworks

| Aspect          | Eigen                                         | [TanStack Start](https://tanstack.com/start) | [Next.js](https://nextjs.org)       |
| --------------- | --------------------------------------------- | -------------------------------------------- | ----------------------------------- |
| Plugin entry    | `eigen()` returns `Plugin[]`                  | `tanstackStart()` returns `Plugin[]`         | Not Vite-based (webpack/turbopack)  |
| Route discovery | Filesystem scan in `configResolved`           | `@tanstack/router-plugin/vite`               | Internal filesystem scanner         |
| Virtual modules | `eigen/routes`                                | Internal virtual modules                     | Webpack virtual modules             |
| Type generation | `.d.ts` in `node_modules/.eigen/`             | `routeTree.gen.ts` (committed)               | `.next/types/` (gitignored)         |
| SSR             | ModuleRunner (`environments.ssr.runner`) + H3 | Nitro server                                 | Built-in Node server                |
| Build           | `buildApp` hook                               | `buildApp` hook                              | Custom webpack/turbopack pipeline   |
| Deployment      | Manual prod server                            | Netlify/Vercel/Cloudflare adapters           | Vercel-optimized, self-hostable     |
| Code stripping  | `transform` hook                              | `.server.ts` convention                      | RSC compiler + separate compilation |
| HMR             | `hotUpdate` + React Fast Refresh              | Same                                         | Turbopack HMR                       |

The architectural patterns are identical. The differences are in scale (Eigen handles 3 routes; Next.js handles thousands), robustness (Eigen's transforms handle a handful of export shapes; Next.js's SWC/Turbopack pipeline handles the whole language), and deployment surface (Eigen has one server file; Next.js supports dozens of platforms).

## Extracting the runtime

Since [Part 4](/04-hydration#the-client-entry-point), `Router` and `Link` have lived inline in `src/entry-client.tsx` (with `matchRoute` already in `eigen/match-route`), and [Part 5](/05-typed-loaders#updating-the-client) taught `Router` to fetch fresh data on navigation. Now that Eigen has a proper package structure, it's time to move them into the framework.

One change comes along for the ride. The Part 5 `Router` read `window.location.pathname` and `window.__EIGEN_DATA__` directly, so only the client could render it — the server entry had to hand-write a matching tree (`<nav>`, `<Suspense>`, the page). Two hand-maintained copies of the same tree is how hydration mismatches happen. Instead, `Router` now takes its initial pathname and data as props. The client passes the `window` values; the server passes the request's. Everything else is Part 5's code, unchanged:

```tsx title="packages/eigen/router.tsx"
import { useState, useEffect, Suspense, type ReactNode } from "react";
import { routes } from "eigen/routes";
import { matchRoute } from "eigen/match-route";
import type { RoutePaths, RouteParamsMap } from "eigen/route-types";

interface RouterProps {
  /** window.location.pathname on the client, the request path on the server */
  initialPathname: string;
  /** window.__EIGEN_DATA__ on the client, the loader result on the server */
  initialData: unknown;
}

export function Router({ initialPathname, initialData }: RouterProps) {
  const [pathname, setPathname] = useState(initialPathname);
  const [data, setData] = useState<unknown>(initialData);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    const handler = async () => {
      const newPath = window.location.pathname;
      setPathname(newPath);
      setLoading(true);
      try {
        const res = await fetch(`/_eigen/data?path=${encodeURIComponent(newPath)}`);
        setData(await res.json());
      } finally {
        setLoading(false);
      }
    };
    window.addEventListener("popstate", handler);
    return () => window.removeEventListener("popstate", handler);
  }, []);

  const match = matchRoute(pathname, routes);
  if (!match) return <h1>404</h1>;
  const Component = match.route.component;

  return (
    <Suspense fallback={<div>Loading...</div>}>
      {loading ? <div>Loading...</div> : <Component params={match.params} data={data} />}
    </Suspense>
  );
}

type LinkProps<T extends RoutePaths> = {
  to: T;
  children: ReactNode;
} & (RouteParamsMap[T] extends Record<string, never> ? { params?: never } : { params: RouteParamsMap[T] });

export function Link<T extends RoutePaths>({ to, params, children }: LinkProps<T>) {
  let href: string = to;
  if (params) {
    href = to.replace(/:(\w+)/g, (_, key: string) => {
      return (params as Record<string, string>)[key] ?? `:${key}`;
    });
  }

  return (
    <a
      href={href}
      onClick={(e) => {
        e.preventDefault();
        window.history.pushState({}, "", href);
        window.dispatchEvent(new PopStateEvent("popstate"));
      }}
    >
      {children}
    </a>
  );
}
```

Neither component touches `window` during render — only inside effects and event handlers — so both are safe to render on the server. `matchRoute` stays in `eigen/match-route`, an implementation detail rather than a public API. `Router` and `Link` are the framework's public runtime exports:

```typescript title="packages/eigen/index.ts"
export type { PageProps, LoaderFn, RouteDefinition, RouteParams } from "./types";
export type { ApiHandler, ApiContext } from "./api-types";
export { defineLoader } from "./helpers";
export { Router, Link } from "./router";
```

### One app shell for both entries

The navigation bar is application code, not framework code, but it must be rendered identically on the server and the client. Give it one home:

```tsx title="src/app.tsx"
import { Router, Link } from "eigen/router";

export function App({ pathname, data }: { pathname: string; data: unknown }) {
  return (
    <div>
      <nav>
        <Link to="/">Home</Link> | <Link to="/about">About</Link> |{" "}
        <Link to="/posts/:id" params={{ id: "1" }}>
          Post 1
        </Link>{" "}
        |{" "}
        <Link to="/posts/:id" params={{ id: "2" }}>
          Post 2
        </Link>
      </nav>
      <Router initialPathname={pathname} initialData={data} />
    </div>
  );
}
```

Now `entry-client.tsx` becomes thin:

```tsx title="src/entry-client.tsx"
import { hydrateRoot } from "react-dom/client";
import { App } from "./app";

const root = document.getElementById("root");
if (!root) throw new Error("Root element not found");
hydrateRoot(root, <App pathname={window.location.pathname} data={window.__EIGEN_DATA__} />);
```

And the server entry renders the very same component instead of its hand-written copy. `Link` renders a plain `<a href>` on the server (the `onClick` is attached during hydration), and the `<Suspense>` boundary sits in the same place on both sides — which matters, because the client's route components are `React.lazy` and will suspend while hydrating:

```tsx title="src/entry-server.tsx"
import { renderToString } from "react-dom/server";
import { matchRoute } from "eigen/match-route";
import { routes } from "eigen/routes";
import { App } from "./app";

export interface RenderResult {
  html: string;
  status: number;
  data: unknown;
}

export async function render(pathname: string): Promise<RenderResult> {
  const match = matchRoute(pathname, routes);

  let data: unknown = null;
  if (match?.route.loader) {
    data = await match.route.loader({ params: match.params });
  }

  const html = renderToString(<App pathname={pathname} data={data} />);
  return { html, status: match ? 200 : 404, data };
}

// loadData (Part 6) is unchanged
```

The entry points do what entry points should do: mount the app, nothing more. The routing logic lives in the framework, and the shell lives in one file.

## What to observe

1. **Run `vite build`** with the unified plugin. A single command builds both environments and produces `dist/client/` (with `index.html`, `assets/`, and `.vite/manifest.json`) and `dist/server/entry-server.js`. Remove `builder: {}` from the `config` hook and run it again: Vite falls back to the legacy single-environment build, and the `buildApp` handler throws because `builder.environments.ssr` doesn't exist.

2. **Inspect the plugin array.** Add `console.log` to the `config` hook and watch how the framework's defaults merge with the user's config.

3. **Compare your `vite.config.ts`** with TanStack Start's:
   ```typescript
   // TanStack Start
   plugins: [tanstackStart(), react()];
   // Eigen
   plugins: [eigen(), react()];
   ```
   The shape is identical. The pattern is universal.

## Key insight

A framework is a _coordinated set of Vite plugins_ that handles route discovery, code generation, type generation, SSR, code stripping, build orchestration, and dev middleware. These concerns are decomposed into separate plugins but composed into a single export function. The user sees one line of config; the framework manages the complexity.

The type architecture has three layers — static types in the package, generated types per-project, and virtual module declarations bridging runtime and type system. Each layer serves a different consumer (the compiler, the IDE, the runtime) but all are generated from the same source of truth.
