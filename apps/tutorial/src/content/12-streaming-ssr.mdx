_This is the thirteenth installment in a series where we build a toy Next.js on top of Vite. In [Part 11](/11-framework-plugin), we composed Eigen into a distributable framework plugin. Now we'll replace our synchronous `renderToString` SSR with React's streaming API, enabling progressive page loads powered by Suspense boundaries._

---

## Why streaming matters

In Parts 3 and 4, we built SSR with `renderToString`. This works, but it has a fundamental bottleneck: the entire page — including all loader data — must be fetched and rendered to a complete HTML string _before the first byte is sent to the browser_. If one loader is slow (say, a database query that takes 800ms), the user stares at a blank screen for 800ms.

Streaming SSR flips this model. React sends the HTML **progressively**:

1. The **shell** — the app layout, navigation, and any content that doesn't depend on slow data — is sent immediately.
2. **Suspense fallbacks** are rendered as placeholder HTML where slow content will appear.
3. As each data dependency resolves, React streams the finished HTML plus a small inline `<script>` that swaps it into the correct placeholder. (Hydration is separate — the client React app does that once its JavaScript runs.)

<StreamingTimelineDiagram />

The browser starts rendering within milliseconds. Slow data arrives incrementally. This is the architecture that Next.js App Router and Remix both use under the hood.

## The React streaming API

React 18 introduced two streaming renderers, and React 19 ships both in its Node build:

- **`renderToReadableStream`** returns a Web [`ReadableStream`](https://developer.mozilla.org/en-US/docs/Web/API/ReadableStream) — the same type a `Response` body uses. It runs in Node 18+, Deno, Bun, and edge runtimes.
- **`renderToPipeableStream`** returns an object with a `pipe(writable)` method for Node streams.

Our server is H3, whose handlers return web-standard `Response` objects ([Part 3](/03-server-side-rendering#the-custom-dev-server)), so `renderToReadableStream` is the natural fit: its output _is_ a response body. The API looks like this:

```tsx
import { renderToReadableStream } from "react-dom/server";

// Resolves when the shell is ready; rejects if the shell fails to render
const stream = await renderToReadableStream(<App />, {
  onError(error) {
    // Called for every render error — in the shell, or inside a
    // Suspense boundary while streaming. Log it here.
  },
  signal, // an AbortSignal to stop rendering (e.g. on timeout)
});

// Resolves when every Suspense boundary has finished
await stream.allReady;
```

The critical distinction is between the **shell** and **all ready**:

**The awaited promise** resolves as soon as React has rendered everything _outside_ of Suspense boundaries. This is the minimum viable HTML — the layout, nav, and Suspense fallback placeholders. For user-facing requests, you return the stream right away for the fastest time-to-first-byte (TTFB). If the shell itself throws, the promise rejects — and since nothing has been sent yet, you can still answer with a 500 page.

**`stream.allReady`** resolves when everything — including all Suspense content — has rendered. Awaiting it before responding gives you the complete, final HTML in one go. You'd use this for crawlers/bots that need the full page, or for static site generation.

(`renderToPipeableStream` expresses the same two moments as `onShellReady` and `onAllReady` callbacks, plus `onShellError` for the rejection case. We'll see it [at the end](#node-streams-instead-of-web-streams).)

## Restructuring the page component for Suspense

Streaming only helps if your component tree has Suspense boundaries that separate fast content from slow content. This requires changing how loaders work.

In our current architecture, the server awaits the loader _before_ rendering and passes the data as a prop. With streaming, we want slow parts of the data to arrive _while_ React renders.

### Deferred values

The trick is to let a loader return some values already awaited and some still as promises. React 19's [`use`](https://react.dev/reference/react/use) hook reads a promise inside a component: if the promise is pending, the component suspends and the nearest Suspense boundary shows its fallback; when it resolves, React renders the real content and streams it.

There's one wrinkle. On the server, the slow value is a promise. On the client, after hydration, it arrives as plain JSON — the promise has already resolved, and promises don't survive serialization anyway. A tiny helper covers both cases:

```typescript title="packages/eigen/deferred.ts"
import { use } from "react";

/** A loader value that may still be in flight while the page streams. */
export type Deferred<T> = T | Promise<T>;

/**
 * Read a deferred value in a component. Suspends while it's pending
 * (on the server); returns plain values as-is (on the client).
 */
export function useDeferred<T>(value: Deferred<T>): T {
  return value instanceof Promise ? use(value) : value;
}

/**
 * Await every top-level promise in loader data, producing plain JSON.
 * Used wherever loader data is serialized instead of rendered.
 */
export async function resolveDeferred(data: unknown): Promise<unknown> {
  if (data === null || typeof data !== "object" || Array.isArray(data)) return data;
  const entries = await Promise.all(
    Object.entries(data).map(async ([key, value]) => [key, value instanceof Promise ? await value : value] as const),
  );
  return Object.fromEntries(entries);
}
```

`use` is the documented way to suspend on data in React 19, and unlike other hooks it may be called conditionally. Before `use`, libraries suspended by throwing a promise out of render — a pattern React never documented and that you shouldn't build new code on.

Add the `eigen/deferred` alias to `vite.config.ts` and `tsconfig.json` alongside the others.

### A page component using Suspense

```tsx title="src/pages/Dashboard.tsx"
import { Suspense } from "react";
import type { PageProps } from "eigen/types";
import { useDeferred, type Deferred } from "eigen/deferred";

interface Order {
  id: string;
  total: number;
}

interface DashboardData {
  stats: { users: number; revenue: number };
  recentOrders: Deferred<Order[] | null>;
}

// Stand-ins for a database: one fast query, one slow one
const wait = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));
async function fetchStats() {
  await wait(50);
  return { users: 1042, revenue: 54300 };
}
async function fetchRecentOrders(): Promise<Order[]> {
  await wait(800);
  return [
    { id: "001", total: 120 },
    { id: "002", total: 87 },
  ];
}

export async function loader(): Promise<DashboardData> {
  return {
    // Fast: awaited, so it's part of the shell
    stats: await fetchStats(),
    // Slow: NOT awaited. The promise travels to the component.
    // The .catch turns a failure into a value the UI can render.
    recentOrders: fetchRecentOrders().catch(() => null),
  };
}

function StatsPanel({ stats }: { stats: DashboardData["stats"] }) {
  return (
    <div>
      <h2>Stats</h2>
      <p>Users: {stats.users}</p>
      <p>Revenue: ${stats.revenue}</p>
    </div>
  );
}

function RecentOrders({ orders }: { orders: DashboardData["recentOrders"] }) {
  const list = useDeferred(orders); // Suspends while the query is pending
  if (!list) return <p>Couldn't load recent orders.</p>;
  return (
    <div>
      <h2>Recent Orders</h2>
      <ul>
        {list.map((o) => (
          <li key={o.id}>
            #{o.id}: ${o.total}
          </li>
        ))}
      </ul>
    </div>
  );
}

export default function Dashboard({ data }: PageProps<"/dashboard", DashboardData>) {
  return (
    <div>
      <h1>Dashboard</h1>
      <StatsPanel stats={data.stats} />

      {/* This Suspense boundary enables streaming.
          The shell sends with the fallback, and the
          orders content streams in when ready. */}
      <Suspense fallback={<div>Loading orders...</div>}>
        <RecentOrders orders={data.recentOrders} />
      </Suspense>
    </div>
  );
}
```

The key architectural insight: the stats are awaited and available immediately, but `recentOrders` is a promise that might still be pending. The Suspense boundary around `<RecentOrders>` tells React "stream the fallback now, stream the real content when the promise resolves." The loader catches its own failure for a reason: a rejected promise passed to `use` would throw to the nearest error boundary, and error boundaries don't run during SSR ([Part 35](/35-error-boundaries-loading) covers that path).

### Resolving deferred data for the data endpoint

Client-side navigations don't stream — they fetch JSON from `/_eigen/data` ([Part 5](/05-typed-loaders#the-data-endpoint)). `JSON.stringify` turns a pending promise into `{}`, so the endpoint must wait for deferred values first. Both the dev middleware and the production route call `runLoader`, so one line fixes both:

```typescript title="packages/eigen/run-loader.ts"
import { matchRoute } from "./match-route";
import { resolveDeferred } from "./deferred"; // [!code ++]
import type { RouteDefinition } from "./types";

export async function runLoader(pathname: string, routes: RouteDefinition[]): Promise<unknown> {
  const match = matchRoute(pathname, routes);
  if (!match || !match.route.loader) return null;
  return match.route.loader({ params: match.params }); // [!code --]
  return resolveDeferred(await match.route.loader({ params: match.params })); // [!code ++]
}
```

## Updating the server entry for streaming

Replace `render` in `entry-server.tsx` with a streaming `renderStream`. It renders the same `<App>` from [Part 11](/11-framework-plugin#one-app-shell-for-both-entries) that the client hydrates — same nav, same `Router`, same Suspense boundaries — so the server and client trees match by construction:

```tsx title="src/entry-server.tsx"
import { renderToReadableStream, type ReactDOMServerReadableStream } from "react-dom/server";
import { matchRoute } from "eigen/match-route";
import { routes } from "eigen/routes";
import { serializeForScript } from "eigen/serialize";
import { resolveDeferred } from "eigen/deferred";
import { App } from "./app";

export interface StreamOptions {
  /** index.html (through transformIndexHtml in dev) with the <!--ssr-outlet--> marker */
  template: string;
  /** Wait for every Suspense boundary before responding (bots, SSG) */
  waitForAll?: boolean;
}

export async function renderStream(
  pathname: string,
  { template, waitForAll = false }: StreamOptions,
): Promise<Response> {
  const match = matchRoute(pathname, routes);

  // Run the loader. Awaited fields are ready now; deferred ones are still promises.
  let data: unknown = null;
  if (match?.route.loader) {
    data = await match.route.loader({ params: match.params });
  }

  // Split the template at the outlet marker
  const [htmlBefore, htmlAfter] = template.split("<!--ssr-outlet-->");
  const encoder = new TextEncoder();

  // Abort rendering after 10s so a hung query can't hold the response open.
  // React flushes the fallbacks of unfinished boundaries and lets the client retry them.
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(new Error("SSR timeout")), 10_000);

  let didError = false;
  let reactStream: ReactDOMServerReadableStream;
  try {
    reactStream = await renderToReadableStream(<App pathname={pathname} data={data} />, {
      signal: controller.signal,
      onError(error) {
        didError = true;
        console.error("Streaming SSR error:", error);
      },
    });
  } catch (error) {
    // The shell failed. Nothing has been sent yet, so we can still send a 500.
    clearTimeout(timeout);
    console.error("Shell render failed:", error);
    return new Response("<h1>Server Error</h1>", {
      status: 500,
      headers: { "Content-Type": "text/html; charset=utf-8" },
    });
  }

  // Bot/SSG mode: wait until every boundary has resolved
  if (waitForAll) await reactStream.allReady;

  // Wrap React's stream: template head first, React's HTML in the middle,
  // then — only after React has finished — the data script and the rest
  // of the template (which holds the client entry <script>).
  const body = reactStream.pipeThrough(
    new TransformStream<Uint8Array, Uint8Array>({
      start(controller) {
        controller.enqueue(encoder.encode(htmlBefore));
      },
      async flush(controller) {
        clearTimeout(timeout);
        const resolved = await resolveDeferred(data);
        controller.enqueue(
          encoder.encode(`<script>window.__EIGEN_DATA__ = ${serializeForScript(resolved)}</script>${htmlAfter}`),
        );
      },
    }),
  );

  return new Response(body, {
    // In streaming mode this reflects errors up to the shell; in bot mode, all of them
    status: didError ? 500 : match ? 200 : 404,
    headers: { "Content-Type": "text/html; charset=utf-8" },
  });
}
```

`flush` is the important detail. It runs exactly once, after React closes its stream, and it can still enqueue output — so `htmlAfter` always lands _after_ the last Suspense chunk, and nothing is ever written after the stream ends.

<StreamAssemblyDiagram />

The data script goes in `flush` too, and that's deliberate. By the time React finishes, every deferred promise has resolved, so `resolveDeferred` produces the complete data without waiting. And the client entry is a `<script type="module">`, which the browser only runs after the whole document has been parsed — so `window.__EIGEN_DATA__` is always in place, with the orders already filled in, before `hydrateRoot` runs. `serializeForScript` (from [Part 3](/03-server-side-rendering)) escapes `<`, `>`, `&`, and the U+2028/U+2029 line separators, so a loader string containing `</script>` can't break out of the tag.

<Callout type="info" title="Streaming display, then hydration">
With this setup the user *sees* content progressively, but hydration starts after the last chunk arrives. That's the right trade-off for a toy framework. Production frameworks go further: they load the client entry early (e.g. `bootstrapModules` in React's options) and stream each deferred value as its own small `<script>` chunk, so hydration can start — and [selective hydration](https://react.dev/reference/react-dom/client/hydrateRoot) can prioritize — while slow boundaries are still loading.
</Callout>

### Updating the dev server

The H3 dev server from [Part 3](/03-server-side-rendering#the-custom-dev-server) barely changes. The SSR handler already returns a `Response`, and `renderStream` now _produces_ one — H3 streams its body to the socket chunk by chunk:

```typescript title="server.ts"
import { readFileSync } from "node:fs";
import { H3, serve, fromNodeHandler } from "h3/node";
import { createServer as createViteServer, isRunnableDevEnvironment, type ViteDevServer } from "vite";

interface StreamOptions {
  template: string;
  waitForAll?: boolean;
}

// Simplified — a production implementation would use a library like
// `isbot` for comprehensive bot detection
const isBot = (request: Request) => /bot|crawler|spider|googlebot/i.test(request.headers.get("user-agent") ?? "");

async function start() {
  const vite: ViteDevServer = await createViteServer({
    server: { middlewareMode: true },
    appType: "custom",
  });

  const app = new H3();

  app.use(fromNodeHandler(vite.middlewares as Parameters<typeof fromNodeHandler>[0]));

  app.all("/**", async (event) => {
    const url = event.url.pathname;

    try {
      // Transform the template BEFORE splitting it (see below)
      let template = readFileSync("index.html", "utf-8");
      template = await vite.transformIndexHtml(url, template);

      const ssrEnv = vite.environments.ssr;
      if (!isRunnableDevEnvironment(ssrEnv)) {
        throw new Error("SSR environment is not runnable");
      }
      const { renderStream } = (await ssrEnv.runner.import("/src/entry-server.tsx")) as {
        renderStream: (pathname: string, options: StreamOptions) => Promise<Response>;
      };

      return await renderStream(url, {
        template,
        waitForAll: isBot(event.req),
      });
    } catch (e) {
      console.error(e);
      return new Response(e instanceof Error ? e.message : "Internal Server Error", {
        status: 500,
      });
    }
  });

  serve(app, { port: 3000 });
  console.log("http://localhost:3000");
}

start();
```

The production server from [Part 6](/06-production-builds) changes the same way: read `dist/client/index.html` once at startup, import `renderStream` from `dist/server/entry-server.js`, and return `renderStream(event.url.pathname, { template, waitForAll: isBot(event.req) })` from the SSR route.

## How streaming HTML actually works on the wire

When you view the network response for a streaming SSR page, it looks surprising. The browser receives something like this, in chunks over time:

**Chunk 1 (immediate — the shell):**

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <title>Eigen Framework</title>
  </head>
  <body>
    <div id="root">
      <div>
        <nav>...</nav>
        <h1>Dashboard</h1>
        <div>
          <h2>Stats</h2>
          <p>Users: 1042</p>
          <p>Revenue: $54300</p>
        </div>
        <!--$?--><template id="B:0"></template>
        <div>Loading orders...</div>
        <!--/$-->
      </div>
    </div>
  </body>
</html>
```

The `<!--$?-->` and `<template id="B:0">` markers are React's Suspense boundary placeholders. The fallback ("Loading orders...") is visible HTML. The `B:0` template is an empty insertion point.

**Chunk 2 (800ms later — when the orders query resolves):**

```html
<div hidden id="S:0">
  <div>
    <h2>Recent Orders</h2>
    <ul>
      <li>#001: $120</li>
      ...
    </ul>
  </div>
</div>
<script>
  // React's inline script that swaps the fallback for the real content
  $RC = function (b, s) {
    // ... swap the template B:0 with the content S:0
  };
  $RC("B:0", "S:0");
</script>
```

**Chunk 3 (when React's stream closes — our `flush`):**

```html
</div><script>window.__EIGEN_DATA__ = {"stats":{...},"recentOrders":[...]}</script>
  <script type="module" src="/src/entry-client.tsx"></script>
</body>
</html>
```

React sends the resolved content in a hidden `<div>`, then a `<script>` that performs the DOM swap — replacing the fallback with the real content. That swap is plain DOM manipulation; the new nodes become interactive when the client app hydrates. The browser progressively renders the page without a full page reload.

## Template splitting and `transformIndexHtml` considerations

Streaming changes how we use `transformIndexHtml`. With `renderToString`, we had the complete HTML and could do simple string replacement. With streaming, we need to split the template into "before the React root" and "after the React root" and write them at different times.

There's a subtlety here: `transformIndexHtml` adds Vite's HMR client script and the React Refresh preamble into `<head>`. This transformation must happen _before_ we split the template, because the `<head>` content needs to be in the first chunk that the browser receives. If it's deferred to after the stream, the browser won't establish the HMR WebSocket connection until the page has fully streamed.

```typescript
// The order matters:
let template = readFileSync("index.html", "utf-8");
template = await vite.transformIndexHtml(url, template); // ← FIRST: inject HMR client
const [before, after] = template.split("<!--ssr-outlet-->"); // ← THEN: split (inside renderStream)
```

For production, `transformIndexHtml` isn't called (there's no dev server). The built `dist/client/index.html` already has the hashed asset URLs. But the split pattern is the same.

## Typing the stream

The streaming API changes the shape of the server entry's contract. With `renderToString`, the return type was simple data: `Promise<{ html: string; status: number; data: unknown }>`. With streaming, there's no single HTML string — the output is a stream that's still being produced when the function returns.

Returning a `Response` captures that precisely:

```typescript
export interface StreamOptions {
  template: string; // HTML template to split
  waitForAll?: boolean; // Bot mode vs. streaming mode
}

export function renderStream(pathname: string, options: StreamOptions): Promise<Response>;
```

The status code and headers are fixed the moment the `Response` is returned; the body keeps flowing afterwards. This changes the error handling contract: errors during streaming can't be caught by the caller in the usual way, because the status code has already been sent. The rejected shell promise and the `onError` callback handle this instead.

<Callout type="warn">
  This is a real framework design tension. Remix solves it by providing `handleError` in the entry server. Next.js uses
  `error.tsx` boundaries. The core issue is the same: once you've started streaming a 200 response, you can't change it
  to a 500 if a Suspense boundary fails mid-stream.
</Callout>

## Node streams instead of Web streams

`renderToReadableStream` returns a Web stream, which is why the same `renderStream` code runs unchanged on Node, Bun, Deno, and the edge environment we'll add in [Part 19](/19-edge-runtimes). If your server is built on Node's `http.ServerResponse` instead (Express, a raw `http` server), `renderToPipeableStream` avoids the Web-stream adapter. The same rule applies: write `htmlAfter` only after React is done. React's `pipe()` calls `end()` on its destination when it finishes, so you can't `res.write()` afterwards — pipe React into a `Transform` whose `flush` appends the tail instead:

```tsx
import { Transform } from "node:stream";
import type { ServerResponse } from "node:http";
import type { ReactNode } from "react";
import { renderToPipeableStream } from "react-dom/server";
import { serializeForScript } from "eigen/serialize";
import { resolveDeferred } from "eigen/deferred";

function renderToNode(res: ServerResponse, app: ReactNode, htmlBefore: string, data: unknown, htmlAfter: string) {
  let didError = false;
  const { pipe, abort } = renderToPipeableStream(app, {
    onShellReady() {
      res.statusCode = didError ? 500 : 200;
      res.setHeader("Content-Type", "text/html; charset=utf-8");
      res.write(htmlBefore);

      const tail = new Transform({
        transform(chunk, _encoding, callback) {
          callback(null, chunk); // pass React's chunks through untouched
        },
        flush(callback) {
          // Runs after React ends the Transform — the last chance to write
          resolveDeferred(data).then((resolved) => {
            this.push(`<script>window.__EIGEN_DATA__ = ${serializeForScript(resolved)}</script>${htmlAfter}`);
            callback();
          }, callback);
        },
      });
      tail.pipe(res); // ends `res` after flush
      pipe(tail);
    },
    onShellError(error) {
      res.statusCode = 500;
      res.setHeader("Content-Type", "text/html; charset=utf-8");
      res.end("<h1>Server Error</h1>");
    },
    onError(error) {
      didError = true;
      console.error("Streaming SSR error:", error);
    },
  });
  setTimeout(() => abort(), 10_000);
}
```

For bots, do the same work in `onAllReady` instead of `onShellReady`. The type difference between the two APIs is the real cost: Node streams tie the server entry to `ServerResponse`, while Web streams give you a plain `Response` that any runtime can serve. That's why Eigen standardizes on the Web version.

## What to observe

1. **Open DevTools → Network** and watch the response timing. With `renderToString`, the document request completes all at once. With streaming, you'll see the response start quickly (the shell) and the content length grow incrementally.

2. **View the raw response** with `curl -N http://localhost:3000/dashboard`. You'll see the shell arrive immediately, then after a pause, the Suspense resolution script, then the `__EIGEN_DATA__` script and the closing tags.

3. **Compare TTFB** (Time to First Byte) between the `renderToString` and streaming approaches. With a slow _deferred_ query, the difference is dramatic — the shell arrives after the awaited part of the loader (~50ms here), regardless of how long the orders query takes.

4. **Test bot mode.** Change the user-agent to `Googlebot` and observe that the response waits for `allReady` — the full HTML arrives in one chunk, ensuring crawlers see complete content.

5. **Error during streaming.** Remove the `.catch` from `fetchRecentOrders()` and make it reject after a delay. The shell renders successfully and the fallback appears; the error is logged by `onError`, and React tells the client to retry that boundary itself. The response stream doesn't crash.

6. **Navigate to the dashboard client-side.** The `/_eigen/data` request takes the full 800ms, because `resolveDeferred` waits for the orders before responding. Only the initial, server-rendered load streams.

## Key insight

Streaming SSR changes the contract between the server and the browser from "here's a complete page" to "here's the start of a page, more is coming." This is fundamentally enabled by two things: a streamed HTTP response body (the transport) and React Suspense (the component model that declares data dependencies declaratively).

From a Vite perspective, streaming doesn't change the plugin architecture — `resolveId`, `load`, `transform`, and `configureServer` all work the same. What changes is the _server entry point_ and the _dev server handler_. The H3 handler switches from returning a finished HTML string to returning a `Response` whose body is still being written. The template must be split before streaming begins, and the tail must wait until React is done. And error handling moves from try/catch to stream callbacks.

This is why framework authors care about Suspense — it's not just a loading indicator pattern. It's the mechanism that enables progressive server rendering, and it requires the framework's SSR layer to support streaming responses.
